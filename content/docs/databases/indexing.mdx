## Ý chính

Một bảng một triệu dòng có người dùng đang hỏi: "cho tôi dòng có token này". Không có gợi ý nào, cơ sở dữ liệu chỉ có cách đọc **mọi dòng** để so sánh (quét tuần tự, `Θ(n)`). **<Term>Index</Term>** (chỉ mục) là một cấu trúc phụ, lưu bên cạnh bảng, giúp đi thẳng tới dòng cần tìm trong `O(log n)` bước đọc. Gần như mọi chỉ mục quan hệ là một **<Term>B-tree</Term>** (chính xác là B+ tree) mà bạn đã gặp ở bài [Tree](/docs/dsa/trees): cây cân bằng, mỗi nút là một **trang đĩa** chứa hàng trăm khoá, nên cây rất thấp.

Chỉ mục là đánh đổi chứ không phải phép màu: nó **tăng tốc đọc, làm chậm ghi, và tốn chỗ**; một chỉ mục sai chỗ không giúp gì mà vẫn trả cả hai cái giá. Bài này đi theo trình tự: dữ liệu nằm trong bảng thế nào (heap và trang); B+ tree tự cài rồi so với B-tree thật của PostgreSQL, bằng cách **tính tay chiều cao và fan-out rồi đối chiếu với trang thật** (`pageinspect`); chỉ mục clustered và secondary, và vì sao thứ tự trên đĩa quan trọng; composite index và quy tắc tiền tố trái; covering index và index-only scan; hash, GIN, BRIN; chi phí ghi; và sáu lý do planner **bỏ qua** chỉ mục dù nó có sẵn. Mọi con số là output thật từ **PostgreSQL 16.15** trong WSL của máy viết bài, trên bảng 1.000.000 dòng. Bài trước là [Relational Model & SQL](/docs/databases/relational-model) (cách đọc `EXPLAIN`); bài sau là [Transactions](/docs/databases/transactions).

## Dữ liệu nằm ở đâu: heap và trang

Một bảng trong PostgreSQL là một **heap file**: dãy các **trang** (page) cỡ 8 KB, mỗi trang chứa nhiều dòng. Đơn vị đọc ghi đĩa (và đọc vào bộ nhớ đệm) là trang, không phải dòng, giống mọi cấu trúc ở [File Systems](/docs/os/file-systems) và [Tree](/docs/dsa/trees). Mỗi dòng có địa chỉ vật lý **`ctid` = (số trang, vị trí trong trang)**. Dựng một bảng 1.000.000 dòng gồm `id` tăng dần, `rnd` ngẫu nhiên, `token` là `md5(id)`, `created` tăng theo `id`, và ba cột nhỏ `a`, `b`, `c`:

```sql
\pset null '∅'
CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT setseed(0.42);
DROP TABLE IF EXISTS t;
-- 1.000.000 dòng. id tăng dần; rnd là cùng dãy 1..N nhưng xáo ngẫu nhiên; created tăng theo id.
CREATE TABLE t AS
SELECT g                          AS id,
       (random() * 1000000)::int  AS rnd,
       md5(g::text)               AS token,
       timestamp '2026-01-01' + g * interval '1 second' AS created,
       (g % 50)                   AS a,
       (g % 20)                   AS b,
       (g % 7)                    AS c
FROM generate_series(1, 1000000) g;
ANALYZE t;

\echo '== kích thước bảng (heap) =='
SELECT pg_size_pretty(pg_relation_size('t')) AS heap_size,
       pg_relation_size('t') / 8192            AS pages,
       (SELECT count(*) FROM t)                AS rows,
       round(1000000.0 / (pg_relation_size('t') / 8192), 1) AS rows_per_page;

\echo ''
\echo '== ctid = (trang, vị trí trong trang) của dòng: heap là các trang 8 KB =='
SELECT ctid, id, token FROM t WHERE id IN (1, 2, 3, 150, 151, 152, 999999) ORDER BY id;

\echo ''
\echo '== nhìn vào bên trong một trang bằng pageinspect (trang số 0) =='
SELECT lp AS slot, lp_off AS offset_in_page, lp_len AS len, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('t', 0)) ORDER BY lp LIMIT 4;
SELECT lower, upper, special, pagesize FROM page_header(get_raw_page('t', 0));
```

Hệ quả cho chỉ mục: một chỉ mục **không chứa dòng**, mà chứa **khoá cộng `ctid`** trỏ về heap. Tìm bằng chỉ mục gồm hai bước: đi xuống cây để lấy `ctid`, rồi đọc đúng trang heap đó.

## Không có chỉ mục: quét tuần tự

Tìm dòng có `token = '8f14e45f...'` (đây là `md5('7')`, nên đúng một dòng khớp). Lần một chưa có chỉ mục nào; lần hai tạo B-tree trên `token`:

## B+ tree: từ trang đĩa tới chiều cao

### Tự cài một B+ tree tối giản

Bài [Tree](/docs/dsa/trees) cài B-tree để minh hoạ ý tưởng. Hầu hết chỉ mục thật là **B+ tree**, khác ở hai điểm: dữ liệu (khoá và giá trị hay `ctid`) chỉ ở **lá**, nút trong chỉ giữ khoá dẫn đường, và các lá được **nối thành danh sách liên kết**. Dưới đây là một B+ tree tối giản, mỗi nút là một "trang" chứa tối đa `order` khoá; bộ đếm `reads` đếm số trang chạm tới:

```python
# B+ tree tối giản: khoá chỉ nằm ở lá, các lá nối thành danh sách liên kết, mỗi nút = một "trang".
import bisect, random, math

class Leaf:
    def __init__(self): self.keys, self.vals, self.next = [], [], None
class Inner:
    def __init__(self): self.keys, self.kids = [], []        # len(kids) = len(keys) + 1

class BPlusTree:
    def __init__(self, order):
        self.order = order                                    # số khoá tối đa mỗi nút (fan-out)
        self.root = Leaf(); self.reads = 0                    # reads = số "trang" đã chạm tới

    def _leaf_for(self, key):
        n, path = self.root, []
        while isinstance(n, Inner):
            self.reads += 1
            path.append(n)
            n = n.kids[bisect.bisect_right(n.keys, key)]
        self.reads += 1
        return n, path

    def get(self, key):
        leaf, _ = self._leaf_for(key)
        i = bisect.bisect_left(leaf.keys, key)
        return leaf.vals[i] if i < len(leaf.keys) and leaf.keys[i] == key else None

    def range(self, lo, hi):                                  # tìm lá chứa lo, rồi đi ngang theo con trỏ next
        leaf, out = self._leaf_for(lo)[0], []
        while leaf:
            for k, v in zip(leaf.keys, leaf.vals):
                if k > hi: return out
                if k >= lo: out.append((k, v))
            leaf = leaf.next
            if leaf: self.reads += 1
        return out

    def insert(self, key, val):
        leaf, path = self._leaf_for(key)
        i = bisect.bisect_left(leaf.keys, key)
        if i < len(leaf.keys) and leaf.keys[i] == key: leaf.vals[i] = val; return
        leaf.keys.insert(i, key); leaf.vals.insert(i, val)
        if len(leaf.keys) <= self.order: return
        mid = len(leaf.keys) // 2                             # lá đầy: tách đôi, khoá giữa được SAO lên cha (vẫn giữ ở lá)
        right = Leaf()
        right.keys, right.vals = leaf.keys[mid:], leaf.vals[mid:]
        leaf.keys, leaf.vals = leaf.keys[:mid], leaf.vals[:mid]
        right.next, leaf.next = leaf.next, right
        self._push_up(path, leaf, right.keys[0], right)

    def _push_up(self, path, left, sep, right):
        if not path:                                          # tách tới tận gốc: cây cao thêm một tầng
            r = Inner(); r.keys, r.kids = [sep], [left, right]; self.root = r; return
        parent = path.pop()
        i = bisect.bisect_right(parent.keys, sep)
        parent.keys.insert(i, sep); parent.kids.insert(i + 1, right)
        if len(parent.keys) <= self.order: return
        mid = len(parent.keys) // 2                           # nút trong đầy: khoá giữa ĐI LÊN (không còn ở nút trong con)
        up = parent.keys[mid]
        sib = Inner(); sib.keys, sib.kids = parent.keys[mid + 1:], parent.kids[mid + 1:]
        parent.keys, parent.kids = parent.keys[:mid], parent.kids[:mid + 1]
        self._push_up(path, parent, up, sib)

    def stats(self):
        h, n = 1, self.root
        while isinstance(n, Inner): n = n.kids[0]; h += 1
        leaves, keys = 0, 0
        while n: leaves += 1; keys += len(n.keys); n = n.next
        return h, leaves, keys / (leaves * self.order)       # chiều cao, số lá, độ đầy trung bình của lá

if __name__ == "__main__":
    ORDER = 100                                               # ~100 khoá mỗi trang
    random.seed(5)
    N = 200_000
    keys = random.sample(range(10 * N), N)

    t = BPlusTree(ORDER)
    for k in keys: t.insert(k, k * 2)
    assert all(t.get(k) == k * 2 for k in keys[:5000])
    h, leaves, fill = t.stats()
    print(f"{N:,} khoá, order = {ORDER}: cao {h} tầng, {leaves:,} lá, độ đầy trung bình của lá = {fill:.0%}")

    t.reads = 0
    for k in keys[:10_000]: t.get(k)
    print(f"tìm 1 khoá: {t.reads / 10_000:.2f} trang mỗi lần (= chiều cao); quét tuần tự cả bảng cần {leaves:,} trang")

    lo = sorted(keys)[N // 2]; hi = lo + 10 * N // 100       # khoảng chứa khoảng 1% số khoá
    t.reads = 0
    res = t.range(lo, hi)
    assert [k for k, _ in res] == [k for k in sorted(keys) if lo <= k <= hi]
    print(f"tìm khoảng 1% ({len(res):,} khoá): {t.reads} trang (xuống lá đầu tiên rồi đi ngang qua các lá kế tiếp)")

    print()
    print(f"{'cách chèn':<24} {'cao':>4} {'số lá':>8} {'độ đầy lá':>10}")
    for name, order_keys in (("ngẫu nhiên", keys), ("tăng dần", sorted(keys)), ("giảm dần", sorted(keys, reverse=True))):
        t = BPlusTree(ORDER)
        for k in order_keys: t.insert(k, 0)
        h, leaves, fill = t.stats()
        print(f"{name:<24} {h:>4} {leaves:>8,} {fill:>10.0%}")
    ideal = math.ceil(N / ORDER)
    print(f"{'nạp hàng loạt (100%)':<24} {'':>4} {ideal:>8,} {'100%':>10}   (lý tưởng: {N:,} / {ORDER} = {ideal:,} lá)")

    print()
    print("chiều cao theo số khoá và fan-out (tính: ceil(log_fanout(N))), mỗi khoá 8 byte + con trỏ 8 byte, trang 8 KB ≈ 500 khoá:")
    for n in (10**6, 10**8, 10**10):
        print(f"  N = {n:>14,}: " + ", ".join(f"fan-out {f}: {math.ceil(math.log(n, f))} tầng" for f in (2, 100, 500)))
```

```text
  N =    100,000,000: fan-out 2: 27 tầng, fan-out 100: 4 tầng, fan-out 500: 3 tầng
  N = 10,000,000,000: fan-out 2: 34 tầng, fan-out 100: 5 tầng, fan-out 500: 4 tầng
```

Với 200.000 khoá và 100 khoá mỗi trang:

- Cây chỉ cao **3 tầng**, nên tìm một khoá luôn chạm đúng 3 trang, trong khi quét cả bảng cần 2.911 trang.
- **Truy vấn khoảng** (1% số khoá, 1.971 khoá) tốn 28 trang: 3 để xuống lá đầu tiên rồi đi ngang qua khoảng 25 lá kế tiếp theo con trỏ `next`. Đây là lý do B+ tree thắng B-tree thường trong cơ sở dữ liệu: khoảng là thao tác chủ lực (`BETWEEN`, `ORDER BY ... LIMIT`, `>`), và các lá được nối sẵn.
- **Độ đầy của lá phụ thuộc thứ tự chèn**: chèn ngẫu nhiên cho lá đầy **69%** (đúng `ln 2 ≈ 0,69`, kết quả kinh điển), nhưng chèn **tăng dần** cho lá đầy **50%** (mỗi lần lá cuối đầy, tách đôi, nửa trái không bao giờ được chèn thêm nữa), tốn 3.999 lá thay vì 2.000 lá của **nạp hàng loạt** (bulk load, dựng từ dữ liệu đã sắp xếp, đầy 100%). PostgreSQL xử lý trường hợp chèn tăng dần phổ biến này bằng cách khi lá **ngoài cùng bên phải** bị tách, nó giữ lá trái đầy tới `fillfactor` (mặc định 90%) thay vì chia 50/50; còn `CREATE INDEX` trên bảng có sẵn dữ liệu sắp xếp rồi dựng thẳng từ dưới lên.

### B-tree thật của PostgreSQL và phép tính tay

Giờ so với chỉ mục thật. Phần cuối của `idx_basic` lấy thông tin cấu trúc bằng `pageinspect`:

- Chỉ mục `token` (chuỗi 32 ký tự): **56 MB, 7.210 trang**, gốc có **65 khoá**, một lá mẫu có **141 khoá**. Cây có `level = 2` (số tầng phía trên lá), tức tổng **3 tầng**: gốc, một tầng giữa, lá.
- Khoá chính `id` (số nguyên 4 byte): **21 MB**, gốc **10 khoá**, một lá có **367 khoá**, cũng 3 tầng.

Tính tay để thấy các con số này không tình cờ. Một trang 8.192 byte trừ phần đầu trang (24 byte) và vùng đặc biệt cuối trang (16 byte) còn **8.152 byte**; B-tree lá của PostgreSQL mặc định chỉ đổ đầy tới **`fillfactor` 90%**, nên dùng được `8.152 × 0,9 ≈ 7.337` byte. Một mục chỉ mục cho khoá `int4` là: đầu mục 8 byte (chứa `ctid`) cộng 4 byte khoá, căn lề lên **16 byte**, cộng 4 byte con trỏ dòng, tức **20 byte** mỗi mục. Vậy mỗi lá chứa `7.337 / 20 ≈ 367` mục. Output báo đúng **367**. Với khoá `md5` 32 ký tự: 8 byte đầu mục, cộng 33 byte (1 byte độ dài cộng 32 ký tự), căn lề lên 48 byte, cộng 4 byte con trỏ dòng, tức **52 byte** mỗi mục: `7.337 / 52 ≈ 141` mục mỗi lá, đúng **141** như output.

Từ đó suy ra chiều cao: `1.000.000 / 367 ≈ 2.725` lá cho `id`; mỗi nút trong cũng chứa vài trăm con trỏ xuống con, nên cần khoảng 8 đến 10 nút trong, và một gốc nhỏ trỏ vào chúng: gốc 10 mục là hợp lý. Tổng ba tầng. Mỗi lần nhân dữ liệu lên 300 đến 400 lần mới thêm một tầng: ở `1.000.000` dòng, 3 tầng; tới khoảng `50 triệu` dòng mới cần 4 tầng (`367^3 ≈ 49 triệu`) cho khoá nguyên (với khoá chuỗi dài thì sớm hơn). Vì vậy tìm một khoá trong bảng tỉ dòng cũng chỉ vài lần đọc trang, và vài tầng trên cùng luôn nằm sẵn trong bộ nhớ đệm.

Một nhận xét về kích thước: chỉ mục `token` (56 MB) bằng khoảng **58% kích thước bảng** (97 MB) vì khoá dài; chỉ mục `id` chỉ 21 MB. **Khoá ngắn, chỉ mục nhỏ, cây thấp, nhiều khoá nằm trong bộ nhớ đệm hơn.**

## Clustered và secondary index; thứ tự trên đĩa quan trọng

Trong PostgreSQL, mọi chỉ mục là **secondary** (phụ): heap xếp dòng theo thứ tự **chèn**, chỉ mục trỏ vào bằng `ctid`. Ngược lại, **InnoDB** của MySQL (và SQL Server, Oracle IOT) dùng **clustered index**: bảng chính là một B+ tree theo khoá chính, lá chứa **cả dòng**. Chỉ mục phụ của InnoDB trỏ về dòng bằng **giá trị khoá chính** chứ không bằng địa chỉ vật lý, nên tìm qua chỉ mục phụ phải đi hai cây (cây phụ lấy khoá chính, cây chính lấy dòng).

Thứ tự trên đĩa quan trọng vì **truy vấn khoảng**. Nếu các dòng có khoá gần nhau cũng nằm gần nhau trên đĩa (khoá chính và `id` tăng dần trong heap), đọc 1% dòng chạm ít trang. Nếu chúng rải ngẫu nhiên, mỗi dòng nằm ở một trang khác. PostgreSQL ghi nhận điều này thành thống kê **correlation** (từ −1 đến 1) cho mỗi cột, planner dựa vào đó để ước lượng chi phí:

```sql
\pset null '∅'
\echo '== tương quan giữa thứ tự chỉ mục và thứ tự trên đĩa =='
CREATE INDEX t_rnd ON t (rnd);
ANALYZE t;
SELECT attname, round(correlation::numeric, 3) AS correlation
FROM pg_stats WHERE tablename = 't' AND attname IN ('id', 'rnd', 'created') ORDER BY attname;

\echo ''
\echo '== khoảng ~1% số dòng trên id (đã sắp trên đĩa) =='
SET enable_bitmapscan = off; SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON) SELECT count(token) FROM t WHERE id BETWEEN 500000 AND 509999;
\echo '== cùng độ rộng ~1% nhưng trên rnd (xáo ngẫu nhiên) cũng bằng index scan =='
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON) SELECT count(token) FROM t WHERE rnd BETWEEN 500000 AND 509999;
RESET enable_bitmapscan; RESET enable_seqscan;

\echo ''
\echo '== để planner tự chọn trên rnd: bitmap scan gom truy cập heap theo trang =='
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON) SELECT count(token) FROM t WHERE rnd BETWEEN 500000 AND 509999;

\echo ''
\echo '== CLUSTER sắp lại heap theo chỉ mục rnd (khoá bảng, tốn thời gian) =='
CLUSTER t USING t_rnd;
ANALYZE t;
SELECT attname, round(correlation::numeric, 3) AS correlation FROM pg_stats WHERE tablename = 't' AND attname IN ('id', 'rnd') ORDER BY attname;
SET enable_bitmapscan = off; SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON) SELECT count(token) FROM t WHERE rnd BETWEEN 500000 AND 509999;
RESET enable_bitmapscan; RESET enable_seqscan;
```

InnoDB cố định thứ tự đó là khoá chính, nên người ta thường chọn khoá chính tăng dần (chèn nối đuôi, ít tách trang) thay vì UUID ngẫu nhiên (chèn rải khắp cây, tách trang liên tục, như bảng "ngẫu nhiên" ở B+ tree tự cài phía trên).

## Composite index và quy tắc tiền tố trái

Chỉ mục có thể trên **nhiều cột**: `CREATE INDEX t_abc ON t (a, b, c)`. Các mục được sắp theo `a` trước, trong cùng `a` sắp theo `b`, trong cùng `(a, b)` sắp theo `c`, giống sắp từ điển theo chữ cái đầu rồi chữ thứ hai. Hệ quả là **quy tắc tiền tố trái** (leftmost prefix): chỉ mục chỉ thu hẹp miền tìm hiệu quả khi truy vấn có điều kiện trên **các cột đầu liên tục**.

```sql
\pset null '∅'
\echo '== composite index (a, b, c): quy tắc tiền tố trái =='
DROP INDEX IF EXISTS t_ab_cover, t_ab, t_abc;
CREATE INDEX t_abc ON t (a, b, c);
ANALYZE t;
\echo '-- lọc a: dùng được (tiền tố)'
EXPLAIN (COSTS OFF) SELECT count(*) FROM t WHERE a = 7;
\echo '-- lọc a và b: dùng được'
EXPLAIN (COSTS OFF) SELECT count(*) FROM t WHERE a = 7 AND b = 7;
\echo '-- lọc a, b, c: dùng được cả ba cột'
EXPLAIN (COSTS OFF) SELECT count(*) FROM t WHERE a = 7 AND b = 7 AND c = 3;
\echo '-- chỉ lọc b (bỏ qua tiền tố a): chỉ mục gần như vô dụng với planner'
EXPLAIN (COSTS OFF) SELECT * FROM t WHERE b = 7;
\echo '-- lọc a và c (nhảy qua b): chỉ cột a thu hẹp được miền tìm'
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY OFF) SELECT * FROM t WHERE a = 7 AND c = 3 AND b IS NOT NULL;
\echo '-- ORDER BY khớp thứ tự chỉ mục: không cần bước sắp xếp'
EXPLAIN (COSTS OFF) SELECT a, b, c FROM t WHERE a = 7 ORDER BY b, c LIMIT 5;
\echo '-- ORDER BY đảo thứ tự cột: phải sắp xếp thêm'
EXPLAIN (COSTS OFF) SELECT a, b, c FROM t WHERE a = 7 ORDER BY c, b LIMIT 5;
```

- **Chỉ lọc `b`** (bỏ qua `a`): các mục có `b = 7` rải khắp chỉ mục (cứ mỗi giá trị `a` lại có một đoạn), không có đoạn liên tục để nhảy tới, nên planner chọn quét tuần tự cả bảng.
- **Lọc `a` và `c`, bỏ `b`**: chỉ cột đầu thu hẹp được: phải đọc **mọi mục có `a = 7`** (20 trang chỉ mục, 20.000 mục) và lọc `c = 3` bên trong. Không tệ, nhưng chi phí tỉ lệ với số dòng `a = 7`, không phải số dòng thoả cả hai điều kiện.
- **Thứ tự `ORDER BY`**: truy vấn `WHERE a = 7 ORDER BY b, c LIMIT 5` khớp thứ tự chỉ mục nên chạy `Index Only Scan` rồi `Limit` ngay, **không có bước `Sort`**; còn `ORDER BY c, b` ngược thứ tự phải thêm `Sort` trên toàn bộ dòng `a = 7`.

Quy tắc đặt thứ tự cột: **cột dùng điều kiện bằng (`=`) đặt trước, cột dùng khoảng (`<`, `BETWEEN`) hoặc `ORDER BY` đặt sau**, vì sau cột khoảng các cột tiếp theo không còn thu hẹp được nữa. Trong số các cột `=`, ưu tiên cột lọc mạnh nhất và cột nhiều truy vấn dùng chung. Một chỉ mục `(a, b)` thay được chỉ mục `(a)` riêng, nên không cần giữ cả hai.

## Covering index và index-only scan

Mỗi lần tìm qua chỉ mục thường còn một bước về heap để lấy các cột không có trong chỉ mục. Nếu chỉ mục **chứa đủ mọi cột truy vấn cần**, PostgreSQL trả kết quả thẳng từ chỉ mục, không đụng heap: **index-only scan**. `INCLUDE` thêm cột vào lá của chỉ mục mà không dùng làm khoá sắp xếp:

```sql
\pset null '∅'
\echo '== covering index: chỉ mục chứa luôn cột cần lấy thì không phải về heap =='
DROP INDEX IF EXISTS t_a_cover, t_a_inc, t_abc;
CREATE INDEX t_ab ON t (a, b);
VACUUM ANALYZE t;
\echo '-- chỉ mục (a, b): tìm được dòng nhưng token nằm ở heap, mỗi dòng một lần về heap'
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON) SELECT token FROM t WHERE a = 7 AND b = 7;

DROP INDEX t_ab;
CREATE INDEX t_ab_cover ON t (a, b) INCLUDE (token);
VACUUM ANALYZE t;
\echo '-- chỉ mục (a, b) INCLUDE (token): Index Only Scan, Heap Fetches = 0'
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON) SELECT token FROM t WHERE a = 7 AND b = 7;
SELECT pg_size_pretty(pg_relation_size('t_ab_cover')) AS covering_index_size;

\echo ''
\echo '-- index-only scan phụ thuộc visibility map: sau khi ghi nhiều, Heap Fetches tăng cho tới khi VACUUM'
UPDATE t SET b = b WHERE a = 7 AND b = 7 AND id < 300000;
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY OFF) SELECT token FROM t WHERE a = 7 AND b = 7;
VACUUM t;
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY OFF) SELECT token FROM t WHERE a = 7 AND b = 7;
```

Truy vấn `SELECT token FROM t WHERE a = 7 AND b = 7` trả 10.000 dòng:

- Với chỉ mục `(a, b)`: **Bitmap Heap Scan**, đọc **6.882 trang heap**, mất **32,3 ms**: chỉ mục tìm ra `ctid` nhưng `token` nằm ở heap.

Ba điều kiện để index-only scan thật sự "không đụng heap": mọi cột nằm trong chỉ mục, chỉ mục hỗ trợ (B-tree có), và các trang heap phải **"tất cả đều nhìn thấy"** theo **visibility map** (bản đồ bit nói trang này không có dòng chết hay dòng chưa commit). Hai lần chạy cuối cho thấy điều đó: sau khi `UPDATE` hàng loạt, visibility map bị xoá bit cho các trang bị sửa, và lần chạy kế tiếp báo **`Heap Fetches: 7510`** (phải kiểm tra từng dòng ở heap, và đọc 2.823 trang); sau `VACUUM`, `Heap Fetches` về lại **0** và chỉ chạm 109 trang. Muốn index-only scan ổn định thì bảng phải được `VACUUM` thường xuyên (autovacuum làm việc này).

## Các kiểu chỉ mục khác

B-tree là mặc định, nhưng không phải lúc nào cũng đúng. PostgreSQL có nhiều kiểu, so trên bảng một triệu dòng khác:

```sql
\pset null '∅'
-- bảng t đã bị CLUSTER theo rnd ở bước trước; dựng lại một bảng sạch để so sánh kiểu chỉ mục
DROP TABLE IF EXISTS u;
CREATE TABLE u AS
SELECT g AS id, md5(g::text) AS token, timestamp '2026-01-01' + g * interval '1 second' AS created,
       ARRAY[g % 100, g % 1000, g % 10000] AS tags
FROM generate_series(1, 1000000) g;
ANALYZE u;
SELECT pg_size_pretty(pg_relation_size('u')) AS heap_size;

\echo '== kích thước các kiểu chỉ mục trên cùng bảng 1.000.000 dòng =='
CREATE INDEX u_token_btree ON u USING btree (token);
CREATE INDEX u_token_hash  ON u USING hash  (token);
CREATE INDEX u_created_btree ON u USING btree (created);
CREATE INDEX u_created_brin  ON u USING brin  (created);
CREATE INDEX u_tags_gin ON u USING gin (tags);
SELECT indexrelname AS index, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes WHERE relname = 'u' ORDER BY pg_relation_size(indexrelid) DESC;

\echo ''
\echo '== hash: chỉ hỗ trợ so sánh bằng. Bỏ B-tree trên token để thấy hash làm việc, rồi thử khoảng =='
DROP INDEX u_token_btree;
EXPLAIN (COSTS OFF) SELECT * FROM u WHERE token = '8f14e45fceea167a5a36dedd4bea2543';
EXPLAIN (COSTS OFF) SELECT * FROM u WHERE token > 'ff0' AND token < 'ff1';

\echo ''
\echo '== BRIN: chỉ nhớ min/max mỗi nhóm trang. Bỏ B-tree trên created để BRIN được dùng =='
DROP INDEX u_created_btree;
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON)
SELECT count(*) FROM u WHERE created BETWEEN '2026-01-05' AND '2026-01-05 00:10:00';
\echo '-- cùng truy vấn nhưng trên cột token (không theo thứ tự trên đĩa) BRIN không giúp được, planner quét cả bảng'
CREATE INDEX u_token_brin ON u USING brin (token);
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON) SELECT count(*) FROM u WHERE token BETWEEN '0000' AND '0001';

\echo ''
\echo '== GIN: chỉ mục ngược cho mảng, JSON, văn bản: tìm dòng chứa phần tử =='
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON)
SELECT count(*) FROM u WHERE tags @> ARRAY[9999];
```

| Kiểu | Hỗ trợ | Kích thước (1 triệu dòng) | Dùng khi |
|---|---|---|---|
| B-tree | `=`, khoảng, `ORDER BY`, tiền tố `LIKE` | 56 MB (chuỗi), 21 MB (timestamp) | mặc định cho hầu hết cột |

- **Hash** nhỏ hơn B-tree cùng cột (32 MB so với 56 MB) vì chỉ lưu mã băm, và tìm bằng `O(1)` bước. Nhưng với khoảng (`token > 'ff0' AND token < 'ff1'`), nó vô dụng: planner quét tuần tự cả bảng (xem plan thứ hai). Vì vậy B-tree thường thắng chỉ vì dùng được nhiều truy vấn hơn.
- **GIN** là chỉ mục **ngược**: với mỗi giá trị phần tử, lưu danh sách các dòng chứa nó (giống chỉ mục cuối sách). Tìm các dòng có `tags @> ARRAY[9999]` chạm chỉ 4 trang chỉ mục và đọc 100 dòng đúng (0,34 ms), điều mà B-tree thường không làm được cho cột mảng.
- **BRIN** (block range index) chỉ lưu **min và max** của mỗi nhóm trang liền nhau. Chỉ **24 KB** cho bảng 112 MB (B-tree cùng cột là 21 MB, hơn 800 lần). Tìm khoảng thời gian 10 phút trên cột `created` (tăng dần theo thứ tự chèn) chạm chỉ 136 trang (128 trang heap lossy cộng 8 trang chỉ mục) trong **0,77 ms**. Nhưng BRIN chỉ có tác dụng khi giá trị **tương quan với thứ tự vật lý**: với cột `token` (băm ngẫu nhiên), mỗi nhóm trang có đủ giá trị nhỏ lẫn lớn nên min/max không loại được gì, và planner bỏ BRIN, quét cả bảng (ở cuối output của BRIN).

## Cái giá khi ghi

Mỗi chỉ mục là một B-tree phải **cập nhật theo** mọi `INSERT`, `UPDATE` (nếu đổi cột được đánh chỉ mục hoặc dòng đổi chỗ) và `DELETE`. Thí nghiệm: nạp 300.000 dòng vào bảng có 0 tới 5 chỉ mục (mỗi cái trên một cột `md5` ngẫu nhiên, trường hợp tệ nhất cho B-tree vì chèn rải khắp cây):

```sql
\pset null '∅'
\echo '== chi phí GHI của chỉ mục: nạp 300.000 dòng ngẫu nhiên vào bảng có 0 đến 5 chỉ mục =='
DROP TABLE IF EXISTS w;
CREATE TABLE w (id int, c1 text, c2 text, c3 text, c4 text, c5 text);
CREATE TEMP TABLE results (n_indexes int, insert_ms numeric, table_mb numeric, indexes_mb numeric);

DO $$
DECLARE
  k int; t0 timestamp; ms numeric;
BEGIN
  FOR k IN 0..5 LOOP
    TRUNCATE w;
    DROP INDEX IF EXISTS w1, w2, w3, w4, w5;
    IF k >= 1 THEN CREATE INDEX w1 ON w (c1); END IF;
    IF k >= 2 THEN CREATE INDEX w2 ON w (c2); END IF;
    IF k >= 3 THEN CREATE INDEX w3 ON w (c3); END IF;
    IF k >= 4 THEN CREATE INDEX w4 ON w (c4); END IF;
    IF k >= 5 THEN CREATE INDEX w5 ON w (c5); END IF;
    t0 := clock_timestamp();
    INSERT INTO w SELECT g, md5(g::text || 'a'), md5(g::text || 'b'), md5(g::text || 'c'), md5(g::text || 'd'), md5(g::text || 'e')
      FROM generate_series(1, 300000) g;
    ms := extract(epoch FROM clock_timestamp() - t0) * 1000;
    INSERT INTO results SELECT k, round(ms), round(pg_relation_size('w') / 1048576.0, 1),
      round(coalesce((SELECT sum(pg_relation_size(indexrelid)) FROM pg_stat_user_indexes WHERE relname = 'w'), 0) / 1048576.0, 1);
  END LOOP;
END $$;

SELECT n_indexes AS indexes, insert_ms AS "insert (ms)",
       round(insert_ms / (SELECT insert_ms FROM results WHERE n_indexes = 0), 2) AS "so với không chỉ mục",
       table_mb AS "bảng (MB)", indexes_mb AS "các chỉ mục (MB)"
FROM results ORDER BY n_indexes;
```

Mỗi chỉ mục thêm làm thời gian nạp tăng thêm khoảng **0,7 lần** thời gian không chỉ mục: 1,71 lần với một chỉ mục, **4,85 lần** với năm chỉ mục (1.078 ms lên 5.224 ms). Đồng thời kích thước tăng: bảng 58,6 MB, nhưng năm chỉ mục chiếm **108,6 MB**, gần gấp đôi bản thân dữ liệu. Phần chi phí này còn bị nhân lên ở `UPDATE`: PostgreSQL dùng MVCC nên mỗi `UPDATE` tạo một phiên bản dòng mới ở vị trí mới, và nếu không dùng được tối ưu HOT (dòng mới nằm cùng trang và không đổi cột có chỉ mục) thì **mọi** chỉ mục phải thêm một mục mới, không chỉ chỉ mục của cột bị đổi (chi tiết ở bài [Transactions](/docs/databases/transactions)).

Nguyên tắc: **mỗi chỉ mục phải đánh đổi được bằng truy vấn đọc nó giúp**. Chỉ mục không bao giờ được dùng là phí thuần tuý; `pg_stat_user_indexes.idx_scan = 0` sau một thời gian dài là dấu hiệu để xoá.

## Khi nào planner bỏ qua chỉ mục

Có chỉ mục không có nghĩa nó được dùng. Sáu trường hợp thường gặp, trên bảng 500.000 dòng với đủ chỉ mục cần thiết:

```sql
\pset null '∅'
\echo '== khi nào planner KHÔNG dùng chỉ mục (dù chỉ mục tồn tại) =='
DROP TABLE IF EXISTS g;
CREATE TABLE g AS
SELECT i AS id, (i % 2) AS half, (i % 1000) AS thousandth, 'User' || (i % 5000) AS name, i::text AS id_text
FROM generate_series(1, 500000) i;
CREATE INDEX g_half ON g (half); CREATE INDEX g_th ON g (thousandth); CREATE INDEX g_name ON g (name); CREATE INDEX g_idtext ON g (id_text text_pattern_ops);
CREATE INDEX g_id ON g (id);
ANALYZE g;

\echo '-- 1. lấy 90% số dòng: đọc tuần tự cả bảng rẻ hơn nhảy qua chỉ mục (dù chỉ mục có sẵn)'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE thousandth < 900;
\echo '-- lấy 0,5% số dòng: chỉ mục thắng'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE thousandth < 5;

\echo ''
\echo '-- 2. bọc cột trong hàm: chỉ mục trên name không dùng được cho lower(name)'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE lower(name) = 'user42';
CREATE INDEX g_lower_name ON g (lower(name));
ANALYZE g;
\echo '-- sau khi tạo chỉ mục trên biểu thức lower(name):'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE lower(name) = 'user42';

\echo ''
\echo '-- 3. tính toán trên cột ở vế trái: id + 1 = 100 không dùng được chỉ mục id'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE id + 1 = 100;
\echo '-- viết lại để cột đứng một mình:'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE id = 99;

\echo ''
\echo '-- 4. LIKE: tiền tố dùng được (với text_pattern_ops), hậu tố hay chứa thì không'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE id_text LIKE '4999%';
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE id_text LIKE '%999';

\echo ''
\echo '-- 5. ép kiểu cột: so sánh trực tiếp dùng chỉ mục, còn id_text::int thì không'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE id_text = '500';
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE id_text::int = 500;

\echo ''
\echo '-- 6. OR trên hai cột đều có chỉ mục: BitmapOr gộp hai chỉ mục; ORDER BY khớp chỉ mục id kèm LIMIT không cần sắp xếp'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE thousandth = 7 OR id = 500;
EXPLAIN (COSTS OFF) SELECT * FROM g ORDER BY id LIMIT 3;
```

1. **Độ chọn lọc thấp**: lấy 90% số dòng thì đọc tuần tự cả bảng rẻ hơn nhảy qua chỉ mục (mỗi dòng một lần đọc ngẫu nhiên); lấy 0,5% thì chỉ mục thắng. Ngưỡng chuyển tuỳ phần cứng và thống kê, thường vài phần trăm tới vài chục phần trăm.
2. **Bọc cột trong hàm**: `lower(name) = 'user42'` không dùng được chỉ mục trên `name`, vì chỉ mục sắp theo giá trị gốc chứ không theo `lower` của nó. Giải: tạo **chỉ mục trên biểu thức** `lower(name)`, và truy vấn sau đó dùng được.
3. **Tính toán trên cột**: `id + 1 = 100` không dùng được chỉ mục `id`; viết lại để cột đứng một mình (`id = 99`).
4. **`LIKE`**: tiền tố (`'4999%'`) chuyển được thành khoảng nên dùng chỉ mục (với toán tử `text_pattern_ops`, hoặc collation `C`); hậu tố hay chứa (`'%999'`) thì không, cần chỉ mục `pg_trgm` kiểu GIN.
5. **Ép kiểu cột**: `id_text = '500'` dùng được chỉ mục, còn `id_text::int = 500` thì không (cột bị bọc trong phép ép kiểu).
6. **Hai trường hợp planner vẫn dùng được chỉ mục**: `OR` trên hai cột đều có chỉ mục dùng **BitmapOr** (gộp hai chỉ mục), và `ORDER BY id LIMIT 3` chạy ngay trên chỉ mục `id` không sắp xếp.

Trong cả sáu trường hợp, `EXPLAIN` cho biết lý do ngay lập tức. Ngoài ra còn hai nguyên nhân thường gặp mà không có trong script: **thống kê cũ** làm planner ước lượng sai số dòng (chạy `ANALYZE`), và **bảng quá nhỏ** (vài trăm dòng) nên quét tuần tự rẻ hơn mọi chỉ mục.

## Trong hệ thống thật

- **PostgreSQL** là heap cộng B-tree secondary mặc định; **InnoDB** là clustered B+ tree theo khoá chính (trang 16 KB), chỉ mục phụ chứa khoá chính; **SQLite** lưu bảng như B-tree theo `rowid`. Cơ sở dữ liệu kiểu **LSM-tree** (RocksDB, Cassandra, LevelDB) đánh đổi ngược lại: ghi tuần tự nhanh hơn B-tree rất nhiều, đọc phải kiểm tra nhiều tầng; chọn B-tree hay LSM là quyết định cốt lõi của một storage engine.
- **Chèn khoá ngẫu nhiên** (UUID v4) vào chỉ mục lớn gây tách trang liên tục và làm chỉ mục phình, ép nhiều trang vào bộ nhớ đệm; khoá tăng theo thời gian (UUID v7, `bigserial`, ULID) chèn nối đuôi vào lá phải nhất và tránh được điều đó.
- **Chỉ mục bị phình (bloat)** theo thời gian vì xoá và cập nhật; `REINDEX` (hoặc `REINDEX CONCURRENTLY`) dựng lại; `CREATE INDEX CONCURRENTLY` tạo mà không khoá ghi, đổi lại chậm hơn và có thể thất bại để lại chỉ mục "invalid".
- **Chỉ mục có điều kiện** (`CREATE INDEX ... WHERE active`) chỉ đánh dấu một tập con dòng, nhỏ và nhanh hơn khi truy vấn luôn lọc điều kiện đó.

## Quan sát và chẩn đoán

- `EXPLAIN (ANALYZE, BUFFERS)`: nhìn kiểu quét (`Seq Scan`, `Index Scan`, `Bitmap`, `Index Only Scan`), `Buffers` (số trang), `Rows Removed by Filter` (công việc bỏ phí), `Heap Fetches` (index-only scan có thật sự không đụng heap).
- `\di+` (psql) liệt kê chỉ mục và kích thước; `pg_stat_user_indexes` cho `idx_scan` (số lần dùng) để tìm chỉ mục thừa.
- `pg_stats.correlation` cho biết thứ tự vật lý khớp thứ tự chỉ mục tới đâu; `pageinspect` (`bt_metap`, `bt_page_stats`) cho chiều cao và độ đầy.
- Chỉ mục mới nên được thử trên bản sao dữ liệu thật: planner chọn dựa trên thống kê, và kết quả trên bảng nhỏ không phản ánh bảng lớn.

| Triệu chứng | Nguyên nhân hay gặp | Cách xử lý |
|---|---|---|
| Truy vấn dùng `Seq Scan` dù đã có chỉ mục | độ chọn lọc thấp; cột bị bọc hàm hoặc phép tính; thống kê cũ | `EXPLAIN`, viết lại điều kiện, `ANALYZE`, chỉ mục biểu thức |
| Chỉ mục composite không giúp | điều kiện bỏ qua cột đầu | đổi thứ tự cột hoặc tạo chỉ mục khác |
| Ghi chậm dần khi thêm chỉ mục | mỗi chỉ mục tốn thêm mỗi lần ghi | bỏ chỉ mục không dùng (`idx_scan = 0`), gộp bằng composite |
| Index-only scan vẫn có `Heap Fetches` lớn | visibility map chưa cập nhật | `VACUUM`, kiểm tra autovacuum |
| Chỉ mục lớn gấp nhiều lần dữ liệu | khoá dài, hoặc phình sau nhiều lần cập nhật | khoá ngắn hơn, `REINDEX` |
| Truy vấn khoảng chậm dù có chỉ mục | correlation thấp, mỗi dòng một trang | `CLUSTER`, chỉ mục covering, hoặc BRIN nếu dữ liệu theo thứ tự |
| Chèn hàng loạt vào bảng chậm | nhiều chỉ mục cập nhật từng dòng | xoá chỉ mục, nạp dữ liệu, tạo lại chỉ mục |

## Lưu ý

- Chỉ mục là một cấu trúc **phụ** chứa khoá cộng địa chỉ dòng; nó đổi **tốc độ đọc** lấy **tốc độ ghi và chỗ chứa**. Mỗi chỉ mục phải có truy vấn thực sự dùng nó.
- B+ tree rất thấp (3 tầng cho một triệu đến vài chục triệu dòng) vì mỗi nút là một trang chứa hàng trăm khoá. Khoá càng ngắn, cây càng thấp và chỉ mục càng nhỏ.
- Tìm khoảng và `ORDER BY` là sức mạnh của B+ tree nhờ các lá được nối theo thứ tự; hash index và bảng băm không làm được.
- Với truy vấn khoảng, thứ tự vật lý của heap (correlation) quyết định số trang phải đọc: cùng 1% dòng có thể là 155 trang hay 10.213 trang.
- Composite index theo quy tắc tiền tố trái: điều kiện `=` trước, khoảng và `ORDER BY` sau; bỏ qua cột đầu thì chỉ mục gần như vô dụng.
- Covering index (`INCLUDE`) tránh về heap nhưng cần visibility map sạch (`VACUUM`) và làm chỉ mục lớn hơn.
- Bọc cột trong hàm, phép tính, hay ép kiểu làm chỉ mục thường không dùng được; viết lại để cột đứng một mình, hoặc tạo chỉ mục trên biểu thức.
- Planner bỏ chỉ mục khi nó rẻ hơn thật (độ chọn lọc thấp, bảng nhỏ) chứ không phải lúc nào cũng "sai"; kiểm tra bằng `EXPLAIN ANALYZE` trên dữ liệu thật trước khi ép bằng `SET enable_seqscan = off` (chỉ dùng để thử, không dùng ở production).
- UUID ngẫu nhiên làm khoá chính hoặc khoá chỉ mục lớn gây tách trang và phình chỉ mục; khoá tăng dần tránh được.

**Cách đọc bài:** mỗi mục có một câu **Đoán trước** và kết bằng một câu **Thử ngay**. Hãy tự trả lời trong đầu (hoặc ra giấy) rồi mới xem đáp án. Việc tự nhớ lại và tự đoán giúp nhớ lâu hơn nhiều so với chỉ đọc.

## Ý chính

Không có gợi ý gì, muốn tìm một dòng trong bảng một triệu dòng thì cơ sở dữ liệu phải đọc **cả bảng** (`O(n)`). Một <Term>index</Term> là cấu trúc phụ nằm cạnh bảng, thường là một <Term>B-tree</Term>, giúp đi thẳng tới dòng cần tìm chỉ sau vài lần đọc (`O(log n)`). Trong bài này, con số đó là 4 trang thay vì 10.368 trang.

Index không miễn phí. Nó **tăng tốc đọc, nhưng làm chậm mọi lần ghi và tốn chỗ**, và chỉ giúp được những truy vấn có dạng hợp với nó. Vì vậy hiểu index là hiểu ba câu hỏi: nó tìm nhanh nhờ đâu, truy vấn nào dùng được nó, và nó tốn gì.

## Không có index: phải đọc cả bảng

Bảng trong PostgreSQL là một dãy **trang** (page) 8 KB, mỗi trang chứa nhiều dòng. Đĩa và bộ nhớ đệm đọc ghi theo trang, không theo dòng, nên **số trang phải đọc** là thước đo chi phí chính của một truy vấn. Dựng một bảng một triệu dòng để thử:

```sql
\pset null '∅'
CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT setseed(0.42) AS seed \gset
DROP TABLE IF EXISTS t;
-- 1.000.000 dòng: id tăng dần, rnd ngẫu nhiên, token = md5(id), a, b, c là các cột nhỏ
CREATE TABLE t AS
SELECT g                         AS id,
       (random() * 1000000)::int AS rnd,
       md5(g::text)              AS token,
       g % 50 AS a, g % 20 AS b, g % 7 AS c
FROM generate_series(1, 1000000) g;
VACUUM ANALYZE t;

SELECT pg_size_pretty(pg_relation_size('t')) AS table_size,
       pg_relation_size('t') / 8192          AS pages,
       round(1000000.0 / (pg_relation_size('t') / 8192), 1) AS rows_per_page;
SELECT ctid, id FROM t WHERE id IN (1, 2, 3, 999999) ORDER BY id;
```

```text

------------+-------+---------------

(1 row)

    ctid    |   id   
------------+--------
 (0,1)      |      1
 (0,2)      |      2
 (0,3)      |      3
 (10309,26) | 999999
(4 rows)
```

Bảng chiếm **10.368 trang**, mỗi trang khoảng 96 dòng. Mỗi dòng có địa chỉ `ctid` = (số trang, vị trí trong trang): dòng 1 ở trang 0, dòng 999.999 ở trang 10.309.

**Đoán trước:** tìm đúng một dòng theo `token`, khi chưa có index thì phải đọc bao nhiêu trang? Sau khi tạo index thì sao?

```sql
\echo '== chưa có index =='
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON)
SELECT * FROM t WHERE token = '8f14e45fceea167a5a36dedd4bea2543';

\echo '== tạo B-tree index trên token, rồi tìm lại =='
CREATE INDEX t_token_idx ON t (token);
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON)
SELECT * FROM t WHERE token = '8f14e45fceea167a5a36dedd4bea2543';
```

Đọc dòng `Buffers` (số trang đã chạm tới):

Không có index, cơ sở dữ liệu đọc mọi trang rồi loại bỏ 999.999 dòng không khớp (`Rows Removed by Filter`). Có index, nó đi xuống cây 3 trang để lấy `ctid` của dòng cần tìm, rồi đọc đúng 1 trang của bảng. Index **không chứa dòng**, chỉ chứa khoá kèm địa chỉ `ctid` trỏ về bảng.

## Vì sao index chỉ cần vài trang: B+ tree

Index mặc định là một **B+ tree**, họ hàng của cây nhị phân tìm kiếm ở bài [Tree](/docs/dsa/trees) với hai khác biệt quyết định:

1. **Mỗi nút là một trang 8 KB**, chứa **hàng trăm khoá** chứ không phải 1 khoá. Nút có nhiều nhánh con thì cây rất thấp.
2. Khoá và địa chỉ dòng chỉ nằm ở **lá**, và các lá được **nối với nhau theo thứ tự**. Tìm một khoảng (`BETWEEN`, `ORDER BY`) chỉ cần xuống tới lá đầu tiên rồi đi ngang.

```text
                     [ gốc: vài khoá dẫn đường ]
                    /            |             \
      [ nút trong ]        [ nút trong ]   ...   [ nút trong ]
       /    |    \           /    |    \
   [lá] → [lá] → [lá] → [lá] → [lá] → [lá] → ...   (mỗi lá: hàng trăm khoá + ctid)
```

PostgreSQL cho xem cấu trúc thật của index bằng extension `pageinspect`:

```sql
ALTER TABLE t ADD PRIMARY KEY (id);   -- khoá chính tự tạo index t_pkey trên id
SELECT c.relname AS index,
       pg_size_pretty(pg_relation_size(c.oid))              AS size,
       (SELECT level FROM bt_metap(c.relname)) + 1          AS levels,
       (SELECT live_items FROM bt_page_stats(c.relname, 1)) AS keys_per_leaf
FROM pg_class c WHERE c.relname IN ('t_pkey', 't_token_idx') ORDER BY c.relname;
```

```text
    index    | size  | levels | keys_per_leaf 
-------------+-------+--------+---------------
 t_pkey      | 21 MB |      3 |           367
 t_token_idx | 56 MB |      3 |           141
(2 rows)
```

Cả hai index đều chỉ có **3 tầng**. Một lá của `t_pkey` chứa **367** khoá (`id` là số nguyên 4 byte), còn một lá của `t_token_idx` chỉ chứa **141** khoá vì mỗi `token` dài 32 ký tự. Từ số khoá mỗi trang, ta tính được chiều cao cây. Ba ví dụ dưới đi từ giải sẵn tới tự làm.

### Ví dụ 1 (giải sẵn): index trên `id`

1. 1.000.000 khoá, mỗi lá 367 khoá, nên cần `⌈1.000.000 / 367⌉ = 2.725` lá.
2. Mỗi nút ở tầng trên trỏ được tới khoảng 367 nút con (đơn giản hoá: coi nút trong chứa cùng số khoá như lá). 2.725 lá cần `⌈2.725 / 367⌉ = 8` nút.
3. 8 nút vừa một nút gốc.
4. Tổng: lá, một tầng giữa, gốc = **3 tầng**, khớp với `levels = 3` ở trên.

Viết thành code để kiểm lại:

```python
import math

def height(n_rows, per_page):
    """Số tầng của B+ tree khi mỗi trang chứa per_page khoá (đơn giản hoá: nút trong cũng vậy)."""
    nodes = math.ceil(n_rows / per_page)          # tầng lá
    levels = 1
    print(f"  lá: {nodes:,} trang")
    while nodes > 1:
        nodes = math.ceil(nodes / per_page)       # mỗi nút tầng trên trỏ tới per_page nút tầng dưới
        levels += 1
        print(f"  tầng {levels}: {nodes:,} trang")
    return levels

print("=>", height(1_000_000, 367), "tầng")
```

```text
  lá: 2,725 trang
  tầng 2: 8 trang
  tầng 3: 1 trang
=> 3 tầng
```

## Composite index và quy tắc tiền tố trái

Index có thể gồm **nhiều cột**: `CREATE INDEX t_abc ON t (a, b, c)`. Các mục được sắp theo `a` trước, cùng `a` thì theo `b`, cùng `(a, b)` thì theo `c`. Giống danh bạ điện thoại sắp theo **họ** rồi tới **tên**: tìm "họ Nguyễn" hay "Nguyễn Văn An" rất nhanh, nhưng tìm mọi người **tên An** thì phải lật cả cuốn, vì những người tên An nằm rải rác ở mọi họ.

**Đoán trước:** với index `(a, b, c)`, ba truy vấn `WHERE a = 7`, `WHERE a = 7 AND b = 7`, `WHERE b = 7`, cái nào dùng được index?

```sql
CREATE INDEX t_abc ON t (a, b, c);
VACUUM ANALYZE t;
\echo '-- 1. WHERE a = 7'
EXPLAIN (COSTS OFF) SELECT * FROM t WHERE a = 7;
\echo '-- 2. WHERE a = 7 AND b = 7'
EXPLAIN (COSTS OFF) SELECT * FROM t WHERE a = 7 AND b = 7;
\echo '-- 3. WHERE b = 7 (bỏ qua cột đầu a)'
EXPLAIN (COSTS OFF) SELECT * FROM t WHERE b = 7;
\echo '-- 4. WHERE a = 7 ORDER BY b, c (cùng thứ tự với index)'
EXPLAIN (COSTS OFF) SELECT a, b, c FROM t WHERE a = 7 ORDER BY b, c LIMIT 5;
\echo '-- 5. WHERE a = 7 ORDER BY c, b (đảo thứ tự)'
EXPLAIN (COSTS OFF) SELECT a, b, c FROM t WHERE a = 7 ORDER BY c, b LIMIT 5;
```

```text
-- 1. WHERE a = 7
            QUERY PLAN            
----------------------------------
 Bitmap Heap Scan on t
   Recheck Cond: (a = 7)
   ->  Bitmap Index Scan on t_abc
         Index Cond: (a = 7)
(4 rows)

-- 2. WHERE a = 7 AND b = 7
                QUERY PLAN                 
-------------------------------------------
 Bitmap Heap Scan on t
   Recheck Cond: ((a = 7) AND (b = 7))
   ->  Bitmap Index Scan on t_abc
         Index Cond: ((a = 7) AND (b = 7))
(4 rows)

-- 3. WHERE b = 7 (bỏ qua cột đầu a)
          QUERY PLAN          
------------------------------
 Gather
   Workers Planned: 2
   ->  Parallel Seq Scan on t
         Filter: (b = 7)
(4 rows)

-- 4. WHERE a = 7 ORDER BY b, c (cùng thứ tự với index)
               QUERY PLAN               
----------------------------------------
 Limit
   ->  Index Only Scan using t_abc on t
         Index Cond: (a = 7)
(3 rows)

-- 5. WHERE a = 7 ORDER BY c, b (đảo thứ tự)
                  QUERY PLAN                  
----------------------------------------------
 Limit
   ->  Sort
         Sort Key: c, b
         ->  Index Only Scan using t_abc on t
               Index Cond: (a = 7)
(5 rows)
```

- Truy vấn 1 và 2 lọc trên **các cột đầu liên tục** (`a`, rồi `a, b`), nên điều kiện nằm trong `Index Cond`: index thu hẹp được miền tìm.
- Truy vấn 3 bỏ qua `a`. Các mục có `b = 7` rải khắp index, nên planner quét cả bảng (`Seq Scan`).
- Truy vấn 4 cần thứ tự `b, c` trong cùng `a`, đúng thứ tự index đã sắp sẵn: không có bước `Sort`. Truy vấn 5 đảo thành `c, b` thì phải sắp xếp thêm.

Đó là **quy tắc tiền tố trái** (leftmost prefix): index nhiều cột chỉ dùng được hiệu quả khi điều kiện bắt đầu từ cột đầu tiên và không nhảy cóc. Từ đó có quy tắc đặt thứ tự cột: **cột so sánh bằng (`=`) đặt trước, cột tìm khoảng (`>`, `BETWEEN`) hoặc `ORDER BY` đặt sau.** Một index `(a, b)` cũng thay được index `(a)`, nên không cần giữ cả hai.

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ index `(a, b, c)` giúp mọi truy vấn có nhắc tới `a`, `b` hoặc `c`. Thật ra nó chỉ giúp truy vấn lọc theo **tiền tố** `a`, `a, b` hoặc `a, b, c`, vì các mục chỉ được sắp theo thứ tự đó.

**Thử ngay:** bảng `orders` có index `(user_id, created_at)`. Truy vấn nào dùng được index tốt: (1) `WHERE user_id = 42 ORDER BY created_at DESC LIMIT 10`; (2) `WHERE created_at > '2026-01-01'`?

<Expand title="Đáp án">

(1) dùng được rất tốt: lọc `user_id` là cột đầu, các đơn của user 42 đã nằm liền nhau và sắp sẵn theo `created_at`. Chỉ cần đọc 10 mục cuối, không phải sắp xếp. (2) không dùng hiệu quả: `created_at` là cột thứ hai, các đơn sau ngày 1/1 nằm rải rác trong mọi `user_id`. Muốn truy vấn (2) nhanh thì cần thêm một index bắt đầu bằng `created_at`.

</Expand>

## Covering index: không cần quay về bảng

Mỗi lần tìm qua index thường còn một bước về bảng để lấy các cột không có trong index. Nếu kết quả có nhiều dòng nằm rải rác, bước này rất đắt: mỗi dòng có thể nằm ở một trang khác.

**Đoán trước:** truy vấn `SELECT token FROM t WHERE a = 7 AND b = 7` trả về 10.000 dòng. Với index `(a, b)`, nó phải đọc khoảng bao nhiêu trang?

```sql
DROP INDEX t_abc;
CREATE INDEX t_ab ON t (a, b);
VACUUM ANALYZE t;
\echo '== index (a, b): token nằm ở bảng =='
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON)
SELECT token FROM t WHERE a = 7 AND b = 7;

DROP INDEX t_ab;
CREATE INDEX t_ab_cover ON t (a, b) INCLUDE (token);
VACUUM ANALYZE t;
\echo '== index (a, b) INCLUDE (token): token nằm sẵn trong index =='
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON)
SELECT token FROM t WHERE a = 7 AND b = 7;
SELECT pg_size_pretty(pg_relation_size('t_ab_cover')) AS covering_index_size;
```

```text
== index (a, b): token nằm ở bảng ==
                         QUERY PLAN                          
-------------------------------------------------------------
 Bitmap Heap Scan on t (actual rows=10000 loops=1)
   Recheck Cond: ((a = 7) AND (b = 7))
   Heap Blocks: exact=10000
   Buffers: shared hit=2489 read=7522
   ->  Bitmap Index Scan on t_ab (actual rows=10000 loops=1)
         Index Cond: ((a = 7) AND (b = 7))
         Buffers: shared read=11
 Planning:
   Buffers: shared hit=21
 Planning Time: 0.135 ms
 Execution Time: 39.117 ms
(11 rows)

== index (a, b) INCLUDE (token): token nằm sẵn trong index ==
                            QUERY PLAN                             
-------------------------------------------------------------------
 Index Only Scan using t_ab_cover on t (actual rows=10000 loops=1)
   Index Cond: ((a = 7) AND (b = 7))
   Heap Fetches: 0
   Buffers: shared hit=1 read=85
 Planning:
   Buffers: shared hit=14
 Planning Time: 0.079 ms
 Execution Time: 1.046 ms
(8 rows)

 covering_index_size 
---------------------
 64 MB
(1 row)
```

| Index | Kiểu quét | Số trang | Thời gian |
|---|---|---|---|
| `(a, b)` | `Bitmap Heap Scan` | 10.011 (11 trang index + **10.000 trang bảng**) | 39,1 ms |
| `(a, b) INCLUDE (token)` | `Index Only Scan`, `Heap Fetches: 0` | **86** | 1,0 ms |

Với index `(a, b)`, tìm ra 10.000 `ctid` rất nhanh (11 trang), nhưng 10.000 dòng đó nằm ở **10.000 trang khác nhau** của bảng. `INCLUDE (token)` cất thêm `token` vào lá của index, nên kết quả lấy thẳng từ index, không đụng bảng: **index-only scan**, ít trang hơn khoảng 116 lần. Cái giá: index to hơn (64 MB).

Một index như vậy, chứa đủ mọi cột truy vấn cần, gọi là **covering index**.

**Thử ngay:** truy vấn trên đổi thành `SELECT token, rnd FROM t WHERE a = 7 AND b = 7`. Index `t_ab_cover` còn cho index-only scan không?

<Expand title="Đáp án">

Không. `rnd` không có trong index, nên với mỗi dòng vẫn phải về bảng lấy `rnd`, quay lại kiểu đọc 10.000 trang. Covering index chỉ có lợi cho đúng những truy vấn mà nó chứa đủ cột.

</Expand>

## Thứ tự trên đĩa: clustered và secondary index

Truy vấn khoảng (`BETWEEN`) trả nhiều dòng. Số trang phải đọc phụ thuộc vào việc các dòng đó **nằm gần nhau trên đĩa** hay rải rác. PostgreSQL đo điều này bằng thống kê **correlation** của mỗi cột: 1 là thứ tự trong bảng khớp hoàn toàn với thứ tự giá trị, 0 là không liên quan.

**Đoán trước:** lấy khoảng 10.000 dòng theo `id` (chèn tăng dần) và 10.000 dòng theo `rnd` (ngẫu nhiên), cả hai đều qua index. Số trang chênh nhau bao nhiêu lần?

```sql
CREATE INDEX t_rnd ON t (rnd);
ANALYZE t;
SELECT attname, round(correlation::numeric, 3) AS correlation
FROM pg_stats WHERE tablename = 't' AND attname IN ('id', 'rnd') ORDER BY attname;

SET enable_bitmapscan = off; SET enable_seqscan = off;   -- ép dùng Index Scan để so cho công bằng
\echo '== 10.000 dòng liền nhau theo id =='
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON)
SELECT count(token) FROM t WHERE id BETWEEN 500000 AND 509999;
\echo '== khoảng 10.000 dòng theo rnd =='
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON)
SELECT count(token) FROM t WHERE rnd BETWEEN 500000 AND 509999;
RESET enable_bitmapscan; RESET enable_seqscan;
```

Đây là lý do có hai kiểu tổ chức:

| | Secondary index (PostgreSQL mặc định) | Clustered index (MySQL InnoDB, SQL Server) |
|---|---|---|
| Bảng lưu ở đâu | heap riêng, dòng theo thứ tự chèn | chính là B+ tree theo khoá chính, lá chứa cả dòng |
| Index trỏ về dòng bằng | địa chỉ vật lý `ctid` | giá trị khoá chính |
| Truy vấn khoảng theo khoá chính | nhanh nếu chèn theo thứ tự khoá | luôn nhanh: dữ liệu sắp theo khoá |
| Mỗi bảng có | nhiều index, không cái nào quyết định thứ tự | đúng một clustered index |

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ PostgreSQL có clustered index như MySQL. Thật ra lệnh `CLUSTER` của PostgreSQL chỉ **sắp lại bảng một lần**; dữ liệu ghi sau đó không tự giữ thứ tự (xem phần Đi sâu hơn).

**Thử ngay:** trong InnoDB, vì sao người ta khuyên dùng khoá chính tăng dần (số tự tăng) thay vì UUID ngẫu nhiên?

<Expand title="Đáp án">

Vì bảng InnoDB **chính là** B+ tree theo khoá chính. Khoá tăng dần thì dòng mới luôn chèn vào lá cuối cùng, các lá được ghi đầy và tuần tự. UUID ngẫu nhiên làm dòng mới rơi vào lá bất kỳ, liên tục phải tách lá, lá chỉ đầy khoảng một nửa tới hai phần ba, index phình to và tốn bộ nhớ đệm. Phần Đi sâu hơn có mô phỏng độ đầy lá theo thứ tự chèn.

</Expand>

## Cái giá khi ghi

Mỗi index là một B+ tree phải **cập nhật theo** mọi `INSERT`, `DELETE`, và mọi `UPDATE` làm đổi cột của index hoặc đổi chỗ dòng.

**Đoán trước:** nạp 300.000 dòng vào bảng có 5 index thì lượng ghi gấp bao nhiêu lần bảng không có index?

```sql
CREATE TEMP TABLE results (n_indexes int, wal_mb numeric, table_mb numeric, indexes_mb numeric);

-- k = số index trên bảng. Mỗi lần nạp 300.000 dòng vào một bảng mới có k index,
-- rồi đo lượng WAL (nhật ký ghi, xem bài Transactions) sinh ra: thước đo lượng việc ghi,
-- ổn định hơn đo thời gian.
DO $$
DECLARE
  k int; lsn0 pg_lsn;
BEGIN
  FOR k IN 0..5 LOOP
    DROP TABLE IF EXISTS w;
    CREATE TABLE w (id int, c1 text, c2 text, c3 text, c4 text, c5 text);
    IF k >= 1 THEN CREATE INDEX w1 ON w (c1); END IF;
    IF k >= 2 THEN CREATE INDEX w2 ON w (c2); END IF;
    IF k >= 3 THEN CREATE INDEX w3 ON w (c3); END IF;
    IF k >= 4 THEN CREATE INDEX w4 ON w (c4); END IF;
    IF k >= 5 THEN CREATE INDEX w5 ON w (c5); END IF;
    lsn0 := pg_current_wal_insert_lsn();
    INSERT INTO w SELECT g, md5(g || 'a'), md5(g || 'b'), md5(g || 'c'), md5(g || 'd'), md5(g || 'e')
      FROM generate_series(1, 300000) g;
    INSERT INTO results SELECT k,
      round(pg_wal_lsn_diff(pg_current_wal_insert_lsn(), lsn0) / 1048576.0, 1),
      round(pg_relation_size('w') / 1048576.0, 1),
      round(coalesce((SELECT sum(pg_relation_size(indexrelid)) FROM pg_stat_user_indexes WHERE relname = 'w'), 0) / 1048576.0, 1);
  END LOOP;
END $$;

SELECT n_indexes AS indexes, wal_mb AS "WAL ghi ra (MB)",
       round(wal_mb / (SELECT wal_mb FROM results WHERE n_indexes = 0), 2) AS "so với 0 index",
       table_mb AS "bảng (MB)", indexes_mb AS "các index (MB)"
FROM results ORDER BY n_indexes;
```

```text

---------+-----------------+----------------+-----------+----------------
       0 |            64.3 |           1.00 |      58.6 |            0.0
       1 |           102.3 |           1.59 |      58.6 |           21.9
       2 |           140.3 |           2.18 |      58.6 |           43.6
       3 |           178.4 |           2.77 |      58.6 |           65.5
       4 |           225.3 |           3.50 |      58.6 |           87.1
       5 |           254.4 |           3.96 |      58.6 |          108.6
(6 rows)
```

Mỗi index thêm khoảng **38 MB** vào lượng ghi. Với 5 index, cùng 300.000 dòng phải ghi **gần gấp 4 lần**, và 5 index chiếm 108,6 MB, **gần gấp đôi** chính dữ liệu (58,6 MB). Index ở đây đặt trên cột `md5` ngẫu nhiên, trường hợp tệ cho B-tree vì mỗi dòng chèn vào một lá bất kỳ.

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ thêm index "cho chắc" thì không mất gì. Thật ra mỗi index làm chậm mọi lần ghi và tốn bộ nhớ đệm, kể cả khi không truy vấn nào dùng tới nó. Mỗi index phải có truy vấn thật sự cần nó. Trong PostgreSQL, `pg_stat_user_indexes.idx_scan = 0` sau một thời gian dài là dấu hiệu index thừa.

**Thử ngay:** cần nạp 50 triệu dòng vào một bảng đang có 6 index, và không ai đọc bảng trong lúc nạp. Làm sao cho nhanh hơn?

<Expand title="Đáp án">

Xoá các index (trừ cái cần cho ràng buộc, nếu phải giữ), nạp dữ liệu, rồi tạo lại index. Tạo index một lần trên dữ liệu có sẵn nhanh hơn nhiều so với cập nhật cây cho từng dòng: PostgreSQL sắp xếp toàn bộ khoá rồi dựng cây từ dưới lên, các lá được ghi đầy và tuần tự.

</Expand>

## Khi nào có index mà không được dùng

<Term>Query planner</Term> ước lượng chi phí từng cách chạy rồi chọn cách rẻ nhất. Có index không có nghĩa là nó được dùng. Bảng dưới có 500.000 dòng, đủ index trên các cột được lọc.

**Đoán trước:** trong năm trường hợp dưới, trường hợp nào planner vẫn dùng index?

```sql
DROP TABLE IF EXISTS g;
CREATE TABLE g AS
SELECT i AS id, i % 1000 AS thousandth, 'User' || (i % 5000) AS name, i::text AS id_text
FROM generate_series(1, 500000) i;
CREATE INDEX g_id ON g (id);
CREATE INDEX g_th ON g (thousandth);
CREATE INDEX g_name ON g (name);
CREATE INDEX g_idtext ON g (id_text text_pattern_ops);
ANALYZE g;

\echo '-- 1a. lấy 90% số dòng'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE thousandth < 900;
\echo '-- 1b. lấy 0,5% số dòng'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE thousandth < 5;
\echo '-- 2. bọc cột trong hàm'

\echo '-- 3. tính toán trên cột'

\echo '-- 4. ép kiểu cột'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE id_text::int = 500;
\echo '-- 5a. LIKE tiền tố'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE id_text LIKE '4999%';
\echo '-- 5b. LIKE hậu tố'
EXPLAIN (COSTS OFF) SELECT * FROM g WHERE id_text LIKE '%999';
```

2. **Điều kiện không khớp với thứ index đã sắp** (2, 3, 4, 5b). Index sắp theo giá trị gốc của `name`, không theo `lower(name)`; sắp theo `id`, không theo `id + 1`. `LIKE '4999%'` đổi được thành một khoảng (từ `4999` tới trước `499:`) nên dùng được index, còn `LIKE '%999'` thì các giá trị khớp nằm rải khắp nơi.

Cách sửa nhóm 2: viết lại để **cột đứng một mình** (`id = 99` thay cho `id + 1 = 100`), hoặc tạo **index trên biểu thức**:

```sql
CREATE INDEX g_lower_name ON g (lower(name));

EXPLAIN (COSTS OFF) SELECT * FROM g WHERE id = 99;
```

```text
(4 rows)

         QUERY PLAN

   Index Cond: (id = 99)
(2 rows)
```

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ thấy `Seq Scan` dù đã có index là planner chọn sai. Thật ra ở trường hợp 1a, `Seq Scan` **là** cách rẻ nhất. Ép planner dùng index (`SET enable_seqscan = off`) chỉ để thử nghiệm, không dùng ở production. Planner chỉ thật sự sai khi thống kê cũ làm nó ước lượng lệch số dòng; khi đó cần chạy `ANALYZE`.

**Thử ngay:** cột `created_at` có index. Truy vấn `WHERE date(created_at) = '2026-01-05'` không dùng được index. Viết lại thế nào để dùng được, mà không cần tạo index mới?

<Expand title="Đáp án">

Đổi thành một khoảng trên chính cột đó: `WHERE created_at >= '2026-01-05' AND created_at < '2026-01-06'`. Cột đứng một mình nên index dùng được, và kết quả giống hệt.

</Expand>

## Các kiểu index khác

B-tree là mặc định và đúng cho hầu hết trường hợp, vì nó hỗ trợ cả `=`, khoảng, `ORDER BY` và `LIKE` tiền tố. PostgreSQL còn vài kiểu khác cho các dạng dữ liệu đặc biệt. Số liệu dưới đo trên một bảng 1.000.000 dòng (112 MB); code và output nằm ở phần Đi sâu hơn.

| Kiểu | Hỗ trợ | Kích thước | Dùng khi |
|---|---|---|---|
| B-tree | `=`, khoảng, `ORDER BY`, `LIKE 'abc%'` | 56 MB (chuỗi 32 ký tự), 21 MB (timestamp) | mặc định cho hầu hết cột |
| Hash | chỉ `=` | 32 MB (chuỗi 32 ký tự) | chỉ tra cứu bằng, khoá dài |
| GIN | "chứa phần tử": mảng, JSON, tìm kiếm văn bản | 16 MB | cột nhiều giá trị, ví dụ `tags @> ARRAY[...]` |
| BRIN | khoảng, khi dữ liệu đã theo thứ tự trên đĩa | **24 kB** | bảng rất lớn, cột tăng theo thời gian (log, sự kiện) |

## Tự kiểm tra tổng hợp

Các câu dưới trộn kiến thức của nhiều mục. Nếu vướng, quay lại mục tương ứng.

1. Bảng `orders(id, user_id, status, created_at, total)`, truy vấn chạy nhiều nhất là `SELECT id, total FROM orders WHERE user_id = ? AND status = 'paid' ORDER BY created_at DESC LIMIT 20`. Thiết kế một index cho nó, và giải thích thứ tự cột.
2. Một đồng nghiệp đánh index cho cả 12 cột của bảng `events` (chủ yếu được ghi, thỉnh thoảng mới đọc) "để truy vấn nào cũng nhanh". Hệ quả là gì?
3. Bảng `users` có index trên `email`, nhưng màn hình đăng nhập chạy `WHERE lower(email) = lower(?)` và rất chậm. Vì sao? Nêu hai cách sửa.
4. Bảng 2 tỉ dòng log, chỉ chèn thêm theo thời gian, thường truy vấn "các dòng trong 10 phút qua". So sánh B-tree và BRIN trên cột thời gian.

<Expand title="Đáp án">

1. `(user_id, status, created_at)`. Hai cột so sánh bằng đặt trước (thứ tự giữa chúng không quan trọng lắm), `created_at` dùng cho `ORDER BY` đặt sau cùng. Như vậy các đơn `paid` của một user nằm liền nhau và đã sắp theo thời gian, chỉ cần đọc 20 mục từ cuối, không sắp xếp. Có thể thêm `INCLUDE (id, total)` để truy vấn thành index-only scan, vì index của PostgreSQL không tự chứa khoá chính.
2. Mỗi lần ghi phải cập nhật 12 cây: lượng ghi tăng nhiều lần (ở thí nghiệm trên, 5 index đã gần gấp 4), index chiếm chỗ gấp nhiều lần dữ liệu và đẩy dữ liệu hữu ích ra khỏi bộ nhớ đệm. Phần lớn index không bao giờ được dùng vì truy vấn thật chỉ lọc vài cột. Nên giữ index cho đúng truy vấn thật, và gộp bằng composite index nếu được.
3. Index sắp theo `email` gốc, còn truy vấn so sánh `lower(email)`, nên planner phải quét cả bảng. Cách 1: tạo index trên biểu thức `lower(email)`. Cách 2: luôn lưu email đã chuyển về chữ thường khi ghi, rồi truy vấn `WHERE email = lower(?)`.
4. Cả hai đều dùng được vì cột tăng dần theo thứ tự chèn (correlation gần 1). B-tree trên 2 tỉ dòng to tới hàng chục GB và phải cập nhật mỗi lần chèn. BRIN chỉ lưu min và max của mỗi nhóm trang nên nhỏ hơn hàng nghìn lần và gần như không tốn chi phí ghi; đổi lại nó chỉ khoanh vùng theo nhóm trang (phải lọc lại các dòng trong vùng), và chỉ dùng được vì dữ liệu nằm theo thứ tự thời gian. Với bảng log kiểu này, BRIN thường là lựa chọn tốt.

</Expand>

## Đi sâu hơn

Các phần dưới không cần để đọc tiếp chặng cơ sở dữ liệu. Chúng chạy tiếp trên cùng các bảng ở trên, theo đúng thứ tự.

<Expand title="Tự cài một B+ tree: chiều cao, truy vấn khoảng, độ đầy của lá">

B+ tree tối giản dưới đây có mỗi nút là một "trang" chứa tối đa `order` khoá, và bộ đếm `reads` đếm số trang đã chạm tới. Khi lá đầy, nó tách đôi và đẩy khoá giữa lên nút cha.

```python
# B+ tree tối giản: khoá chỉ nằm ở lá, các lá nối thành danh sách liên kết, mỗi nút = một "trang".
import bisect, random, math

class Leaf:
    def __init__(self): self.keys, self.vals, self.next = [], [], None
class Inner:
    def __init__(self): self.keys, self.kids = [], []        # len(kids) = len(keys) + 1

class BPlusTree:
    def __init__(self, order):
        self.order = order                                    # số khoá tối đa mỗi nút (fan-out)
        self.root = Leaf(); self.reads = 0                    # reads = số "trang" đã chạm tới

    def _leaf_for(self, key):
        n, path = self.root, []
        while isinstance(n, Inner):
            self.reads += 1
            path.append(n)
            n = n.kids[bisect.bisect_right(n.keys, key)]
        self.reads += 1
        return n, path

    def get(self, key):
        leaf, _ = self._leaf_for(key)
        i = bisect.bisect_left(leaf.keys, key)
        return leaf.vals[i] if i < len(leaf.keys) and leaf.keys[i] == key else None

    def range(self, lo, hi):                                  # tìm lá chứa lo, rồi đi ngang theo con trỏ next
        leaf, out = self._leaf_for(lo)[0], []
        while leaf:
            for k, v in zip(leaf.keys, leaf.vals):
                if k > hi: return out
                if k >= lo: out.append((k, v))
            leaf = leaf.next
            if leaf: self.reads += 1
        return out

    def insert(self, key, val):
        leaf, path = self._leaf_for(key)
        i = bisect.bisect_left(leaf.keys, key)
        if i < len(leaf.keys) and leaf.keys[i] == key: leaf.vals[i] = val; return
        leaf.keys.insert(i, key); leaf.vals.insert(i, val)
        if len(leaf.keys) <= self.order: return
        mid = len(leaf.keys) // 2                             # lá đầy: tách đôi, khoá giữa được SAO lên cha (vẫn giữ ở lá)
        right = Leaf()
        right.keys, right.vals = leaf.keys[mid:], leaf.vals[mid:]
        leaf.keys, leaf.vals = leaf.keys[:mid], leaf.vals[:mid]
        right.next, leaf.next = leaf.next, right
        self._push_up(path, leaf, right.keys[0], right)

    def _push_up(self, path, left, sep, right):
        if not path:                                          # tách tới tận gốc: cây cao thêm một tầng
            r = Inner(); r.keys, r.kids = [sep], [left, right]; self.root = r; return
        parent = path.pop()
        i = bisect.bisect_right(parent.keys, sep)
        parent.keys.insert(i, sep); parent.kids.insert(i + 1, right)
        if len(parent.keys) <= self.order: return
        mid = len(parent.keys) // 2                           # nút trong đầy: khoá giữa ĐI LÊN (không còn ở nút trong con)
        up = parent.keys[mid]
        sib = Inner(); sib.keys, sib.kids = parent.keys[mid + 1:], parent.kids[mid + 1:]
        parent.keys, parent.kids = parent.keys[:mid], parent.kids[:mid + 1]
        self._push_up(path, parent, up, sib)

    def stats(self):
        h, n = 1, self.root
        while isinstance(n, Inner): n = n.kids[0]; h += 1
        leaves, keys = 0, 0
        while n: leaves += 1; keys += len(n.keys); n = n.next
        return h, leaves, keys / (leaves * self.order)       # chiều cao, số lá, độ đầy trung bình của lá

if __name__ == "__main__":
    ORDER = 100                                               # ~100 khoá mỗi trang
    random.seed(5)
    N = 200_000
    keys = random.sample(range(10 * N), N)

    t = BPlusTree(ORDER)
    for k in keys: t.insert(k, k * 2)
    assert all(t.get(k) == k * 2 for k in keys[:5000])
    h, leaves, fill = t.stats()
    print(f"{N:,} khoá, order = {ORDER}: cao {h} tầng, {leaves:,} lá, độ đầy trung bình của lá = {fill:.0%}")

    t.reads = 0
    for k in keys[:10_000]: t.get(k)
    print(f"tìm 1 khoá: {t.reads / 10_000:.2f} trang mỗi lần (= chiều cao); quét tuần tự cả bảng cần {leaves:,} trang")

    lo = sorted(keys)[N // 2]; hi = lo + 10 * N // 100       # khoảng chứa khoảng 1% số khoá
    t.reads = 0
    res = t.range(lo, hi)
    assert [k for k, _ in res] == [k for k in sorted(keys) if lo <= k <= hi]
    print(f"tìm khoảng 1% ({len(res):,} khoá): {t.reads} trang (xuống lá đầu tiên rồi đi ngang qua các lá kế tiếp)")

    print()
    print(f"{'cách chèn':<24} {'cao':>4} {'số lá':>8} {'độ đầy lá':>10}")
    for name, order_keys in (("ngẫu nhiên", keys), ("tăng dần", sorted(keys)), ("giảm dần", sorted(keys, reverse=True))):
        t = BPlusTree(ORDER)
        for k in order_keys: t.insert(k, 0)
        h, leaves, fill = t.stats()
        print(f"{name:<24} {h:>4} {leaves:>8,} {fill:>10.0%}")
    ideal = math.ceil(N / ORDER)
    print(f"{'nạp hàng loạt (100%)':<24} {'':>4} {ideal:>8,} {'100%':>10}   (lý tưởng: {N:,} / {ORDER} = {ideal:,} lá)")
```

- Chèn ngẫu nhiên cho lá đầy **69%** (khoảng `ln 2`, một kết quả kinh điển). Chèn tăng dần với cách tách 50/50 cho lá chỉ đầy **50%**, vì nửa trái sau khi tách không bao giờ được chèn thêm. PostgreSQL tránh điều này: khi tách lá ngoài cùng bên phải, nó giữ lá trái đầy tới `fillfactor` (mặc định 90%). Còn `CREATE INDEX` trên dữ liệu có sẵn thì sắp xếp rồi dựng cây từ dưới lên, các lá gần đầy hoàn toàn.

<Expand title="Tính tay vì sao một lá chứa đúng 367 hay 141 khoá">

Một trang 8.192 byte, trừ phần đầu trang (24 byte) và vùng đặc biệt ở cuối trang (16 byte), còn **8.152 byte**. Lá B-tree của PostgreSQL mặc định chỉ đổ đầy tới `fillfactor` **90%** khi dựng index, nên dùng `8.152 × 0,9 ≈ 7.337` byte.

- Khoá `int4`: mỗi mục gồm phần đầu 8 byte (chứa `ctid`) cộng 4 byte khoá, căn lề lên **16 byte**, cộng 4 byte con trỏ dòng trong trang = **20 byte**. `7.337 / 20 ≈ 367` mục, khớp output.
- Khoá `md5` 32 ký tự: 8 byte đầu mục, cộng 33 byte (1 byte độ dài và 32 ký tự), căn lề lên 48 byte, cộng 4 byte con trỏ dòng = **52 byte**. `7.337 / 52 ≈ 141` mục, khớp output.

Bài học: **khoá ngắn thì index nhỏ, cây thấp, và nhiều phần của index nằm vừa bộ nhớ đệm hơn.**

</Expand>

<Expand title="Index-only scan cần visibility map sạch">

Index không lưu thông tin dòng nào còn "nhìn thấy được" với transaction hiện tại (xem <Term>MVCC</Term> ở bài [Transactions](/docs/databases/transactions)). <Expand title="Bitmap scan và lệnh CLUSTER">

Ở mục thứ tự trên đĩa, ta đã ép planner dùng `Index Scan` cho `rnd`. Để planner tự chọn, nó dùng **bitmap scan**: đọc index trước, gom mọi `ctid` thành một bản đồ bit theo trang, rồi đọc bảng **theo thứ tự trang, mỗi trang đúng một lần**. Sau đó `CLUSTER` sắp lại cả bảng theo index `t_rnd`:

```sql
\echo '== planner tự chọn cho rnd =='
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON)
SELECT count(token) FROM t WHERE rnd BETWEEN 500000 AND 509999;

\echo '== CLUSTER: sắp lại bảng theo index t_rnd =='
CLUSTER t USING t_rnd;
ANALYZE t;
SELECT attname, round(correlation::numeric, 3) AS correlation
FROM pg_stats WHERE tablename = 't' AND attname IN ('id', 'rnd') ORDER BY attname;
SET enable_bitmapscan = off; SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, COSTS OFF, SUMMARY ON)
SELECT count(token) FROM t WHERE rnd BETWEEN 500000 AND 509999;
RESET enable_bitmapscan; RESET enable_seqscan;
```

<Expand title="Index trong vận hành thật">

- **Index bị phình (bloat)** theo thời gian vì xoá và cập nhật. `REINDEX CONCURRENTLY` dựng lại mà không khoá ghi.
- `CREATE INDEX CONCURRENTLY` tạo index trên bảng đang chạy mà không chặn ghi, đổi lại chậm hơn và có thể thất bại, để lại một index "invalid" cần xoá.
- **Partial index** (`CREATE INDEX ... WHERE active`) chỉ đánh index một phần dòng. Nó nhỏ và nhanh hơn khi truy vấn luôn lọc đúng điều kiện đó.
- Cơ sở dữ liệu kiểu **LSM-tree** (RocksDB, Cassandra) đánh đổi ngược lại B-tree: ghi nhanh hơn nhiều, đọc phải kiểm tra nhiều tầng. Xem bài [Storage Engines](/docs/databases/storage-engines).

| Triệu chứng | Nguyên nhân hay gặp | Cách xử lý |
|---|---|---|
| `Seq Scan` dù đã có index | lấy quá nhiều dòng; cột bị bọc hàm hoặc phép tính; thống kê cũ | `EXPLAIN`, viết lại điều kiện, `ANALYZE`, index trên biểu thức |
| Composite index không được dùng | điều kiện bỏ qua cột đầu | đổi thứ tự cột hoặc thêm index khác |
| Ghi chậm dần | quá nhiều index | xoá index có `idx_scan = 0`, gộp bằng composite index |
| Index-only scan vẫn nhiều `Heap Fetches` | visibility map chưa cập nhật | `VACUUM`, kiểm tra autovacuum |
| Truy vấn khoảng chạm quá nhiều trang | correlation thấp, mỗi dòng một trang | covering index, `CLUSTER`, hoặc BRIN nếu dữ liệu theo thứ tự |

</Expand>

**Cần biết trước:** đọc được C cơ bản (hàm, vòng lặp, con trỏ tới mảng), và bù hai ở bài [Data Representation](/docs/architecture/data-representation). Ví dụ chạy trên x86-64 Linux (WSL2) với gcc 13.

**Cách đọc bài:** mỗi mục có một câu **Đoán trước** và kết bằng một câu **Thử ngay**. Hãy tự trả lời trong đầu (hoặc ra giấy) rồi mới xem đáp án. Việc tự nhớ lại và tự đoán giúp nhớ lâu hơn nhiều so với chỉ đọc.

## Ý chính

CPU không hiểu C hay Python. Nó chỉ chạy những **lệnh** rất nhỏ: cộng hai thanh ghi, đọc 8 byte từ một địa chỉ, so sánh, nhảy tới lệnh khác. Danh sách lệnh mà một họ CPU hiểu gọi là <Term>ISA</Term>. Trình biên dịch dịch mã nguồn thành các lệnh đó; dạng đọc được của chúng là <Term>assembly</Term>.

Bạn hiếm khi viết assembly, nhưng đọc được nó trả lời những câu mã nguồn không trả lời: vì sao bản debug chậm hơn bản release cả chục lần, đối số của hàm nằm ở đâu, vì sao đệ quy quá sâu làm chương trình chết, và trình biên dịch đã biến một `if` thành gì. Bài này đọc assembly mà gcc sinh ra cho vài hàm nhỏ, rồi đo những điều đó.

## CPU chỉ làm những việc rất nhỏ

CPU tính toán trên <Term>register</Term> (**thanh ghi**): vài chục ô nhớ nằm ngay trong CPU, đọc ghi trong một chu kỳ. x86-64 có 16 thanh ghi đa dụng 64 bit: `rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`, `rbp`, `rsp`, và `r8` tới `r15`. Phần lớn lệnh lấy toán hạng từ thanh ghi và ghi kết quả vào thanh ghi.

Hàm dưới nhân rồi cộng. **Đoán trước:** khi biên dịch có tối ưu, nó thành bao nhiêu lệnh?

```c
// mul_add.c
long mul_add(long a, long b, long c) { return a * b + c; }
```

Script nhỏ `asm.sh` gọi `gcc -S` để dịch ra assembly cú pháp Intel và bỏ các dòng chỉ thị cho dễ đọc:

<Expand title="Code asm.sh">

```bash
# asm.sh: in assembly (cú pháp Intel) của một file C, bỏ các dòng chỉ thị bắt đầu bằng dấu chấm
# dùng: bash asm.sh <mức tối ưu> <file.c>
gcc "$1" -S -masm=intel -fno-asynchronous-unwind-tables -fcf-protection=none -o - "$2" | grep -vP '^\t\.'
```

</Expand>

```bash
bash asm.sh -O2 mul_add.c
```

```text
mul_add:
	imul	rdi, rsi
	lea	rax, [rdi+rdx]
	ret
```

Ba lệnh. Cú pháp Intel viết **đích trước**:

```text
imul rdi, rsi          ; rdi = rdi * rsi        (a * b)
lea  rax, [rdi+rdx]    ; rax = rdi + rdx        (+ c)
ret                    ; trở về; kết quả nằm trong rax
```

`lea` vốn để tính địa chỉ `[cơ sở + chỉ số]`, nhưng trình biên dịch mượn nó làm phép cộng ba toán hạng vì nó ghi được vào một thanh ghi thứ ba. Không có biến `a`, `b`, `c` nào trong bộ nhớ: tất cả nằm trong thanh ghi.

**Thử ngay:** hàm `long add(long a, long b) { return a + b; }` ở `-O2` sẽ ra lệnh gì?

<Expand title="Đáp án">

Một `lea` cộng hai thanh ghi đối số vào `rax`, rồi `ret`:

```c
// add.c
long add(long a, long b) { return a + b; }
```

```bash
bash asm.sh -O2 add.c
```

```text
add:
	lea	rax, [rdi+rsi]
	ret
```

</Expand>

## Quy ước gọi hàm: đối số nằm ở đâu

Mục trước có một câu chưa trả lời: sao biết `a` nằm trong `rdi`, `b` trong `rsi`, và kết quả phải để trong `rax`? Đó là <Term>calling convention</Term> (**quy ước gọi hàm**). Trên Linux và macOS x86-64, quy ước là System V AMD64 ABI:

| Vai trò | Thanh ghi |
|---|---|
| 6 đối số nguyên hoặc con trỏ đầu tiên | `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9` (từ đối số thứ 7 trở đi để trên stack) |
| Đối số số thực | `xmm0` tới `xmm7` |
| Giá trị trả về | `rax` (số thực: `xmm0`) |
| Hàm được gọi phải giữ nguyên | `rbx`, `rbp`, `r12` tới `r15`, và `rsp` |
| Hàm được gọi được tự do ghi đè | `rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8` tới `r11` |

Nhờ thoả thuận này, mã do hai trình biên dịch khác nhau sinh ra gọi được nhau: Rust gọi được thư viện C, Python gọi được hàm C qua `ctypes`. Hai bên chỉ cần dùng cùng quy ước. Windows x64 dùng quy ước khác (`rcx`, `rdx`, `r8`, `r9`), nên một file `.o` biên dịch cho Linux không gọi thẳng được từ mã biên dịch cho Windows.

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ đối số luôn được đẩy lên stack trước khi gọi hàm. Thật ra trên x86-64, sáu đối số nguyên đầu đi bằng thanh ghi; stack chỉ dùng khi nhiều hơn, hoặc khi đối số là struct lớn. Kiểu "đẩy hết lên stack" là của x86 32 bit cũ.

**Thử ngay:** với `long f(long a, long b, long c, long d, long e, long g, long h)`, đối số `d` và `h` nằm ở đâu khi `f` bắt đầu chạy?

<Expand title="Đáp án">

`d` là đối số thứ 4, nằm trong `rcx`. `h` là đối số thứ 7, hết thanh ghi nên nằm trên stack, ngay trên địa chỉ trả về.

</Expand>

## Không tối ưu và có tối ưu

Cùng `mul_add`, biên dịch với `-O0` (không tối ưu, mặc định khi bạn không ghi gì). **Đoán trước:** dài hơn bao nhiêu, và các lệnh thêm vào làm gì?

```bash
bash asm.sh -O0 mul_add.c
```

```text
mul_add:
	push	rbp
	mov	rbp, rsp
	mov	QWORD PTR -8[rbp], rdi
	mov	QWORD PTR -16[rbp], rsi
	mov	QWORD PTR -24[rbp], rdx
	mov	rax, QWORD PTR -8[rbp]
	imul	rax, QWORD PTR -16[rbp]
	mov	rdx, rax
	mov	rax, QWORD PTR -24[rbp]
	add	rax, rdx
	pop	rbp
	ret
```

Mười hai lệnh thay cho ba. `-O0` cất từng đối số từ thanh ghi xuống **bộ nhớ** (`mov QWORD PTR -8[rbp], rdi`), rồi đọc lại từ bộ nhớ để tính. Mỗi biến có một chỗ cố định trên stack để debugger đọc được giá trị của nó ở bất kỳ dòng nào. Cái giá là mọi phép tính đều đi vòng qua bộ nhớ.

Chênh lệch đó lớn tới đâu? Chương trình dưới cộng 4.096 số `long` (32 KiB, nằm gọn trong cache L1) 400.000 lần, và in thời gian mỗi phần tử:

<Expand title="Code sum_cost.c">

```c
// sum_cost.c: cộng 4096 số long (32 KiB, nằm gọn trong L1) 400000 lần, in thời gian mỗi phần tử
#include <stdio.h>
#include <time.h>

#define N 4096
long data[N];

long sum_array(const long *p, long n) {
    long s = 0;
    for (long i = 0; i < n; i++) s += p[i];
    return s;
}

int main(void) {
    for (long i = 0; i < N; i++) data[i] = i & 7;
    int reps = 400000;
    long total = 0;
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    for (int r = 0; r < reps; r++) {
        total += sum_array(data, N);
        __asm__ volatile("" ::: "memory");   // bắt trình biên dịch tính lại mỗi lần, không được gộp các lần lặp
    }
    clock_gettime(CLOCK_MONOTONIC, &t1);
    double ns = ((t1.tv_sec - t0.tv_sec) * 1e9 + (t1.tv_nsec - t0.tv_nsec)) / ((double)N * reps);
    printf("%.3f ns mỗi phần tử (tổng kiểm tra %ld)\n", ns, total);
    return 0;
}
```

</Expand>

```bash
for lv in -O0 -O2; do
  printf "%s: " $lv
  gcc $lv -o sum_cost sum_cost.c && ./sum_cost
done
```

```text
-O0: 1.714 ns mỗi phần tử (tổng kiểm tra 5734400000)
-O2: 0.241 ns mỗi phần tử (tổng kiểm tra 5734400000)
```

Cùng mã nguồn, chỉ đổi một cờ biên dịch: `1,714` ns xuống `0,241` ns mỗi phần tử, nhanh hơn khoảng **7 lần**. Phần lớn chênh lệch đến từ việc `-O0` đọc ghi `s` và `i` vào bộ nhớ ở mỗi vòng, còn `-O2` giữ chúng trong thanh ghi (mục sau đọc từng lệnh của vòng lặp này).

**Hiểu lầm hay gặp ở đây:** nhiều người đo tốc độ trên bản debug rồi kết luận đoạn code nào nhanh hơn. Thật ra bản `-O0` chậm theo cách khác hẳn bản release: nút thắt là việc đọc ghi biến vào bộ nhớ mà bản release không có. Luôn đo bản `-O2` (hoặc `--release`, chế độ production của ngôn ngữ bạn dùng).

**Thử ngay:** debugger đang dừng ở một dòng của bản `-O2` và báo biến `i` là "optimized out". Vì sao?

<Expand title="Đáp án">

Ở `-O2`, `i` không có chỗ cố định trong bộ nhớ; nó sống trong một thanh ghi, và có khi bị bỏ hẳn (như vòng lặp ở mục sau chỉ còn một con trỏ chạy). Debugger không còn chỗ nào để đọc `i`. Muốn debug từng biến thì biên dịch `-O0` (hoặc `-Og`), muốn đo tốc độ thì dùng `-O2`.

</Expand>

## if và vòng lặp: so sánh rồi nhảy

CPU chạy lệnh theo thứ tự, trừ khi gặp lệnh **nhảy**. Mọi `if`, `for`, `while` được dịch thành hai bước:

1. Lệnh `cmp a, b` tính `a - b`, bỏ kết quả, chỉ giữ lại các **cờ** (bằng 0 không, âm không...) trong thanh ghi cờ `rflags`.
2. Lệnh nhảy có điều kiện đọc cờ và quyết định có nhảy không: `je` (bằng), `jne` (khác), `jl` (nhỏ hơn), `jle` (nhỏ hơn hoặc bằng), `jge` (lớn hơn hoặc bằng)...

**Đoán trước:** hàm `clamp` dưới có hai `if`. Ở `-O0`, bạn sẽ thấy bao nhiêu lệnh nhảy?

```c
// clamp.c
long clamp(long x, long lo, long hi) {
    if (x < lo) return lo;
    if (x > hi) return hi;
    return x;
}
```

```bash
bash asm.sh -O0 clamp.c
```

```text
clamp:
	push	rbp
	mov	rbp, rsp
	mov	QWORD PTR -8[rbp], rdi
	mov	QWORD PTR -16[rbp], rsi
	mov	QWORD PTR -24[rbp], rdx
	mov	rax, QWORD PTR -8[rbp]
	cmp	rax, QWORD PTR -16[rbp]
	jge	.L2
	mov	rax, QWORD PTR -16[rbp]
	jmp	.L3
.L2:
	mov	rax, QWORD PTR -8[rbp]
	cmp	rax, QWORD PTR -24[rbp]
	jle	.L4
	mov	rax, QWORD PTR -24[rbp]
	jmp	.L3
.L4:
	mov	rax, QWORD PTR -8[rbp]
.L3:
	pop	rbp
	ret
```

Bốn lệnh nhảy: hai nhảy có điều kiện cho hai `if`, hai `jmp` để nhảy tới đoạn `return` chung. Để ý điều kiện bị **đảo ngược**: C viết `if (x < lo)`, assembly viết `jge .L2` ("nếu `x >= lo` thì nhảy qua phần `return lo`"). Trình biên dịch nhảy qua thân `if` khi điều kiện sai, nên lệnh nhảy kiểm tra điều kiện ngược lại. Các nhãn `.L2`, `.L3` là đích nhảy.

**Thử ngay:** `cmp rax, rbx` rồi `jl .L5`. CPU nhảy tới `.L5` khi nào?

<Expand title="Đáp án">

Khi `rax < rbx` (so sánh có dấu). `cmp rax, rbx` đặt cờ theo `rax - rbx`, và `jl` (jump if less) nhảy khi kết quả đó âm theo nghĩa có dấu. Với số không dấu, lệnh tương ứng là `jb` (jump if below).

</Expand>

## Đọc assembly: ba ví dụ

Đọc assembly là kỹ năng: đối chiếu từng lệnh với một dòng C. Ba ví dụ dưới đi từ giải sẵn tới tự làm, đều ở `-O2`.

### Ví dụ 1 (giải sẵn): vòng lặp cộng mảng

```c
// sum_array.c
long sum_array(const long *p, long n) {
    long s = 0;
    for (long i = 0; i < n; i++) s += p[i];
    return s;
}
```

```bash
bash asm.sh -O2 sum_array.c
```

```text
sum_array:
	test	rsi, rsi
	jle	.L4
	lea	rdx, [rdi+rsi*8]
	xor	eax, eax
.L3:
	add	rax, QWORD PTR [rdi]
	add	rdi, 8
	cmp	rdi, rdx
	jne	.L3
	ret
.L4:
	xor	eax, eax
	ret
```

Đọc từng khối, nhớ `p` ở `rdi`, `n` ở `rsi`, kết quả ở `rax`:

| Lệnh | Nghĩa | Dòng C |
|---|---|---|
| `test rsi, rsi` / `jle .L4` | nếu `n <= 0` thì nhảy tới cuối, trả 0 | điều kiện vòng lặp lần đầu |
| `lea rdx, [rdi+rsi*8]` | `rdx = p + n` (mỗi `long` 8 byte): con trỏ **cuối mảng** | (trình biên dịch tự thêm) |
| `xor eax, eax` | `rax = 0` (XOR với chính nó là cách gán 0 ngắn nhất) | `s = 0` |
| `add rax, QWORD PTR [rdi]` | `s += *p` | `s += p[i]` |
| `add rdi, 8` | `p++` | `i++` |
| `cmp rdi, rdx` / `jne .L3` | nếu `p` chưa tới cuối thì lặp | `i < n` |

Biến `i` biến mất. Trình biên dịch thay "tính `p + i*8` mỗi vòng" bằng "tăng thẳng con trỏ và so với con trỏ cuối". Vòng lặp chỉ còn 4 lệnh, không lệnh nào ghi bộ nhớ. Đây là lý do `-O2` nhanh hơn `-O0` ở mục trước.

### Ví dụ 2 (giải một nửa): clamp không còn lệnh nhảy

```bash
bash asm.sh -O2 clamp.c
```

```text
clamp:
	cmp	rdi, rdx
	mov	rax, rsi
	cmovle	rdx, rdi
	cmp	rdi, rsi
	cmovge	rax, rdx
	ret
```

Không còn lệnh nhảy nào. `cmovle a, b` là **di chuyển có điều kiện**: "nếu cờ báo nhỏ hơn hoặc bằng thì `a = b`, không thì giữ nguyên `a`". Điền chỗ trống, nhớ `x` ở `rdi`, `lo` ở `rsi`, `hi` ở `rdx`:

| Lệnh | Nghĩa |
|---|---|
| `cmp rdi, rdx` | so `x` với `hi` |
| `mov rax, rsi` | `rax = lo` |
| `cmovle rdx, rdi` | nếu `x <= hi` thì `rdx = ___`; sau lệnh này `rdx = min(x, hi)` |
| `cmp rdi, rsi` | so `x` với ___ |
| `cmovge rax, rdx` | nếu ___ thì `rax = rdx`; không thì `rax` giữ ___ |

<Expand title="Đáp án">

`cmovle rdx, rdi`: nếu `x <= hi` thì `rdx = x`, nên `rdx = min(x, hi)`. `cmp rdi, rsi` so `x` với `lo`. `cmovge rax, rdx`: nếu `x >= lo` thì `rax = min(x, hi)`, không thì `rax` giữ `lo`. Kiểm với `x = 15, lo = 0, hi = 10`: `rdx = min(15, 10) = 10`, `x >= lo` nên `rax = 10`. Với `x = -3`: `rdx = -3`, `x < lo` nên `rax` giữ `lo = 0`. Đúng với `clamp`.

</Expand>

Trình biên dịch chọn `cmov` khi cả hai nhánh đều rẻ và an toàn để tính. Không có lệnh nhảy thì CPU không phải đoán nhảy hay không, điều bài [CPU Pipeline & Branch Prediction](/docs/architecture/pipeline-branch-prediction) sẽ đo.

### Ví dụ 3 (tự làm)

Đây là assembly `-O2` của một hàm nhận `(const long *p, long n)`. Không có mã C. Hàm này làm gì, và `shr rax, 63` thay cho dòng C nào?

```text
count_neg:
	test	rsi, rsi
	jle	.L5
	lea	rcx, [rdi+rsi*8]
	xor	edx, edx
.L4:
	mov	rax, QWORD PTR [rdi]
	add	rdi, 8
	shr	rax, 63
	add	rdx, rax
	cmp	rcx, rdi
	jne	.L4
	mov	rax, rdx
	ret
.L5:
	xor	edx, edx
	mov	rax, rdx
	ret
```

<Expand title="Đáp án">

Hàm đếm số phần tử âm. Khung vòng lặp giống hệt ví dụ 1. Trong thân: đọc `p[i]` vào `rax`, dịch phải logic 63 bit để chỉ còn **bit dấu** (1 nếu âm, 0 nếu không, theo bù hai ở bài [Data Representation](/docs/architecture/data-representation)), rồi cộng vào bộ đếm `rdx`. Dòng C `if (p[i] < 0) c++;` thành "cộng bit dấu", không cần lệnh nhảy. Mã nguồn thật:

```c
// count_neg.c
long count_neg(const long *p, long n) {
    long c = 0;
    for (long i = 0; i < n; i++)
        if (p[i] < 0) c++;
    return c;
}
```

```bash
bash asm.sh -O2 count_neg.c
```

```text

	test	rsi, rsi
	jle	.L5
	lea	rcx, [rdi+rsi*8]
	xor	edx, edx
.L4:
	mov	rax, QWORD PTR [rdi]
	add	rdi, 8
	shr	rax, 63
	add	rdx, rax
	cmp	rcx, rdi
	jne	.L4
	mov	rax, rdx
	ret
.L5:

	mov	rax, rdx
	ret
```

## Stack: mỗi lời gọi một khung

Khi hàm A gọi hàm B, CPU phải nhớ quay về đâu trong A. Chỗ nhớ là <Term>stack</Term>: một vùng bộ nhớ mà thanh ghi `rsp` luôn trỏ vào đỉnh. Trên x86, stack **mọc xuống**: đẩy thêm thì `rsp` giảm.

- `call f`: đẩy địa chỉ lệnh kế tiếp (**địa chỉ trả về**) lên stack rồi nhảy tới `f`.
- `ret`: lấy địa chỉ trả về ra khỏi stack và nhảy tới đó.

Ngoài địa chỉ trả về, mỗi lời gọi thường có thêm biến cục bộ và thanh ghi cần cất. Cả cụm đó là một <Term>stack frame</Term> (**khung**). Hàm đệ quy gọi chính nó, nên mỗi tầng đệ quy thêm một khung bên dưới khung cũ.

Stack có giới hạn: 8 MiB mặc định cho thread chính trên Linux. **Đoán trước:** một hàm đệ quy có mảng cục bộ 16 byte, đệ quy mãi không dừng. Nó chết ở độ sâu cỡ bao nhiêu: một nghìn, một trăm nghìn hay mười triệu?

<Expand title="Code stack_depth.c">

```c
// stack_depth.c: đệ quy mãi tới khi stack cạn; in địa chỉ biến cục bộ ở ba tầng đầu và độ sâu lúc chết
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

static volatile long depth = 0;

static void on_segv(int sig) {
    (void)sig;
    printf("SIGSEGV ở độ sâu %ld (stack cạn)\n", depth);
    fflush(stdout);
    _exit(0);
}

void dive(void) {
    char pad[16];
    depth++;
    if (depth <= 3) printf("độ sâu %ld: &pad = %p\n", depth, (void *)pad);
    dive();
    pad[0] = 0;                 // dùng pad sau lời gọi để lời gọi không bị biến thành vòng lặp
}

int main(void) {
    static char alt[65536];     // trình xử lý tín hiệu chạy trên stack riêng, vì stack chính đã cạn
    stack_t ss = { .ss_sp = alt, .ss_size = sizeof alt };
    sigaltstack(&ss, NULL);
    struct sigaction sa = { .sa_handler = on_segv, .sa_flags = SA_ONSTACK };
    sigaction(SIGSEGV, &sa, NULL);
    setvbuf(stdout, NULL, _IONBF, 0);
    dive();
    return 0;
}
```

</Expand>

```bash
echo "giới hạn stack: $(ulimit -s) KiB"
gcc -O0 -o stack_depth stack_depth.c && ./stack_depth
```

```text
giới hạn stack: 8192 KiB
độ sâu 1: &pad = 0x7ffd289585a0
độ sâu 2: &pad = 0x7ffd28958570
độ sâu 3: &pad = 0x7ffd28958540
SIGSEGV ở độ sâu 174538 (stack cạn)
```

Địa chỉ của `pad` giảm đều `0x30` = 48 byte mỗi tầng: mỗi khung chiếm 48 byte (16 byte của `pad`, địa chỉ trả về, `rbp` được cất, phần căn lề). Chia: `8 MiB / 48 byte ≈ 174.000`, khớp với độ sâu đo được. Vượt giới hạn, `rsp` chạm một trang bộ nhớ không được cấp, CPU báo lỗi trang và kernel gửi `SIGSEGV`: đó là **stack overflow**.

Quy tắc: **độ sâu đệ quy tối đa ≈ kích thước stack / kích thước khung**. Hàm có biến cục bộ lớn cạn nhanh hơn. Đó là lý do duyệt cây hay đồ thị có thể sâu hàng triệu tầng nên viết bằng vòng lặp với stack tự quản lý ([Graph](/docs/dsa/graphs)), và Python tự giới hạn đệ quy ở 1.000 tầng. Mỗi thread có stack riêng ([Process vs Thread](/docs/os/process-thread)), và stack của thread phụ thường nhỏ hơn stack của thread chính.

(Chương trình biên dịch với `-O0` có lý do: ở `-O2`, gcc nhận ra nhiều hàm đệ quy kiểu này và biến chúng thành vòng lặp, khi đó không còn khung nào để cạn.)

**Thử ngay:** nếu mảng `pad` là 1.000 byte thì độ sâu tối đa cỡ bao nhiêu?

<Expand title="Đáp án">

Khung khoảng 1.000 byte cộng vài chục byte phụ, làm tròn theo bội 16: cỡ 1.024 byte. `8 MiB / 1.024 byte ≈ 8.000` tầng. Mảng cục bộ lớn trong hàm đệ quy làm độ sâu tối đa giảm theo tỉ lệ.

</Expand>

## Gọi hàm có đắt không

Mỗi lời gọi hàm tốn `call`, có thể dựng khung, rồi `ret`. Nghe tốn kém. **Đoán trước:** một lời gọi tới hàm `x + 1` tốn bao nhiêu nano giây? Và nếu trình biên dịch được phép **inline** (chép thân hàm vào chỗ gọi) thì vòng lặp 400 triệu lần gọi còn tốn bao nhiêu?

<Expand title="Code call_cost.c">

```c
// call_cost.c: gọi một hàm rất nhỏ 400 triệu lần; bản cấm inline so với bản được inline
#include <stdio.h>
#include <time.h>

__attribute__((noinline)) long add_one_call(long x) { return x + 1; }
static inline long add_one_inline(long x) { return x + 1; }

static double now(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec * 1e-9;
}

int main(void) {
    long n = 400000000, x = 0, y = 0;
    double t0 = now();
    for (long i = 0; i < n; i++) x = add_one_call(x);
    double t1 = now();
    for (long i = 0; i < n; i++) y = add_one_inline(y);
    double t2 = now();
    printf("cấm inline : %.3f ns mỗi lần gọi (x = %ld)\n", (t1 - t0) / n * 1e9, x);
    printf("được inline: %.3f ns mỗi lần gọi (y = %ld)\n", (t2 - t1) / n * 1e9, y);
    return 0;
}
```

</Expand>

```bash
gcc -O2 -o call_cost call_cost.c && ./call_cost
```

```text
cấm inline : 0.317 ns mỗi lần gọi (x = 400000000)
được inline: 0.000 ns mỗi lần gọi (y = 400000000)
```

Một lời gọi thật chỉ tốn vài phần mười nano giây, cỡ một hai chu kỳ: CPU đoán trước rất tốt `call` và `ret` sẽ đi đâu. Bản được inline thì gần như không tốn gì, vì sau khi chép thân hàm vào vòng lặp, trình biên dịch thấy vòng lặp chỉ cộng 1 bốn trăm triệu lần và thay cả vòng bằng một phép gán `y = 400000000`.

Vậy cái đắt của lời gọi hàm **không phải** `call` và `ret`, mà là nó **chặn trình biên dịch nhìn xuyên qua**: không gộp được vòng lặp, không giữ được biến trong thanh ghi qua lời gọi, không bỏ được phép tính thừa. Trình biên dịch tự inline các hàm nhỏ nằm cùng file; với hàm ở file khác, nó cần `-flto` (tối ưu lúc liên kết).

**Hiểu lầm hay gặp ở đây:** nhiều người tự chép tay thân hàm nhỏ vào vòng lặp "để khỏi tốn lời gọi". Thật ra trình biên dịch làm việc đó tốt hơn và tự quyết khi nào đáng làm; viết hàm nhỏ rõ ràng, để chúng ở nơi trình biên dịch nhìn thấy, rồi đo.

**Thử ngay:** `add_one_call` nằm trong một thư viện `.so` liên kết động. Trình biên dịch có inline nó được không?

<Expand title="Đáp án">

Không. Lúc biên dịch chương trình, mã của hàm trong thư viện động không có mặt (nó chỉ được nạp lúc chạy), nên trình biên dịch không có thân hàm để chép. Lời gọi vào thư viện động còn đi qua một bảng nhảy trung gian (PLT), đắt hơn lời gọi thường một chút.

</Expand>

## Mỗi họ CPU một tập lệnh

x86-64 không phải ISA duy nhất. Hai họ lớn khác là ARM64 (điện thoại, Apple Silicon, nhiều máy chủ đám mây) và RISC-V (ISA mở, dùng nhiều trong chip nhúng):

| | x86-64 (Intel, AMD) | ARM64 (AArch64) | RISC-V |
|---|---|---|---|
| Kiểu | CISC: lệnh phức tạp, phép tính đọc thẳng bộ nhớ được (`add rax, [rdi]`) | RISC: chỉ lệnh `load`/`store` chạm bộ nhớ | RISC, mở, chia mô-đun |
| Độ dài lệnh | **1 tới 15 byte** | cố định 4 byte | 4 byte (2 byte với phần mở rộng nén) |
| Thanh ghi đa dụng | 16 | 31 | 32 |

Hệ quả cho người viết phần mềm: **cùng một chương trình C biên dịch ra mã máy khác hẳn cho mỗi ISA**. File thực thi x86-64 không chạy trên máy ARM64, trừ khi có lớp dịch (Rosetta 2 của Apple, QEMU). Java, Python, JavaScript chạy được khắp nơi vì phần phụ thuộc ISA nằm trong runtime (JVM, trình thông dịch), và runtime đó đã được biên dịch riêng cho từng ISA. Docker image cũng vì thế mà thường có hai bản `linux/amd64` và `linux/arm64`.

**Thử ngay:** bạn build Docker image trên MacBook chip M (ARM64) rồi chạy trên máy chủ x86-64, và nhận lỗi `exec format error`. Vì sao?

<Expand title="Đáp án">

Image chứa file thực thi biên dịch cho ARM64; CPU x86-64 không hiểu tập lệnh đó, và kernel từ chối chạy file thực thi khác kiến trúc. Sửa: build cho đúng nền tảng (`docker build --platform linux/amd64`) hoặc build image đa kiến trúc.

</Expand>

## Tự kiểm tra tổng hợp

1. Một đồng nghiệp đo hai cách viết vòng lặp trên bản `-O0`, thấy cách A nhanh hơn cách B 30%, và đề nghị đổi toàn bộ code sang cách A. Bạn trả lời thế nào?
2. Đọc đoạn assembly `-O2` sau (`rdi` là `x`) và viết lại thành C: `lea rax, [rdi+rdi*4]` rồi `ret`.
3. Hàm `long avg(long a, long b) { return (a + b) / 2; }` ở `-O2` có lệnh `shr rax, 63` rồi `add rax, rdi` trước khi `sar rax` (dịch phải số học 1 bit). Vì sao phép chia 2 không chỉ là một lệnh dịch phải?
4. Một hàm đệ quy duyệt cây chạy tốt trong test nhưng chết với `Segmentation fault` trên dữ liệu thật có cây lệch (sâu 500.000 tầng). Giải thích và nêu hai cách sửa.
5. Vì sao `clamp` ở `-O2` dùng `cmov` mà không dùng lệnh nhảy, và khi nào trình biên dịch **không** được dùng `cmov` thay cho `if`?

<Expand title="Đáp án">

1. Số đo ở `-O0` không nói gì về bản release: ở `-O0` mọi biến đi vòng qua bộ nhớ, nên cách viết nào ít đọc ghi biến hơn thì thắng, còn ở `-O2` cả hai thường được dịch ra cùng một vòng lặp. Đo lại trên `-O2` trước khi đổi gì.
2. `rax = x + x*4 = 5x`. Hàm là `long f(long x) { return x * 5; }`. Trình biên dịch dùng `lea` vì một phép cộng có hệ số rẻ hơn phép nhân `imul`.

   ```c
   // times5.c
   long times5(long x) { return x * 5; }
   ```

   ```bash
   bash asm.sh -O2 times5.c
   ```

   ```text
   times5:
   	lea	rax, [rdi+rdi*4]
   	ret
   ```

3. C quy định phép chia số nguyên **cắt về 0** (`-3 / 2 = -1`), còn dịch phải số học làm tròn **xuống** (`-3 >> 1 = -2`). Với số âm, trình biên dịch cộng thêm 1 trước khi dịch: `shr rax, 63` lấy bit dấu (1 nếu tổng âm), cộng vào tổng, rồi mới `sar`. Với số dương, bit dấu là 0 nên không đổi gì.

   ```c
   // avg.c

   ```

   ```bash
   bash asm.sh -O2 avg.c
   ```

   ```text
   avg:
   	add	rdi, rsi
   	mov	rax, rdi
   	shr	rax, 63
   	add	rax, rdi
   	sar	rax
   	ret
   ```

4. Mỗi tầng đệ quy thêm một khung; 500.000 tầng nhân kích thước khung vượt 8 MiB stack nên `rsp` chạm vùng không được cấp, kernel gửi `SIGSEGV`. Test dùng cây cân bằng (sâu `log n`) nên không thấy. Sửa: viết lại bằng vòng lặp với stack tự quản lý trên heap; hoặc chạy trong một thread có stack lớn hơn; tốt nhất là cả giữ cây cân bằng (xem [Tree](/docs/dsa/trees)).
5. Cả hai nhánh của `clamp` chỉ là chọn một trong hai giá trị đã có trong thanh ghi, tính cả hai không tốn gì và không có tác dụng phụ; bỏ lệnh nhảy thì CPU không phải đoán. Trình biên dịch không được dùng `cmov` khi tính cả hai nhánh có thể gây lỗi hay tác dụng phụ, ví dụ `if (p) x = *p;` (đọc `*p` khi `p` là NULL sẽ crash), hoặc nhánh gọi hàm, ghi bộ nhớ.

## Đi sâu hơn

<Expand title="Giải mã tay từng byte mã máy">

`gcc -c` sinh file đối tượng, `objdump -d` hiện byte mã máy cạnh lệnh:

```bash
gcc -O2 -c -fcf-protection=none -o mul_add.o mul_add.c
objdump -d -M intel mul_add.o | grep -A4 '<mul_add>:'
```

```text
0000000000000000 <mul_add>:
   0:	48 0f af fe          	imul   rdi,rsi
   4:	48 8d 04 17          	lea    rax,[rdi+rdx*1]
   8:	c3                   	ret
```

Cả hàm là 9 byte. Tách `imul rdi, rsi` (`48 0f af fe`):

- `48`: tiền tố **REX.W** (`0100 1000`), báo toán hạng 64 bit.
- `0f af`: mã lệnh `IMUL r64, r/m64`.
- `fe`: byte **ModRM** `11 111 110`: `mod = 11` (cả hai toán hạng là thanh ghi), `reg = 111` (thanh ghi số 7 là `rdi`), `r/m = 110` (thanh ghi số 6 là `rsi`).

`lea rax, [rdi+rdx*1]` (`48 8d 04 17`): `8d` là `LEA`; ModRM `04` = `00 000 100` (`reg = rax`, `r/m = 100` nghĩa là có byte SIB theo sau); SIB `17` = `00 010 111` (hệ số `2^0 = 1`, chỉ số `010 = rdx`, cơ sở `111 = rdi`). `ret` là một byte `c3`.

Lệnh x86 dài từ 1 tới 15 byte, nên không biết lệnh thứ hai bắt đầu ở đâu nếu chưa giải mã lệnh thứ nhất. CPU x86 hiện đại vì vậy có khối giải mã phức tạp và dịch mỗi lệnh thành các **vi lệnh** (micro-ops) độ dài cố định bên trong. ARM64 và RISC-V có lệnh 4 byte nên giải mã song song nhiều lệnh dễ hơn.

</Expand>

<Expand title="Tràn bộ đệm trên stack và các lớp phòng thủ">

Địa chỉ trả về nằm trên stack, ngay cạnh biến cục bộ. Nếu chương trình chép dữ liệu vượt quá một mảng cục bộ (`strcpy` vào mảng 16 byte một chuỗi 100 byte), nó ghi đè lên địa chỉ trả về, và `ret` sẽ nhảy tới nơi kẻ tấn công chọn. Đó là lỗ hổng **stack buffer overflow**, kinh điển từ bài viết của Aleph One (1996). Ba lớp phòng thủ hiện có mặc định trên Linux:

- **Stack canary** (`-fstack-protector-strong`): một giá trị bí mật đặt giữa biến cục bộ và địa chỉ trả về, được kiểm tra ngay trước `ret`; bị ghi đè thì chương trình dừng.
- **NX** (không thực thi): vùng stack được đánh dấu không chạy mã, nên mã chèn vào stack không chạy được.
- **ASLR**: địa chỉ của stack, heap, thư viện ngẫu nhiên mỗi lần chạy (thấy ở `&pad` khác nhau giữa các lần chạy `stack_depth`), nên khó biết nhảy tới đâu.

Kẻ tấn công vẫn có kỹ thuật vượt qua (return-oriented programming); cách chữa tận gốc là ngôn ngữ kiểm tra biên mảng (Rust, Go, Java).

</Expand>

<Expand title="System call và các quy ước khác">

- **System call** trên Linux x86-64: số hiệu syscall trong `rax`, đối số trong `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9` (`r10` thay `rcx`, vì lệnh `syscall` ghi đè `rcx`), rồi lệnh `syscall` chuyển sang kernel mode (xem [Process vs Thread](/docs/os/process-thread)).
- **Windows x64**: 4 đối số đầu trong `rcx`, `rdx`, `r8`, `r9`, và hàm gọi phải chừa 32 byte "shadow space" trên stack.
- **Callee-saved**: nếu hàm được gọi muốn dùng `rbx` hay `r12`, nó phải `push` giá trị cũ lúc vào và `pop` lại lúc ra; đó là các cặp `push`/`pop` bạn thấy ở đầu và cuối nhiều hàm.
- **Căn lề stack**: ngay trước `call`, `rsp` phải chia hết cho 16, để các lệnh SIMD đọc ghi biến 16 byte trên stack đúng căn lề.

</Expand>

<Expand title="-O3 và vector hoá">

`-O3` bật thêm vector hoá mạnh hơn: dùng lệnh SIMD (thanh ghi `xmm` 16 byte, `ymm` 32 byte) để cộng nhiều phần tử trong một lệnh. Cùng `sum_cost.c`:

```bash
gcc -O3 -o sum_cost sum_cost.c && ./sum_cost
```

```text
0.117 ns mỗi phần tử (tổng kiểm tra 5734400000)
```

Trong assembly `-O3` sẽ thấy `paddq xmm0, ...` (cộng hai số 64 bit một lúc). Vector hoá có hiệu quả khi vòng lặp đơn giản, không có phụ thuộc giữa các vòng, và dữ liệu liền khối; cộng số thực thì trình biên dịch chỉ vector hoá khi được phép đổi thứ tự cộng (`-ffast-math`), vì phép cộng số thực không có tính kết hợp ([Data Representation](/docs/architecture/data-representation)).

</Expand>

<Expand title="Công cụ đọc assembly">

- `gcc -S -masm=intel -O2 file.c` ra file `.s`; `objdump -d -M intel` cho mã máy cạnh lệnh; trong `gdb`, `disassemble` và `x/10i $pc` xem lệnh đang chạy.
- **Compiler Explorer** (godbolt.org): gõ C, C++, Rust, Go và thấy assembly ngay, tô màu dòng nguồn tương ứng; cách nhanh nhất để thử "trình biên dịch làm gì với đoạn này".
- `perf annotate` gắn số lần lấy mẫu vào từng lệnh, chỉ ra lệnh nào nóng.
- Ngôn ngữ khác: Go `go build -gcflags=-S`; Rust `cargo rustc --release -- --emit asm`; Java `-XX:+PrintAssembly` (cần hsdis).

</Expand>

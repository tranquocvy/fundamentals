**Cần biết trước:** Big-O và hằng số ẩn ở bài [Big-O & Complexity](/docs/dsa/complexity); hàm băm ở bài [Hash Table](/docs/dsa/hash-tables). Cách số và ký tự được biểu diễn bằng bit nằm ở bài [Data Representation](/docs/architecture/data-representation).

**Cách đọc bài:** mỗi mục có một câu **Đoán trước** và kết bằng một câu **Thử ngay**. Hãy tự trả lời trong đầu (hoặc ra giấy) rồi mới xem đáp án. Việc tự nhớ lại và tự đoán giúp nhớ lâu hơn nhiều so với chỉ đọc.

## Ý chính

Chuỗi trông như một mảng ký tự, nhưng "ký tự" có ba nghĩa: **byte** sau khi mã hoá, **code point** trong bảng Unicode, và thứ người đọc nhìn thấy là một ký tự. Tiếng Việt có hai cách viết cùng một chữ (dựng sẵn và tách dấu), nhìn y hệt nhưng khác byte, nên so sánh, băm và tìm kiếm đều thất bại nếu không **chuẩn hoá** trước.

Thao tác điển hình trên chuỗi là **tìm** một mẫu trong văn bản. Cách ngây thơ thường nhanh, nhưng có đầu vào làm nó tốn `n × m` bước; KMP bảo đảm tuyến tính trong mọi trường hợp. Regex còn nguy hiểm hơn: engine kiểu backtracking (Python `re`, Java, JavaScript) có thể chậm theo **hàm mũ** với một chuỗi đầu vào chỉ vài chục ký tự, đủ làm sập cả một dịch vụ.

## Byte, code point và ký tự nhìn thấy

**Unicode** gán cho mỗi ký tự một số gọi là **code point**, viết `U+1EC7`. **UTF-8** là cách mã hoá code point thành byte: ký tự ASCII 1 byte, chữ có dấu tiếng Việt 2 tới 3 byte, emoji 4 byte. `len()` của Python đếm code point.

Tiếng Việt có hai cách viết chữ `ệ`: một code point **dựng sẵn**, hoặc chữ `e` cộng hai **dấu kết hợp** (dấu chấm dưới, dấu mũ). Unicode gọi hai dạng là **NFC** (dựng sẵn) và **NFD** (tách dấu).

**Đoán trước:** chữ "Việt" viết theo NFC và theo NFD. Hai chuỗi có bằng nhau (`==`) không? `len` của mỗi chuỗi là bao nhiêu?

```python
import unicodedata as ud

nfc = ud.normalize("NFC", "Việt")
nfd = ud.normalize("NFD", "Việt")
print(f"NFC: len = {len(nfc)}, UTF-8 = {len(nfc.encode())} byte")
print(f"NFD: len = {len(nfd)}, UTF-8 = {len(nfd.encode())} byte")
print("nfc == nfd:", nfc == nfd)
print("ệ dựng sẵn:", [f"U+{ord(c):04X} {ud.name(c)}" for c in ud.normalize("NFC", "ệ")])
print("ệ tách dấu:", [f"U+{ord(c):04X} {ud.name(c)}" for c in ud.normalize("NFD", "ệ")])
```

```text
NFC: len = 4, UTF-8 = 6 byte
NFD: len = 6, UTF-8 = 8 byte
nfc == nfd: False
ệ dựng sẵn: ['U+1EC7 LATIN SMALL LETTER E WITH CIRCUMFLEX AND DOT BELOW']
ệ tách dấu: ['U+0065 LATIN SMALL LETTER E', 'U+0323 COMBINING DOT BELOW', 'U+0302 COMBINING CIRCUMFLEX ACCENT']
```

Trên màn hình hai chuỗi giống hệt, nhưng chúng là hai dãy code point khác nhau nên `==` trả về `False`. Dữ liệu thật trộn cả hai dạng: bàn phím trên Windows thường gõ ra NFC, macOS lưu tên file dạng tách dấu, copy từ PDF có thể ra bất kỳ dạng nào.

Còn một tầng nữa: thứ người đọc thấy là **một** ký tự có thể gồm nhiều code point.

```python
samples = {"Hanoi": "Hanoi", "Hà Nội (NFC)": "Hà Nội", "Hà Nội (NFD)": ud.normalize("NFD", "Hà Nội"),
           "cờ Việt Nam": "\U0001F1FB\U0001F1F3", "emoji gia đình": "\U0001F468‍\U0001F469‍\U0001F467"}
for label, s in samples.items():
    print(f"{label:<15} code point = {len(s):>2}, UTF-8 = {len(s.encode()):>2} byte")
```

```text
Hanoi           code point =  5, UTF-8 =  5 byte
Hà Nội (NFC)    code point =  6, UTF-8 =  9 byte
Hà Nội (NFD)    code point =  9, UTF-8 = 12 byte
cờ Việt Nam     code point =  2, UTF-8 =  8 byte
emoji gia đình  code point =  5, UTF-8 = 18 byte
```

Cờ Việt Nam là hai code point (hai "ký hiệu vùng" V và N). Emoji gia đình là ba emoji nối bằng hai ký tự nối vô hình, năm code point, 18 byte, nhưng người dùng thấy một ký tự. Unicode gọi đơn vị "một ký tự nhìn thấy" là **grapheme cluster**.

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ `len(s)` là số ký tự. Thật ra nó là số code point; số byte thì phải `len(s.encode())`; còn số ký tự nhìn thấy cần thư viện riêng (thư viện chuẩn Python không đếm được). Giới hạn "tên tối đa 20 ký tự" phải nói rõ đơn vị: cột database thường giới hạn byte hoặc code point, người dùng thì nghĩ theo ký tự nhìn thấy.

**Thử ngay:** chuỗi `"Nội"` ở dạng NFD có bao nhiêu code point?

<Expand title="Đáp án">

5: `N`, `o`, dấu chấm dưới, dấu mũ, `i`. Chữ `ộ` tách thành `o` cộng hai dấu kết hợp. Ở dạng NFC thì 3.

</Expand>

## Chuẩn hoá trước khi so sánh

Vì hai dạng khác nhau từng code point, mọi thao tác dựa trên so sánh hay băm đều bị ảnh hưởng.

**Đoán trước:** dict có khoá "Việt" dạng NFC. Tra bằng "Việt" dạng NFD thì thấy không?

```python
d = {nfc: "có"}
print("tra NFD trong dict khoá NFC:", d.get(nfd, "không thấy"))
print("tra sau khi chuẩn hoá NFC  :", d.get(ud.normalize("NFC", nfd), "không thấy"))
print("cắt 3 code point đầu: NFC", repr(nfc[:3]), "| NFD", repr(nfd[:3]))

words = ["Đà Nẵng", "Hà Nội", "An Giang", "Cần Thơ", "Huế"]
print("sorted():", sorted(words))
print("lower(): ", "STRASSE".lower() == "straße".lower(), "| casefold():", "STRASSE".casefold() == "straße".casefold())
```

```text
tra NFD trong dict khoá NFC: không thấy
tra sau khi chuẩn hoá NFC  : có
cắt 3 code point đầu: NFC 'Việ' | NFD 'Vie'
sorted(): ['An Giang', 'Cần Thơ', 'Huế', 'Hà Nội', 'Đà Nẵng']
lower():  False | casefold(): True
```

Ba lỗi từ cùng một gốc:

- **Tra cứu thất bại**: hash khác nhau vì code point khác nhau. Sau khi chuẩn hoá về NFC thì tìm thấy.
- **Cắt chuỗi hỏng chữ**: 3 code point đầu của NFD là `Vie`, mất dấu của `ệ`.
- **Sắp xếp sai**: `sorted()` so theo code point, nên `Huế` đứng trước `Hà Nội` (`u` là `U+0075`, nhỏ hơn `à` là `U+00E0`), và `Đ` (`U+0110`) đứng sau cả bảng chữ cái. Thứ tự đúng theo tiếng Việt cần **collation** theo ngôn ngữ (thư viện ICU, hoặc `COLLATE` trong PostgreSQL).

Quy tắc: **chuẩn hoá về NFC ngay khi dữ liệu vào hệ thống**, trước khi so sánh, băm, lưu hay đánh chỉ mục. So sánh không phân biệt hoa thường thì dùng `casefold()`, không dùng `lower()`: chữ `ß` của tiếng Đức viết hoa thành `SS`, và chỉ `casefold` xử lý đúng.

**Thử ngay:** người dùng gõ "Nguyễn" vào ô tìm kiếm, nhưng database trả về không có, dù bản ghi "Nguyễn" hiện rõ trên màn hình quản trị. Bản ghi được nhập từ một máy Mac. Nghi ngờ đầu tiên là gì, và kiểm tra thế nào?

<Expand title="Đáp án">

Hai bên khác dạng chuẩn hoá: bản ghi có thể ở NFD, từ khoá ở NFC. Kiểm tra bằng cách in code point của cả hai (`[hex(ord(c)) for c in s]`) hoặc so `len`. Sửa: chuẩn hoá NFC khi ghi vào database và khi nhận từ khoá, rồi chuẩn hoá lại dữ liệu cũ.

</Expand>

## Tìm chuỗi con: cách ngây thơ và trường hợp xấu

Bài toán: tìm mọi vị trí mẫu `P` (dài `m`) xuất hiện trong văn bản `T` (dài `n`). Cách ngây thơ: thử từng vị trí, so từng ký tự, lệch thì dịch mẫu một bước và so lại từ đầu mẫu.

```python
import random, time

def naive(t, p):
    cmp, res = 0, []
    for i in range(len(t) - len(p) + 1):
        j = 0
        while j < len(p):
            cmp += 1
            if t[i + j] != p[j]: break
            j += 1
        if j == len(p): res.append(i)
    return res, cmp
```

**Đoán trước:** văn bản 200.000 ký tự. Với văn bản ngẫu nhiên và mẫu 8 ký tự, cách ngây thơ tốn bao nhiêu lần so sánh? Với văn bản toàn chữ `a` và mẫu là 99 chữ `a` rồi một chữ `b` thì sao?

```python
random.seed(1)
text = "".join(random.choices("abcdefghijklmnopqrstuvwxyz", k=200_000))
pat = text[123_456:123_464]
print(f"ngẫu nhiên, mẫu 8 ký tự     : {naive(text, pat)[1]:>12,} lần so sánh")
bad_t, bad_p = "a" * 200_000, "a" * 99 + "b"
print(f"'aaa...a', mẫu 'a'*99 + 'b' : {naive(bad_t, bad_p)[1]:>12,} lần so sánh")
```

```text
ngẫu nhiên, mẫu 8 ký tự     :      208,092 lần so sánh
'aaa...a', mẫu 'a'*99 + 'b' :   19,990,100 lần so sánh
```

Với văn bản ngẫu nhiên, hầu hết vị trí lệch ngay ký tự đầu, nên chỉ khoảng `n` lần so sánh. Với văn bản toàn `a`, mỗi vị trí khớp 99 ký tự rồi mới lệch ở `b`, và cách ngây thơ vứt bỏ hết những gì đã khớp để bắt đầu lại ở vị trí kế tiếp: khoảng `n × m` lần so sánh, gần 20 triệu. Trường hợp này không hiếm: log lặp lại, chuỗi DNA, dữ liệu do người dùng gửi lên.

**Thử ngay:** văn bản là `"abababab...ab"` (100.000 ký tự) và mẫu là `"ababababc"`. Cách ngây thơ tốn cỡ `n` hay cỡ `n × m`?

<Expand title="Đáp án">

Cỡ `n × m`. Ở mỗi vị trí chẵn, mẫu khớp 8 ký tự `abababab` rồi lệch ở `c`. Phần đã khớp chứa đầy thông tin (nó có dạng lặp lại), nhưng cách ngây thơ không dùng.

</Expand>

## KMP: không bao giờ lùi trên văn bản

**KMP** (Knuth-Morris-Pratt) dùng chính phần đã khớp. Khi đã khớp `k` ký tự đầu của mẫu rồi lệch, nó hỏi: trong `k` ký tự vừa khớp, **đoạn đầu dài nhất cũng là đoạn cuối** là bao nhiêu? Đoạn đó đã khớp sẵn với văn bản, nên mẫu chỉ cần lùi về đó, còn con trỏ trên văn bản không lùi. Độ dài này được tính trước cho mọi vị trí của mẫu, gọi là **bảng thất bại** `f`: `f[i]` là độ dài đoạn đầu dài nhất của `p[0..i]` đồng thời là đoạn cuối của nó (không tính chính nó).

```python
def failure(p):
    f, k = [0] * len(p), 0
    for i in range(1, len(p)):
        while k and p[i] != p[k]: k = f[k - 1]      # đoạn đầu không nối dài được: lùi về đoạn ngắn hơn
        if p[i] == p[k]: k += 1
        f[i] = k
    return f

def kmp(t, p):
    f, cmp, res, k = failure(p), 0, [], 0           # k: số ký tự của mẫu đang khớp
    for i, c in enumerate(t):                       # mỗi ký tự văn bản đọc đúng một lần
        while True:
            cmp += 1
            if c == p[k]: k += 1; break
            if k == 0: break
            k = f[k - 1]                            # lùi trong mẫu, không lùi trên văn bản
        if k == len(p):                             # khớp trọn mẫu, kết thúc ở vị trí i
            res.append(i - k + 1); k = f[k - 1]
    return res, cmp
```

### Tính bảng thất bại: ba ví dụ

#### Ví dụ 1 (giải sẵn): mẫu `ABABCABAB`

Ở mỗi vị trí `i`, nhìn đoạn `p[0..i]` và tìm đoạn đầu dài nhất cũng là đoạn cuối:

1. `A`: không có đoạn đầu thật sự nào, `f[0] = 0`.
2. `AB`: đoạn đầu `A`, đoạn cuối `B`, không khớp: `f[1] = 0`.
3. `ABA`: `A` vừa là đầu vừa là cuối: `f[2] = 1`.
4. `ABAB`: `AB` vừa là đầu vừa là cuối: `f[3] = 2`.
5. `ABABC`: không đoạn đầu nào kết thúc bằng `C`: `f[4] = 0`.
6. `ABABCA`, `ABABCAB`, `ABABCABA`, `ABABCABAB`: `A`, `AB`, `ABA`, `ABAB`, nên `1, 2, 3, 4`.

```python
p = "ABABCABAB"
print("ký tự:", "  ".join(p))
print("f[i] :", "  ".join(str(x) for x in failure(p)))
```

```text
ký tự: A  B  A  B  C  A  B  A  B
f[i] : 0  0  1  2  0  1  2  3  4
```

Nếu đã khớp 8 ký tự `ABABCABA` rồi lệch ở ký tự thứ 9, KMP lùi mẫu về `f[7] = 3`: ba ký tự `ABA` cuối cùng của phần vừa khớp chính là ba ký tự đầu của mẫu, nên không cần so lại.

#### Ví dụ 2 (giải một nửa): mẫu `AABAAA`

Điền vào chỗ trống:

1. `f[0] = 0`; `AA`: `A` vừa đầu vừa cuối, `f[1] = 1`.
2. `AAB`: không đoạn đầu nào kết thúc bằng `B`, `f[2] = 0`.
3. `AABA`: `f[3] =` ___.
4. `AABAA`: `f[4] =` ___.
5. `AABAAA`: đoạn `AAB` không phải đoạn cuối; đoạn đầu dài nhất cũng là đoạn cuối là ___, nên `f[5] =` ___.

<Expand title="Đáp án">

3. `1` (`A`).
4. `2` (`AA`).
5. `AA`, nên `f[5] = 2`. Đây là chỗ vòng `while` trong `failure` lùi: đoạn `AA` đang có không nối thành `AAB` được (ký tự kế là `A`, không phải `B`), nên lùi về `f[1] = 1` rồi nối thành `AA`.

```python
print(failure("AABAAA"))
```

```text
[0, 1, 0, 1, 2, 2]
```

</Expand>

#### Ví dụ 3 (tự làm): mẫu `ABCABD`

Tính bảng thất bại. Nếu đã khớp `ABCAB` rồi lệch ở ký tự thứ 6, KMP lùi mẫu về đâu?

<Expand title="Đáp án">

`f = [0, 0, 0, 1, 2, 0]`. Đã khớp `ABCAB` (5 ký tự) thì lùi về `f[4] = 2`: hai ký tự `AB` cuối của phần đã khớp là đầu mẫu, nên tiếp tục so ký tự thứ 3 của mẫu (`C`) với ký tự hiện tại của văn bản.

```python
print(failure("ABCABD"))
```

```text
[0, 0, 0, 1, 2, 0]
```

</Expand>

### So sánh trên ba loại dữ liệu

Hai thuật toán khác đáng biết:

- **Horspool** (bản đơn giản của Boyer-Moore) so từ **cuối** mẫu; khi lệch, nhìn ký tự cuối của cửa sổ văn bản và **nhảy** xa nhất có thể, có khi cả độ dài mẫu. Nó bỏ qua phần lớn văn bản.
- **Rabin-Karp** so **hash** của cửa sổ văn bản với hash của mẫu, và tính hash của cửa sổ kế tiếp từ cửa sổ trước trong `O(1)` (**rolling hash**). Hash trùng mới so thật.

Code dưới cài Horspool rồi chạy naive, KMP và Horspool trên ba loại dữ liệu, đếm số lần so sánh ký tự, kèm thời gian của `str.find` có sẵn.

**Đoán trước:** trên văn bản ngẫu nhiên, thuật toán nào tốn ít so sánh nhất? Trên trường hợp xấu, KMP tốn cỡ bao nhiêu?

<Expand title="Code Horspool và phép đo">

```python
def horspool(t, p):
    m, cmp, res = len(p), 0, []
    shift = {p[i]: m - 1 - i for i in range(m - 1)}  # ký tự này cách cuối mẫu bao xa
    i = 0
    while i <= len(t) - m:
        j = m - 1
        while j >= 0:
            cmp += 1
            if t[i + j] != p[j]: break
            j -= 1
        if j < 0: res.append(i)
        i += shift.get(t[i + m - 1], m)             # ký tự không có trong mẫu: nhảy cả độ dài mẫu
    return res, cmp

random.seed(1)
cases = {
    "văn bản ngẫu nhiên, mẫu 8":  (text, pat),
    "DNA (ACGT), mẫu 12":         ("".join(random.choices("ACGT", k=200_000)), None),
    "'aaa...a', mẫu 'a'*99+'b'":  (bad_t, bad_p),
}
def find_all(t, p):                                 # mọi vị trí, bằng str.find có sẵn
    out, i = [], t.find(p)
    while i != -1: out.append(i); i = t.find(p, i + 1)
    return out

def best_ms(fn, *args):
    times = []
    for _ in range(3):
        t0 = time.perf_counter(); fn(*args); times.append(time.perf_counter() - t0)
    return min(times) * 1000

print(f"{'':<28}{'naive':>12}{'KMP':>11}{'Horspool':>10} | {'KMP (ms)':>9}{'str.find (ms)':>14}")
for name, (t, p) in cases.items():
    if p is None: p = t[50_000:50_012]
    (r1, c1), (r2, c2), (r3, c3) = naive(t, p), kmp(t, p), horspool(t, p)
    assert r1 == r2 == r3 == find_all(t, p)         # mọi cách cho cùng các vị trí
    print(f"{name:<28}{c1:>12,}{c2:>11,}{c3:>10,} | {best_ms(kmp, t, p):>9.1f}{best_ms(find_all, t, p):>14.2f}")
```

</Expand>

- Văn bản ngẫu nhiên: naive và KMP đều quanh `n`. Horspool ít hơn nhiều lần, vì phần lớn ký tự cuối cửa sổ không có trong mẫu nên nó nhảy cả 8 ô.
- DNA chỉ có 4 chữ cái: mỗi ký tự đều có trong mẫu, nên Horspool nhảy ngắn hơn, nhưng vẫn thắng.
- Trường hợp xấu: naive gần 20 triệu, KMP chỉ khoảng `2n`. KMP bảo đảm `O(n + m)` với **mọi** đầu vào: mỗi bước hoặc tiến trên văn bản, hoặc lùi trong mẫu, và tổng số lần lùi không vượt số lần tiến.

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ tự cài KMP hay Horspool sẽ nhanh hơn `str.find`. Thật ra `str.find` chạy bằng C với thuật toán tinh chỉnh (CPython kết hợp ý tưởng kiểu Horspool với thuật toán Two-Way), và nhanh hơn KMP tự cài bằng Python từ khoảng 75 tới hơn 250 lần, như hai cột cuối cho thấy. Hiểu thuật toán để biết **vì sao** nó nhanh và khi nào nó có thể chậm; còn trong code thật, dùng hàm của thư viện.

**Thử ngay:** vì sao Horspool nhảy xa hơn khi mẫu dài và bảng chữ cái lớn?

<Expand title="Đáp án">

Bước nhảy tối đa bằng độ dài mẫu, và xảy ra khi ký tự cuối cửa sổ không có trong mẫu. Mẫu dài thì nhảy được xa; bảng chữ cái lớn thì xác suất một ký tự ngẫu nhiên không có trong mẫu cao. Với DNA (4 chữ cái), hầu như mọi ký tự đều có trong mẫu, nên bước nhảy ngắn.

</Expand>

## Regex: cùng cú pháp, hai thuật toán

Regex mô tả một tập chuỗi. Có hai cách kiểm tra một chuỗi có khớp không:

- **Backtracking** (Python `re`, Java, JavaScript, PCRE): đi theo regex như một chương trình; gặp lựa chọn (`|`, `*`, `+`) thì thử một nhánh, thất bại thì **quay lui** thử nhánh khác. Hỗ trợ nhiều tính năng (tham chiếu ngược `\1`, lookahead), nhưng số nhánh có thể bùng nổ.
- **Automat hữu hạn** (Thompson NFA, 1968; dùng trong RE2, Rust `regex`, Go `regexp`, `grep`): giữ **tập mọi trạng thái** có thể đang ở, mỗi ký tự văn bản cập nhật cả tập một lần, không bao giờ quay lui. Luôn tuyến tính theo độ dài văn bản, đổi lại không hỗ trợ tham chiếu ngược.

**Đoán trước:** regex `(a+)+b` trên chuỗi `n` chữ `a` (không có `b`, nên không bao giờ khớp). Khi `n` thêm 2, thời gian của `re` tăng bao nhiêu lần?

```python
import re
prev = None
for n in (16, 18, 20, 22, 24, 26):
    t0 = time.perf_counter(); re.match(r"(a+)+b", "a" * n); dt = time.perf_counter() - t0
    print(f"n={n}: {dt * 1000:8.1f} ms" + (f"   (x{dt / prev:.1f} so với n-2)" if prev else ""))
    prev = dt
t0 = time.perf_counter(); re.match(r"a+b", "a" * 100_000); dt = time.perf_counter() - t0
print(f"a+b trên 100.000 chữ a: {dt * 1000:.1f} ms")
```

```text
n=16:      5.2 ms
n=18:     15.8 ms   (x3.0 so với n-2)
n=20:     80.3 ms   (x5.1 so với n-2)
n=22:    333.5 ms   (x4.2 so với n-2)
n=24:   1169.3 ms   (x3.5 so với n-2)
n=26:   4583.3 ms   (x3.9 so với n-2)
a+b trên 100.000 chữ a: 0.2 ms
```

Mỗi khi thêm 2 ký tự, thời gian nhân khoảng 4: thời gian **gấp đôi với mỗi ký tự**, tăng theo hàm mũ. Lý do: `(a+)+` có thể chia `n` chữ `a` thành các nhóm theo `2^(n-1)` cách, và vì không có `b` để khớp, backtracking thử hết mọi cách chia rồi mới chịu thua. Cùng đường cong đó, 40 chữ `a` sẽ mất hàng giờ. Regex tương đương không có lặp lồng nhau, `a+b`, xử lý 100.000 chữ `a` trong tích tắc.

Đây là **ReDoS** (regular expression denial of service): kẻ tấn công không cần gửi nhiều dữ liệu, chỉ cần một chuỗi ngắn được chọn đúng. Năm 2016 Stack Overflow ngừng hoạt động vì một regex xử lý khoảng trắng gặp một bài đăng có hàng nghìn khoảng trắng; năm 2019 Cloudflare làm CPU toàn mạng lưới lên 100% vì một quy tắc tường lửa có regex kiểu này.

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ regex luôn chạy tuyến tính theo độ dài chuỗi. Thật ra chỉ engine kiểu automat (RE2, Rust, Go) mới bảo đảm điều đó. Với engine backtracking, tránh lặp lồng nhau (`(a+)+`, `(a|aa)+`, `(.*)*`), giới hạn độ dài đầu vào, và dùng engine tuyến tính cho dữ liệu không tin cậy.

**Thử ngay:** regex `^(\w+\s?)*$` dùng để kiểm tra "chuỗi gồm các từ cách nhau bởi khoảng trắng". Vì sao nó có thể bị ReDoS, và viết lại thế nào?

<Expand title="Đáp án">

`(\w+\s?)*` là lặp lồng nhau, và vì `\s?` có thể rỗng, một từ dài có thể chia thành nhiều lần `\w+` theo hàm mũ cách. Với một chuỗi dài toàn chữ kết thúc bằng một ký tự không hợp lệ (như `!`), backtracking thử mọi cách chia. Viết lại sao cho mỗi vị trí chỉ có một cách khớp: `^\w+(\s\w+)*$`, khoảng trắng bắt buộc giữa các từ.

</Expand>

## Tự kiểm tra tổng hợp

Các câu dưới trộn kiến thức của nhiều mục, nên khó hơn câu "Thử ngay". Nếu vướng, quay lại mục tương ứng.

1. Một trường "tên hiển thị" giới hạn 20 ký tự. Người dùng nhập 10 emoji gia đình và bị báo quá dài. Hệ thống đang đếm theo đơn vị nào, và nên đếm theo gì?
2. Một hệ thống loại bỏ file trùng bằng cách so sánh tên file. Hai file tên `Báo cáo.docx`, một tạo trên Windows, một trên macOS, bị coi là khác nhau. Vì sao, và nên sửa ở đâu?
3. Bạn tìm một mẫu 1.000 ký tự trong log 1 GB gồm các dòng gần như giống hệt nhau. Có nên lo về cách ngây thơ không? Nếu dùng `str.find` thì sao?
4. API nhận một trường email và kiểm tra bằng regex phức tạp lấy từ Internet, chạy trên Python `re`. Có rủi ro gì? Đề xuất hai cách giảm rủi ro.
5. `sorted(names)` cho danh sách tên tiếng Việt xếp "Đức" sau "Yến". Vì sao, và có nên tự viết hàm so sánh không?

<Expand title="Đáp án">

1. Mỗi emoji gia đình là 5 code point, 18 byte. 10 emoji là 50 code point hay 180 byte, vượt 20 theo cả hai đơn vị. Giới hạn hiển thị nên đếm theo grapheme cluster (10 ký tự nhìn thấy); giới hạn lưu trữ thì đếm byte, và nói rõ cho người dùng.
2. macOS lưu tên file dạng tách dấu (gần NFD), Windows dùng dạng dựng sẵn (NFC). Cùng tên nhìn thấy nhưng khác code point. Chuẩn hoá tên về NFC ngay khi đọc vào, trước khi so sánh hay băm.
3. Có: các dòng gần giống nhau đúng là trường hợp mẫu khớp gần hết rồi mới lệch, cách ngây thơ tiến tới `n × m` (`10^12` lần so sánh). `str.find` của CPython dùng thuật toán Two-Way cho mẫu dài, bảo đảm tuyến tính, nên an toàn.
4. Regex phức tạp với lặp lồng nhau có thể bị ReDoS: một chuỗi vài chục ký tự giữ một luồng CPU hàng giây tới hàng giờ. Giảm rủi ro: giới hạn độ dài trường trước khi chạy regex; dùng regex đơn giản không lặp lồng nhau (hoặc thư viện kiểm tra email chuyên dụng); hoặc dùng engine tuyến tính như RE2.
5. `sorted()` so theo code point: `Đ` là `U+0110`, lớn hơn mọi chữ Latin không dấu kể cả `Y`. Không nên tự viết: thứ tự chữ cái tiếng Việt (dấu, chữ `đ`, `ơ`, `ư`) có nhiều quy tắc. Dùng collation có sẵn: ICU (`PyICU`), hoặc `COLLATE` của database.

</Expand>

## Đi sâu hơn

Các phần dưới không cần để đọc tiếp chặng DSA.

<Expand title="Tự dựng một regex engine kiểu Thompson NFA">

Bộ dựng dưới hỗ trợ ký tự, `.`, `|`, `*`, `+`, `?` và ngoặc. Nó biến regex thành một automat với các trạng thái `char` (đọc một ký tự) và `split` (rẽ hai nhánh không đọc gì), rồi chạy bằng cách giữ **tập** trạng thái đang sống.

```python
class Frag:
    def __init__(self, start, outs): self.start, self.outs = start, outs

class NFA:
    def __init__(self): self.t = []                 # ('char', c, next) | ('split', a, b) | ('match',)
    def add(self, s): self.t.append(list(s)); return len(self.t) - 1
    def patch(self, outs, target):
        for st, slot in outs: self.t[st][slot] = target

def compile_regex(pat):
    nfa, pos = NFA(), [0]
    def peek(): return pat[pos[0]] if pos[0] < len(pat) else None
    def eat(): c = pat[pos[0]]; pos[0] += 1; return c
    def alt():
        f = seq()
        while peek() == "|":
            eat(); g = seq(); s = nfa.add(("split", f.start, g.start)); f = Frag(s, f.outs + g.outs)
        return f
    def seq():
        frags = []
        while peek() not in (None, "|", ")"): frags.append(rep())
        f = frags[0]
        for g in frags[1:]: nfa.patch(f.outs, g.start); f = Frag(f.start, g.outs)
        return f
    def rep():
        f = atom()
        while peek() in ("*", "+", "?"):
            op = eat(); s = nfa.add(("split", f.start, None))
            if op == "*": nfa.patch(f.outs, s); f = Frag(s, [(s, 2)])
            elif op == "+": nfa.patch(f.outs, s); f = Frag(f.start, [(s, 2)])
            else: f = Frag(s, f.outs + [(s, 2)])
        return f
    def atom():
        c = eat()
        if c == "(": f = alt(); eat(); return f
        s = nfa.add(("char", c, None)); return Frag(s, [(s, 2)])
    f = alt(); m = nfa.add(("match",)); nfa.patch(f.outs, m)
    return nfa, f.start

def nfa_match(nfa, start, text):
    def closure(states):                            # mọi trạng thái tới được không cần đọc ký tự
        seen, stack = set(), list(states)
        while stack:
            s = stack.pop()
            if s in seen: continue
            seen.add(s)
            if nfa.t[s][0] == "split": stack += [x for x in nfa.t[s][1:3] if x is not None]
        return seen
    cur = closure([start])
    for ch in text:
        cur = closure([nfa.t[i][2] for i in cur if nfa.t[i][0] == "char" and nfa.t[i][1] in (ch, ".")])
        if not cur: return False
    return any(nfa.t[i][0] == "match" for i in cur)

for pat, tests in (("(a|b)*abb", ["abb", "aabb", "ab", "abba"]), ("a(b|c)*d", ["ad", "abcbd", "abx"]), ("h.llo", ["hello", "hllo"])):
    c, s = compile_regex(pat)
    assert all(nfa_match(c, s, w) == bool(re.fullmatch(pat, w)) for w in tests)
c, s = compile_regex("(a+)+b")
for n in (26, 1000, 100_000):
    t0 = time.perf_counter(); ok = nfa_match(c, s, "a" * n)
    print(f"NFA, (a+)+b trên {n:>7,} chữ a: {ok}, {(time.perf_counter() - t0) * 1000:7.2f} ms")
```

```text
NFA, (a+)+b trên      26 chữ a: False,    0.05 ms
NFA, (a+)+b trên   1,000 chữ a: False,    1.46 ms
NFA, (a+)+b trên 100,000 chữ a: False,  164.16 ms
```

Cùng regex làm `re` mất vài giây ở `n = 26`, automat xử lý 100.000 ký tự tuyến tính. Russ Cox, "Regular Expression Matching Can Be Simple And Fast", giải thích chi tiết.

</Expand>

<Expand title="Suffix array: một văn bản, rất nhiều truy vấn">

Khi văn bản cố định và có rất nhiều truy vấn (bộ gen, kho mã nguồn), ta xây chỉ mục một lần. **Suffix array** là danh sách vị trí bắt đầu của mọi hậu tố, sắp theo thứ tự từ điển. Mọi hậu tố bắt đầu bằng mẫu `P` nằm liền nhau trong mảng, nên tìm bằng tìm nhị phân trong `O(m log n)`, không quét lại văn bản.

```python
import bisect

def suffix_array(s):                                # nhân đôi tiền tố: xếp theo 1, 2, 4, ... ký tự đầu
    n, sa, rank, k = len(s), list(range(len(s))), [ord(c) for c in s], 1
    while True:
        key = lambda i: (rank[i], rank[i + k] if i + k < n else -1)
        sa.sort(key=key)
        new = [0] * n
        for a in range(1, n): new[sa[a]] = new[sa[a - 1]] + (key(sa[a]) != key(sa[a - 1]))
        rank = new
        if rank[sa[-1]] == n - 1: return sa
        k *= 2

def sa_search(s, sa, p):
    lo = bisect.bisect_left(sa, p, key=lambda i: s[i:i + len(p)])
    hi = bisect.bisect_right(sa, p, key=lambda i: s[i:i + len(p)])
    return sorted(sa[lo:hi])

s = "banana"; sa = suffix_array(s)
for i, p in enumerate(sa): print(f"sa[{i}] = {p}  {s[p:]}")
print("tìm 'ana':", sa_search(s, sa, "ana"), "| tìm 'na':", sa_search(s, sa, "na"))
```

```text
sa[0] = 5  a
sa[1] = 3  ana
sa[2] = 1  anana
sa[3] = 0  banana
sa[4] = 4  na
sa[5] = 2  nana
tìm 'ana': [1, 3] | tìm 'na': [2, 4]
```

Biến thể nén của nó, **FM-index**, là thứ các công cụ gióng hàng DNA như BWA và Bowtie dùng để tìm hàng triệu đoạn đọc trong bộ gen người 3 tỷ ký tự. Khi cần tìm **nhiều mẫu cùng lúc** trong một dòng văn bản (lọc từ khoá, quét virus), thuật toán **Aho-Corasick** biến trie của các mẫu (xem [Tree](/docs/dsa/trees)) thành một automat chạy qua văn bản một lần.

</Expand>

<Expand title="Chuỗi trong hệ thống thật">

- **Bộ nhớ của `str` trong CPython** (PEP 393): mỗi ký tự 1, 2 hoặc 4 byte tuỳ code point **lớn nhất** trong chuỗi. 1.000 chữ ASCII khoảng 1 KB; thêm một emoji, cả chuỗi lên khoảng 4 KB. Nhờ độ rộng cố định, `s[i]` là `O(1)`. Go và Rust lưu UTF-8 thẳng, nên chỉ số là theo byte và có thể rơi giữa một ký tự.
- **Rolling hash** của Rabin-Karp có mặt trong `rsync` (tìm khối trùng giữa hai phiên bản file) và trong các hệ thống sao lưu (cắt dữ liệu thành khối theo nội dung, để chèn một byte ở đầu file không làm đổi mọi khối).
- **Cơ sở dữ liệu**: `LIKE '%abc%'` không dùng được B-tree (xem [Indexing](/docs/databases/indexing)); cần chỉ mục trigram (`pg_trgm`) hoặc tìm kiếm toàn văn (chỉ mục ngược theo từ).
- **`grep`, `ripgrep`**: dùng automat hữu hạn, cộng SIMD để tìm nhanh các byte đặc trưng của mẫu trước.

</Expand>

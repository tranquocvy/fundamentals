**Cần biết trước:** Big-O, cây đệ quy của merge sort và hằng số ẩn ở bài [Big-O & Complexity](/docs/dsa/complexity); heap ở bài [Tree](/docs/dsa/trees).

**Cách đọc bài:** mỗi mục có một câu **Đoán trước** và kết bằng một câu **Thử ngay**. Hãy tự trả lời trong đầu (hoặc ra giấy) rồi mới xem đáp án. Việc tự nhớ lại và tự đoán giúp nhớ lâu hơn nhiều so với chỉ đọc.

## Ý chính

Mọi thuật toán sắp xếp chỉ dùng phép so sánh "a có nhỏ hơn b không" đều cần ít nhất khoảng `n log2 n` lần so sánh trong trường hợp xấu nhất. Đây là giới hạn được chứng minh, không phải do chưa ai nghĩ ra cách hay hơn. Merge sort và quicksort đạt mức đó; insertion sort thì `n^2`. Muốn nhanh hơn `n log n` phải bỏ phép so sánh, như counting sort và radix sort dùng chính giá trị khoá làm chỉ số.

Nhưng không thuật toán nào thắng mọi lúc. Insertion sort tuyến tính trên dữ liệu gần sắp xếp; quicksort nhanh nhất trên dữ liệu ngẫu nhiên nhưng có thể rơi về `n^2`; merge sort luôn ổn định nhưng tốn bộ nhớ phụ. Dữ liệu thật lại hay có sẵn các đoạn đã sắp xếp. Vì vậy thư viện chuẩn ghép nhiều thuật toán: `sorted()` của Python dùng Timsort (merge sort cộng insertion sort), `std::sort` của C++ dùng introsort (quicksort cộng heap sort cộng insertion sort).

## Insertion sort: tốt khi dữ liệu gần đúng thứ tự

Insertion sort làm giống xếp bài trên tay: giữ phần đầu mảng đã sắp xếp, lấy phần tử kế tiếp, dịch các phần tử lớn hơn nó sang phải một ô, rồi đặt nó vào chỗ trống.

```python
import random, math

def insertion_sort(a):
    cmp = 0
    for i in range(1, len(a)):
        x, j = a[i], i - 1
        while j >= 0:
            cmp += 1
            if a[j] <= x: break
            a[j + 1] = a[j]; j -= 1            # dịch phần tử lớn hơn sang phải
        a[j + 1] = x
    return cmp

def make_shapes(n, seed=12):
    random.seed(seed)
    near = list(range(n))
    for _ in range(20):                         # đổi chỗ 20 cặp ngẫu nhiên
        i, j = random.randrange(n), random.randrange(n); near[i], near[j] = near[j], near[i]
    return {"ngẫu nhiên": random.sample(range(n), n), "đã sắp xếp": list(range(n)),
            "ngược": list(range(n, 0, -1)), "gần sắp xếp": near}

shapes = make_shapes(2000)
```

**Đoán trước:** với 2.000 phần tử, insertion sort tốn bao nhiêu lần so sánh khi mảng đã sắp xếp sẵn? Khi mảng ngược hoàn toàn?

```python
n = 2000
for name, data in shapes.items():
    a = list(data); c = insertion_sort(a); assert a == sorted(data)
    print(f"{name:<12}: {c:>9,} lần so sánh")
print(f"tham chiếu: n - 1 = {n - 1:,}, n^2/4 = {n * n // 4:,}, n(n-1)/2 = {n * (n - 1) // 2:,}")
```

```text
ngẫu nhiên  :   996,864 lần so sánh
đã sắp xếp  :     1,999 lần so sánh
ngược       : 1,999,000 lần so sánh
gần sắp xếp :    28,807 lần so sánh
tham chiếu: n - 1 = 1,999, n^2/4 = 1,000,000, n(n-1)/2 = 1,999,000
```

Mảng đã sắp xếp: mỗi phần tử chỉ so một lần với phần tử ngay trước rồi dừng, tổng `n - 1`. Mảng ngược: mỗi phần tử phải dịch qua mọi phần tử trước nó, tổng `n(n-1)/2`. Ngẫu nhiên: trung bình dịch qua một nửa, khoảng `n^2/4`. Gần sắp xếp (chỉ 20 cặp bị đổi chỗ) tốn khoảng 29.000, ít hơn ngẫu nhiên khoảng 35 lần: chi phí tỉ lệ với số cặp đứng sai thứ tự, không phải với `n^2`. Thuật toán chạy nhanh hơn khi dữ liệu đã gần đúng thứ tự gọi là **thích nghi** (adaptive).

**Thử ngay:** insertion sort trên 2.000 phần tử ngẫu nhiên tốn khoảng một triệu lần so sánh. Với 20.000 phần tử thì khoảng bao nhiêu?

<Expand title="Đáp án">

Khoảng 100 triệu: `n` gấp 10 thì `n^2` gấp 100. Đây là lý do insertion sort chỉ dùng cho mảng nhỏ hoặc gần sắp xếp.

</Expand>

## Merge sort: chia đôi rồi trộn

Merge sort chia mảng làm đôi, sắp xếp từng nửa (đệ quy), rồi **trộn** hai nửa đã sắp xếp: so hai phần tử đầu, lấy cái nhỏ hơn, lặp lại. Trộn hai dãy tổng cộng `n` phần tử tốn tối đa `n - 1` lần so sánh.

```python
def merge(l, r, st):
    out, i, j = [], 0, 0
    while i < len(l) and j < len(r):
        st["cmp"] += 1
        if l[i] <= r[j]: out.append(l[i]); i += 1    # <= : khi bằng nhau lấy bên trái trước
        else: out.append(r[j]); j += 1
    return out + l[i:] + r[j:]                        # một bên hết thì chép nốt bên kia

def merge_sort(a, st):
    if len(a) <= 1: return a
    mid = len(a) // 2
    return merge(merge_sort(a[:mid], st), merge_sort(a[mid:], st), st)

st = {"cmp": 0}
print(merge([1, 4, 7], [2, 3, 9], st), "| so sánh:", st["cmp"])
```

```text
[1, 2, 3, 4, 7, 9] | so sánh: 5
```

Bài [Big-O & Complexity](/docs/dsa/complexity) đã vẽ cây đệ quy: `log2 n` tầng, mỗi tầng trộn tổng cộng `n` phần tử, nên tổng là `O(n log n)`.

**Đoán trước:** merge sort có thích nghi như insertion sort không? Đếm trên cùng bốn dạng dữ liệu.

```python
for name, data in shapes.items():
    st = {"cmp": 0}; out = merge_sort(list(data), st); assert out == sorted(data)
    print(f"{name:<12}: {st['cmp']:>7,} lần so sánh")
print(f"tham chiếu: n log2 n = {n * math.log2(n):,.0f}")
```

```text
ngẫu nhiên  :  19,391 lần so sánh
đã sắp xếp  :  10,864 lần so sánh
ngược       :  11,088 lần so sánh
gần sắp xếp :  14,886 lần so sánh
tham chiếu: n log2 n = 21,932
```

Mọi dạng đều quanh `n log2 n`, không có dạng nào tệ. Đã sắp xếp hay ngược còn rẻ hơn khoảng một nửa, vì khi một nửa toàn nhỏ hơn nửa kia thì trộn kết thúc sớm, nhưng vẫn là `n log n`, không xuống được `n` như insertion sort. Merge sort cần thêm `O(n)` bộ nhớ cho các mảng con, và nó **ổn định**: hai phần tử bằng nhau giữ nguyên thứ tự ban đầu, nhờ dấu `<=` lấy bên trái trước (mục "Ổn định" bên dưới giải thích vì sao điều này quan trọng).

**Thử ngay:** trộn `[1, 2, 3]` với `[4, 5, 6]` tốn mấy lần so sánh? Trộn `[1, 3, 5]` với `[2, 4, 6]` thì sao?

<Expand title="Đáp án">

`[1, 2, 3]` với `[4, 5, 6]`: 3 lần (so `4` với `1`, `2`, `3`), rồi bên trái hết nên chép nốt `4, 5, 6`. `[1, 3, 5]` với `[2, 4, 6]`: 5 lần, vì hai dãy xen kẽ nên phải so tới khi bên trái hết ở phần tử cuối. Đó là `n - 1` với `n = 6`, trường hợp xấu nhất.

</Expand>

## Quicksort: phân hoạch quanh một pivot

Quicksort chọn một phần tử làm **pivot**, **phân hoạch** (partition) mảng để mọi phần tử nhỏ hơn pivot đứng trước nó và mọi phần tử còn lại đứng sau, rồi sắp xếp hai phần đó. Phân hoạch làm tại chỗ, không cần mảng phụ. Cách phân hoạch dưới đây (Lomuto) lấy pivot ở đầu đoạn, đi qua các phần tử còn lại, và mỗi khi gặp phần tử nhỏ hơn pivot thì đổi nó về vùng "nhỏ hơn" ở đầu.

```python
def partition(a, lo, hi, trace=False):
    p, i = a[lo], lo                            # i: cuối vùng "nhỏ hơn pivot"
    for j in range(lo + 1, hi + 1):
        if a[j] < p:
            i += 1; a[i], a[j] = a[j], a[i]
        if trace: print(f"  xét ô {j}: {a[lo:hi + 1]}, vùng nhỏ hơn pivot tới ô {i}")
    a[lo], a[i] = a[i], a[lo]                   # đưa pivot vào giữa hai vùng
    return i
```

### Đọc một lần phân hoạch: ba ví dụ

#### Ví dụ 1 (giải sẵn)

Phân hoạch `[5, 8, 2, 9, 1, 7, 3]`, pivot là `5`:

1. `8` không nhỏ hơn 5: để yên.
2. `2` nhỏ hơn: vùng nhỏ hơn mở rộng tới ô 1, đổi `2` với `8`.
3. `9` để yên. `1` nhỏ hơn: vùng tới ô 2, đổi `1` với `8`.
4. `7` để yên. `3` nhỏ hơn: vùng tới ô 3, đổi `3` với `9`.
5. Cuối cùng đổi pivot `5` với phần tử cuối vùng nhỏ hơn (ô 3).

```python
a = [5, 8, 2, 9, 1, 7, 3]
k = partition(a, 0, len(a) - 1, trace=True)
print("kết quả:", a, "| pivot ở ô", k)
```

```text
  xét ô 1: [5, 8, 2, 9, 1, 7, 3], vùng nhỏ hơn pivot tới ô 0
  xét ô 2: [5, 2, 8, 9, 1, 7, 3], vùng nhỏ hơn pivot tới ô 1
  xét ô 3: [5, 2, 8, 9, 1, 7, 3], vùng nhỏ hơn pivot tới ô 1
  xét ô 4: [5, 2, 1, 9, 8, 7, 3], vùng nhỏ hơn pivot tới ô 2
  xét ô 5: [5, 2, 1, 9, 8, 7, 3], vùng nhỏ hơn pivot tới ô 2
  xét ô 6: [5, 2, 1, 3, 8, 7, 9], vùng nhỏ hơn pivot tới ô 3
kết quả: [3, 2, 1, 5, 8, 7, 9] | pivot ở ô 3
```

Pivot `5` nằm đúng vị trí cuối cùng của nó (ô 3); bên trái `3, 2, 1` đều nhỏ hơn, bên phải `8, 7, 9` đều lớn hơn, dù mỗi bên chưa sắp xếp. Phân hoạch tốn `n - 1` lần so sánh.

#### Ví dụ 2 (giải một nửa)

Phân hoạch `[4, 7, 1, 6, 3]`, pivot `4`. Điền vào chỗ trống:

1. Các phần tử nhỏ hơn 4 là ___, nên vùng nhỏ hơn có ___ phần tử.
2. Pivot cuối cùng nằm ở ô ___.
3. Hai đoạn còn phải sắp xếp tiếp có độ dài ___ và ___.

<Expand title="Đáp án">

1. `1` và `3`; vùng nhỏ hơn có 2 phần tử.
2. Ô 2.
3. 2 và 2.

```python
a = [4, 7, 1, 6, 3]
k = partition(a, 0, 4)
print("kết quả:", a, "| pivot ở ô", k)
```

```text
kết quả: [3, 1, 4, 6, 7] | pivot ở ô 2
```

</Expand>

#### Ví dụ 3 (tự làm)

Phân hoạch mảng **đã sắp xếp** `[1, 2, 3, 4, 5, 6]` với pivot là phần tử đầu. Hai đoạn còn lại dài bao nhiêu? Nếu quicksort cứ lấy phần tử đầu làm pivot cho mọi đoạn tiếp theo, tổng số lần so sánh với `n` phần tử là bao nhiêu?

<Expand title="Đáp án">

Không phần tử nào nhỏ hơn `1`, nên pivot ở ô 0, đoạn trái rỗng và đoạn phải dài 5. Đoạn phải `[2, ..., 6]` cũng đã sắp xếp, lại chia thành 0 và 4, và cứ thế. Tổng so sánh `(n-1) + (n-2) + ... + 1 = n(n-1)/2`, tức `O(n^2)`, như Ví dụ 1 của bài Complexity.

```python
a = [1, 2, 3, 4, 5, 6]
k = partition(a, 0, 5)
print("pivot ở ô", k, "| đoạn trái dài", k, "| đoạn phải dài", 5 - k)
```

```text
pivot ở ô 0 | đoạn trái dài 0 | đoạn phải dài 5
```

</Expand>

### Chọn pivot quyết định tất cả

Quicksort hoàn chỉnh chỉ là phân hoạch rồi lặp lại cho hai đoạn con. Code dưới dùng một stack thay cho đệ quy để mảng lớn không làm tràn stack của Python.

```python
def quick_sort(a, pivot="first"):
    cmp, stack = 0, [(0, len(a) - 1)]
    while stack:
        lo, hi = stack.pop()
        if lo >= hi: continue
        k = random.randint(lo, hi) if pivot == "random" else lo
        a[lo], a[k] = a[k], a[lo]               # đưa pivot đã chọn lên đầu đoạn
        cmp += hi - lo                          # phân hoạch so mỗi phần tử còn lại một lần
        i = partition(a, lo, hi)
        stack += [(lo, i - 1), (i + 1, hi)]
    return cmp
```

**Đoán trước:** với dữ liệu đã sắp xếp, quicksort lấy pivot đầu tốn bao nhiêu lần so sánh? Lấy pivot ngẫu nhiên thì sao?

```python
random.seed(4)
print(f"{'':<14}" + "".join(f"{k:>14}" for k in shapes))
for pv in ("first", "random"):
    row = []
    for data in shapes.values():
        a = list(data); row.append(quick_sort(a, pv)); assert a == sorted(data)
    print(f"pivot {pv:<8}" + "".join(f"{c:>14,}" for c in row))
print(f"tham chiếu: n log2 n = {n * math.log2(n):,.0f}, n(n-1)/2 = {n * (n - 1) // 2:,}")
```

```text
                  ngẫu nhiên    đã sắp xếp         ngược   gần sắp xếp
pivot first           24,543     1,999,000     1,999,000       147,861
pivot random          26,422        24,554        27,116        26,206
tham chiếu: n log2 n = 21,932, n(n-1)/2 = 1,999,000
```

Pivot đầu thắng trên dữ liệu ngẫu nhiên nhưng sụp về đúng `n(n-1)/2` trên dữ liệu đã sắp xếp và ngược, như Ví dụ 3, và rất tệ cả trên dữ liệu gần sắp xếp. Pivot ngẫu nhiên giữ mọi dạng quanh `1,2 × n log2 n`: không có đầu vào nào làm nó chậm một cách có hệ thống, vì kẻ ra đề không đoán được pivot.

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ quicksort là `O(n log n)`. Thật ra đó là **trung bình**; trường hợp xấu nhất là `O(n^2)`, và với pivot cố định, trường hợp xấu là dữ liệu đã sắp xếp, thứ rất hay gặp. Pivot không cần chia đôi hoàn hảo: chia `1/10` và `9/10` vẫn cho `n log n`. Chỉ khi pivot liên tục rơi vào đầu mút thì mới thành `n^2`.

**Thử ngay:** vì sao quicksort được dùng nhiều dù có trường hợp `O(n^2)`, còn merge sort luôn `O(n log n)`?

<Expand title="Đáp án">

Quicksort phân hoạch tại chỗ, không cần mảng phụ, và đi qua mảng tuần tự nên thân thiện cache; trên dữ liệu ngẫu nhiên nó thường nhanh nhất. Trường hợp xấu được chặn bằng pivot ngẫu nhiên, hoặc như introsort: đếm độ sâu và đổi sang heap sort khi sâu quá `2 log2 n`. Merge sort cần `O(n)` bộ nhớ phụ và chép dữ liệu nhiều hơn.

</Expand>

## Heap sort và bảng so sánh

Heap sort dựng một max-heap (xem bài [Tree](/docs/dsa/trees)) trên chính mảng, rồi lặp: đổi phần tử lớn nhất ở gốc về cuối, thu heap lại một ô, sift-down. Luôn `O(n log n)`, tại chỗ, không có trường hợp xấu. Code dưới đặt cả bốn thuật toán lên cùng bốn dạng dữ liệu.

**Đoán trước:** trên dữ liệu ngẫu nhiên, thuật toán nào tốn ít so sánh nhất? Heap sort có hưởng lợi khi dữ liệu đã sắp xếp không?

```python
def heap_sort(a):
    cmp, n = 0, len(a)
    def sift(i, end):
        nonlocal cmp
        while True:
            l, r, m = 2 * i + 1, 2 * i + 2, i
            if l < end:
                cmp += 1
                if a[l] > a[m]: m = l
            if r < end:
                cmp += 1
                if a[r] > a[m]: m = r
            if m == i: return
            a[i], a[m] = a[m], a[i]; i = m
    for i in range(n // 2 - 1, -1, -1): sift(i, n)      # dựng max-heap
    for end in range(n - 1, 0, -1):
        a[0], a[end] = a[end], a[0]; sift(0, end)         # đưa lớn nhất về cuối
    return cmp

def ms_count(a):
    st = {"cmp": 0}; a[:] = merge_sort(a, st); return st["cmp"]

random.seed(4)
algos = {"insertion": insertion_sort, "merge": ms_count,
         "quick (ngẫu nhiên)": lambda a: quick_sort(a, "random"), "heap": heap_sort}
print(f"{'':<19}" + "".join(f"{k:>13}" for k in shapes))
for name, fn in algos.items():
    row = []
    for data in shapes.values():
        a = list(data); row.append(fn(a)); assert a == sorted(data)
    print(f"{name:<19}" + "".join(f"{c:>13,}" for c in row))
```

```text
                      ngẫu nhiên   đã sắp xếp        ngược  gần sắp xếp
insertion                996,864        1,999    1,999,000       28,807
merge                     19,391       10,864       11,088       14,886
quick (ngẫu nhiên)        26,422       24,554       27,116       26,206
heap                      37,787       39,159       35,964       39,192
```

| Thuật toán | Xấu nhất | Thích nghi | Tại chỗ | Ổn định |
|---|---|---|---|---|
| Insertion sort | `O(n^2)` | có, `O(n)` khi đã sắp xếp | có | có |
| Merge sort | `O(n log n)` | một phần | không, `O(n)` phụ | có |
| Quicksort | `O(n^2)` (trung bình `n log n`) | không | có | không |
| Heap sort | `O(n log n)` | không | có | không |

Merge sort ít so sánh nhất và ổn định; heap sort chặn được trường hợp xấu mà không tốn bộ nhớ, nhưng tốn gần gấp đôi so sánh và nhảy cóc trong bộ nhớ nên chậm hơn trên máy thật; insertion sort vô địch khi dữ liệu gần sắp xếp hoặc rất ngắn.

**Thử ngay:** bạn cần sắp xếp trong một thiết bị nhúng có rất ít RAM, và tuyệt đối không được có trường hợp chạy chậm bất thường. Chọn thuật toán nào?

<Expand title="Đáp án">

Heap sort: luôn `O(n log n)`, chỉ cần `O(1)` bộ nhớ phụ. Merge sort cần `O(n)` bộ nhớ; quicksort có trường hợp `O(n^2)`.

</Expand>

## Giới hạn dưới: không thể nhanh hơn n log n

Mọi thuật toán chỉ dùng so sánh có thể vẽ thành một **cây quyết định**: mỗi nút là một câu hỏi "`a_i < a_j`?", hai nhánh là có và không, mỗi lá là một thứ tự đã sắp xếp. Với `n` phần tử khác nhau có `n!` thứ tự, và thuật toán phải phân biệt được hết, nên cây có ít nhất `n!` lá. Cây nhị phân có `L` lá thì cao ít nhất `log2 L`. Vậy trường hợp xấu nhất cần ít nhất `log2(n!)` lần so sánh, và `log2(n!) ≈ n log2 n − 1,44n`.

**Đoán trước:** với 1.000 phần tử, merge sort ở trường hợp xấu nhất tốn nhiều hơn cận dưới này bao nhiêu phần trăm?

```python
def merge_worst(n):                             # W(n) = W(⌊n/2⌋) + W(⌈n/2⌉) + n - 1
    return 0 if n <= 1 else merge_worst(n // 2) + merge_worst(n - n // 2) + n - 1

print(f"{'n':>5} {'cận dưới ⌈log2 n!⌉':>19} {'merge sort xấu nhất':>20} {'insertion xấu nhất':>19}")
for k in (3, 4, 5, 10, 100, 1000):
    lb = math.ceil(math.lgamma(k + 1) / math.log(2))
    print(f"{k:>5} {lb:>19,} {merge_worst(k):>20,} {k * (k - 1) // 2:>19,}")
```

```text
    n  cận dưới ⌈log2 n!⌉  merge sort xấu nhất  insertion xấu nhất
    3                   3                    3                   3
    4                   5                    5                   6
    5                   7                    8                  10
   10                  22                   25                  45
  100                 525                  573               4,950
 1000               8,530                8,977             499,500
```

Ở `n = 3` và `4`, merge sort đạt đúng cận dưới. Ở `n = 1000` nó chỉ hơn khoảng 5%. Merge sort gần như tối ưu về số lần so sánh; không thuật toán so sánh nào có thể nhanh hơn `O(n log n)`.

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ cận dưới này có nghĩa là không cách sắp xếp nào nhanh hơn `n log n`. Thật ra nó chỉ áp dụng cho thuật toán **chỉ dùng so sánh**. Nếu biết thêm về khoá, ví dụ khoá là số nguyên nhỏ, ta làm được `O(n)` (mục "Không so sánh" bên dưới). Và với dữ liệu có cấu trúc sẵn, thuật toán thích nghi có thể dùng ít so sánh hơn `n log2 n` nhiều, vì cận dưới là cho trường hợp xấu nhất.

**Thử ngay:** có thuật toán so sánh nào sắp xếp mọi dãy 5 phần tử chỉ với tối đa 6 lần so sánh không?

<Expand title="Đáp án">

Không. `5! = 120` thứ tự, `log2 120 ≈ 6,9`, nên cần ít nhất 7 lần ở trường hợp xấu nhất. Bảng trên cho thấy cận dưới là 7, còn merge sort tốn 8.

</Expand>

## Ổn định: thứ tự của các phần tử bằng nhau

Một thuật toán sắp xếp là <Term>stable sort</Term> (ổn định) nếu hai phần tử có khoá bằng nhau giữ nguyên thứ tự như trong dữ liệu ban đầu.

**Đoán trước:** sắp danh sách học viên theo cấp. Ba người cấp 3 là `An, Chi, Phuc` theo thứ tự gốc. Sau khi sắp, họ đứng theo thứ tự nào?

```python
people = [("An", 3), ("Binh", 1), ("Chi", 3), ("Dung", 2), ("Em", 1), ("Phuc", 3)]

def selection_sort_by(a, key):                  # chọn nhỏ nhất rồi đổi chỗ: không ổn định
    a = list(a)
    for i in range(len(a)):
        m = min(range(i, len(a)), key=lambda j: key(a[j]))
        a[i], a[m] = a[m], a[i]
    return a

print("sorted (ổn định):        ", sorted(people, key=lambda p: p[1]))
print("selection (không ổn định):", selection_sort_by(people, key=lambda p: p[1]))
```

```text
sorted (ổn định):         [('Binh', 1), ('Em', 1), ('Dung', 2), ('An', 3), ('Chi', 3), ('Phuc', 3)]
selection (không ổn định): [('Binh', 1), ('Em', 1), ('Dung', 2), ('Chi', 3), ('An', 3), ('Phuc', 3)]
```

`sorted()` giữ `An, Chi, Phuc` và `Binh, Em` như thứ tự gốc. Selection sort đổi chỗ xa nên làm xáo thứ tự trong nhóm cấp 3.

Ổn định cho phép sắp theo nhiều khoá bằng nhiều lần sắp: muốn sắp theo cấp, trong cùng cấp theo tên, thì **sắp theo tên trước, rồi theo cấp sau** bằng một thuật toán ổn định. Lần sắp sau giữ nguyên thứ tự tên trong mỗi nhóm cấp.

**Thử ngay:** một bảng nhân viên cần sắp theo phòng ban, trong mỗi phòng theo lương giảm dần. Với `sorted()` của Python, sắp hai lần theo thứ tự nào? Còn cách nào gọn hơn?

<Expand title="Đáp án">

Sắp theo lương giảm dần trước, rồi theo phòng ban sau: `rows.sort(key=lambda r: -r.salary)` rồi `rows.sort(key=lambda r: r.dept)`. Gọn hơn: một lần với khoá là tuple, `rows.sort(key=lambda r: (r.dept, -r.salary))`.

</Expand>

## Không so sánh: counting sort và radix sort

Nếu khoá là số nguyên trong một miền nhỏ `0 .. k-1`, không cần so sánh: **counting sort** đếm mỗi giá trị xuất hiện bao nhiêu lần, cộng dồn để biết nhóm giá trị `v` bắt đầu ở đâu, rồi đặt từng phần tử vào đúng chỗ. Chi phí `O(n + k)`, và đặt phần tử theo thứ tự xuất hiện thì nó ổn định.

**Radix sort** mở rộng cho số lớn: tách số thành các "chữ số" theo cơ số `b` (ví dụ mỗi byte, `b = 256`) và counting sort lần lượt theo từng chữ số, **từ thấp lên cao**. Tính ổn định là điều làm cách này đúng: lượt sau giữ nguyên thứ tự của các lượt trước trong mỗi nhóm.

```python
import time

def counting_sort(a, k, key=lambda x: x):
    start = [0] * (k + 1)
    for x in a: start[key(x) + 1] += 1
    for v in range(k): start[v + 1] += start[v]      # start[v] = vị trí đầu của nhóm v
    out = [None] * len(a)
    for x in a:                                     # đi xuôi: giữ thứ tự gốc, nên ổn định
        out[start[key(x)]] = x; start[key(x)] += 1
    return out

def radix_sort(a, base=256):
    exp, m = 1, max(a)
    while m // exp > 0:
        a = counting_sort(a, base, key=lambda x, e=exp: (x // e) % base)
        exp *= base
    return a

print(counting_sort([3, 0, 2, 3, 1, 0], 4))
```

```text
[0, 0, 1, 2, 3, 3]
```

**Đoán trước:** radix sort là `O(n)`, `sorted()` là `O(n log n)`. Với một triệu số nguyên, cái nào nhanh hơn trong Python?

```python
random.seed(21)
for cnt, hi in ((100_000, 10**6), (1_000_000, 10**9)):
    a = [random.randrange(hi) for _ in range(cnt)]
    t = time.perf_counter(); r = radix_sort(a); t1 = time.perf_counter() - t
    t = time.perf_counter(); s = sorted(a); t2 = time.perf_counter() - t
    assert r == s
    print(f"{cnt:>9,} số < {hi:,}: radix {t1 * 1000:>5.0f} ms, sorted() {t2 * 1000:>4.0f} ms")
```

```text
  100,000 số < 1,000,000: radix   190 ms, sorted()   25 ms
1,000,000 số < 1,000,000,000: radix  3217 ms, sorted()  362 ms
```

`sorted()` thắng khoảng 8 lần. Không phải vì thuật toán sai: `sorted()` chạy bằng C, còn radix sort ở đây là vòng lặp Python, mỗi bước tốn hàng chục lệnh thông dịch. Đây là **hằng số ẩn** trong bài [Big-O & Complexity](/docs/dsa/complexity): lợi thế tiệm cận chỉ thấy khi so trên cùng một nền cài đặt. Trong C hay trên GPU, radix sort trên khoá số nguyên thường thắng sắp xếp so sánh. Giới hạn của nó: khoá phải là số nguyên hoặc tách được thành chữ số; không dùng được cho "so hai bản ghi theo hàm tuỳ ý".

**Thử ngay:** sắp xếp 100 triệu bản ghi theo tuổi (0 tới 150). Dùng gì, và tốn bao nhiêu?

<Expand title="Đáp án">

Counting sort với `k = 151`: `O(n + k)`, tức hai lượt qua dữ liệu. Sắp xếp so sánh cần khoảng `n log2 n ≈ 2,7 tỷ` lần so sánh.

</Expand>

## Thư viện chuẩn: Timsort và introsort

Dữ liệu thật hiếm khi ngẫu nhiên hoàn toàn: nó hay có sẵn các **run**, tức các đoạn đã tăng (hoặc giảm) dần. **Timsort**, do Tim Peters viết cho Python năm 2002, khai thác điều đó: quét tìm các run (run giảm thì đảo lại), nới run ngắn bằng insertion sort, rồi trộn các run như merge sort. Nó ổn định và dùng trong `sorted()`, `list.sort()` của Python và sắp xếp object của Java.

**Đoán trước:** `sorted()` trên 100.000 số đã sắp xếp tốn bao nhiêu lần so sánh? Trên mảng ngược hoàn toàn?

```python
from functools import cmp_to_key

def comparisons(data):
    cnt = 0
    def cmp(a, b):
        nonlocal cnt; cnt += 1
        return (a > b) - (a < b)
    sorted(data, key=cmp_to_key(cmp))
    return cnt

random.seed(31)
N = 100_000
tim_shapes = {
    "ngẫu nhiên": [random.random() for _ in range(N)],
    "đã sắp xếp": list(range(N)),
    "ngược hoàn toàn": list(range(N, 0, -1)),
    "10 đoạn tăng nối nhau": sum((sorted(random.random() for _ in range(N // 10)) for _ in range(10)), []),
    "đã sắp xếp + 100 số mới ở cuối": list(range(N - 100)) + [random.random() * N for _ in range(100)],
}
print(f"n = {N:,}: log2(n!) ≈ {math.lgamma(N + 1) / math.log(2):,.0f}")
for name, d in tim_shapes.items():
    c = comparisons(d)
    print(f"{name:<32} {c:>10,} lần so sánh  ({c / N:5.2f} mỗi phần tử)")
```

```text
n = 100,000: log2(n!) ≈ 1,516,704
ngẫu nhiên                        1,531,895 lần so sánh  (15.32 mỗi phần tử)
đã sắp xếp                           99,999 lần so sánh  ( 1.00 mỗi phần tử)
ngược hoàn toàn                      99,999 lần so sánh  ( 1.00 mỗi phần tử)
10 đoạn tăng nối nhau               439,989 lần so sánh  ( 4.40 mỗi phần tử)
đã sắp xếp + 100 số mới ở cuối      102,509 lần so sánh  ( 1.03 mỗi phần tử)
```

Dữ liệu ngẫu nhiên: sát cận dưới `log2(n!)`. Đã sắp xếp hay ngược: đúng `n - 1`, vì một lần quét thấy cả mảng là một run (run ngược được đảo tại chỗ). Thêm 100 số vào cuối một mảng đã sắp xếp: chỉ nhỉnh hơn `n`. Đây là lý do thêm vài phần tử rồi gọi lại `sort()` trong Python rất rẻ.

C++ không yêu cầu `std::sort` ổn định, nên dùng **introsort** (Musser, 1997): quicksort với pivot trung vị của ba phần tử; nếu độ sâu đệ quy vượt khoảng `2 log2 n` thì đổi sang heap sort cho đoạn đó để chặn `O(n^2)`; đoạn ngắn dưới khoảng 16 phần tử thì kết thúc bằng insertion sort. Mỗi thuật toán làm phần nó giỏi nhất.

| Thư viện | Thuật toán | Ổn định |
|---|---|---|
| Python `sorted`, `list.sort` | Timsort | có |
| Java `Arrays.sort(Object[])` | Timsort | có |
| Java `Arrays.sort(int[])` | dual-pivot quicksort | không (số nguyên không cần) |
| C++ `std::sort` / `std::stable_sort` | introsort / merge sort | không / có |
| Go `sort.Slice` / `sort.SliceStable` | pdqsort / insertion + merge | không / có |
| Rust `sort` / `sort_unstable` | driftsort / ipnsort | có / không |

<Expand title="Đáp án">

## Đi sâu hơn

Các phần dưới không cần để đọc tiếp chặng DSA.

<Expand title="Vì sao quicksort trung bình là O(n log n)">

Giả sử pivot luôn chia theo tỉ lệ `1/10` và `9/10`, tệ hơn chia đôi nhiều. Recurrence `T(n) = T(n/10) + T(9n/10) + n`. Trong cây đệ quy, mỗi tầng tốn tối đa `n`, và đường dài nhất (luôn đi nhánh `9/10`) có `log_{10/9} n ≈ 6,6 log2 n` tầng. Tổng vẫn là `O(n log n)`, chỉ hằng số lớn hơn. Chỉ khi tỉ lệ chia là `0` và `n-1` thì mới thành `n^2`. Với pivot ngẫu nhiên, xác suất liên tục chọn trúng đầu mút nhỏ tới mức có thể bỏ qua; kỳ vọng số so sánh là khoảng `1,39 n log2 n`, khớp với bảng đo trong bài.

Trung vị của ba phần tử (đầu, giữa, cuối) cho pivot tốt hơn ngẫu nhiên trên dữ liệu thường gặp, nhưng không loại bỏ trường hợp xấu: có những dãy được dựng riêng để đánh bại nó. Introsort đếm độ sâu để có bảo đảm; pdqsort (Go từ 1.19, `sort_unstable` của Rust trước 1.81) còn nhận diện các mẫu xấu như dãy đã sắp xếp hay nhiều phần tử bằng nhau để xử lý riêng.

<Expand title="Sắp xếp ngoài: khi dữ liệu lớn hơn RAM">

Khi dữ liệu không vừa RAM, chi phí chính là số lượt đọc ghi đĩa, và merge sort hợp vì nó đọc tuần tự:

1. **Tạo run**: đọc từng mẻ vừa RAM, sắp xếp trong RAM, ghi ra một file run.
2. **Trộn `k` đường**: mở đồng thời `k` run, dùng min-heap `k` phần tử để luôn lấy phần tử nhỏ nhất trong các đầu run.

```python
import os, struct, heapq, tempfile

def read_run(path, chunk=4096):
    with open(path, "rb") as f:
        while b := f.read(8 * chunk):
            yield from struct.unpack(f"{len(b) // 8}q", b)

def external_sort(src, dst, mem_items):
    tmp, runs = tempfile.mkdtemp(), []
    with open(src, "rb") as f:                  # pha 1: tạo run vừa RAM
        while b := f.read(8 * mem_items):
            nums = sorted(struct.unpack(f"{len(b) // 8}q", b))
            p = os.path.join(tmp, f"run{len(runs)}.bin")
            with open(p, "wb") as g: g.write(struct.pack(f"{len(nums)}q", *nums))
            runs.append(p)
    with open(dst, "wb") as out:                # pha 2: trộn mọi run một lượt bằng heap
        buf = []
        for x in heapq.merge(*(read_run(p) for p in runs)):
            buf.append(x)
            if len(buf) == 4096: out.write(struct.pack("4096q", *buf)); buf.clear()
        out.write(struct.pack(f"{len(buf)}q", *buf))
    for p in runs: os.remove(p)
    os.rmdir(tmp)
    return len(runs)

TOTAL, MEM = 2_000_000, 100_000
random.seed(5)
d = tempfile.mkdtemp(); src, dst = os.path.join(d, "in.bin"), os.path.join(d, "out.bin")
with open(src, "wb") as f:
    for _ in range(TOTAL // MEM):
        f.write(struct.pack(f"{MEM}q", *[random.randrange(10**12) for _ in range(MEM)]))
k = external_sort(src, dst, MEM)
res = list(read_run(dst))
assert res == sorted(read_run(src)) and len(res) == TOTAL
print(f"{TOTAL:,} số ({os.path.getsize(src) / 2**20:.1f} MB), RAM giữ {MEM:,} số: {k} run, trộn {k} đường trong một lượt, kết quả đúng")
for p in (src, dst): os.remove(p)
os.rmdir(d)
```

```text
2,000,000 số (15.3 MB), RAM giữ 100,000 số: 20 run, trộn 20 đường trong một lượt, kết quả đúng
```

Một lượt trộn `k` đường xử lý được dữ liệu cỡ `k × RAM`, nên thực tế dữ liệu hầu như chỉ qua đĩa hai lần. `ORDER BY` của cơ sở dữ liệu khi vượt bộ nhớ làm việc (`Sort Method: external merge` trong `EXPLAIN` của PostgreSQL) và lệnh `sort` của Unix đều làm như vậy.

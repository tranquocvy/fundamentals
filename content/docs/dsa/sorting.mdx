## Ý chính

Sắp xếp là bài toán đầu tiên mà mọi người học thuật toán đều gặp, và là bài toán mà lý thuyết trả lời **trọn vẹn nhất**: ta biết thuật toán so sánh nào tốt nhất có thể (`n log n`) và chứng minh được không ai làm tốt hơn. Nhưng "tốt nhất có thể" chỉ là phần đầu. Trên máy thật, tốc độ phụ thuộc vào dữ liệu đã gần sắp xếp chưa, có trùng lặp nhiều không, bộ nhớ có vừa không, hai phần tử bằng nhau có được giữ nguyên thứ tự không. Thư viện chuẩn của mọi ngôn ngữ vì thế không dùng một thuật toán thuần mà ghép nhiều thuật toán lại.

Bài đi theo trình tự: các thước đo (ổn định, tại chỗ, thích nghi); bốn thuật toán so sánh tự cài và so sánh bằng số phép so sánh trên bốn dạng dữ liệu; vì sao `n log n` là giới hạn (cây quyết định) và merge sort sát giới hạn tới mức nào; counting và radix sort, những cách "phá" giới hạn bằng cách không so sánh; Timsort và introsort, hai thuật toán thật nằm trong Python, Java, C++; cuối cùng là sắp xếp ngoài khi dữ liệu không vừa bộ nhớ. Mọi code là Python 3.13 chạy thật. Bài này dùng kiến thức từ [Big-O & Complexity](/docs/dsa/complexity) (hằng số ẩn, recurrence của merge sort) và [Tree](/docs/dsa/trees) (heap, bài heapsort).

## Thước đo của một thuật toán sắp xếp

Cùng đưa ra một dãy tăng dần, nhưng các thuật toán khác nhau ở bốn tính chất:

| Tính chất | Nghĩa |
|---|---|
| **Dựa trên so sánh** | chỉ dùng phép "a có nhỏ hơn b không"; áp dụng cho mọi kiểu có thứ tự |
| **<Term>Stable sort</Term> (ổn định)** | hai phần tử bằng khoá giữ nguyên thứ tự ban đầu |
| **Tại chỗ (in-place)** | chỉ dùng `O(1)` hoặc `O(log n)` bộ nhớ phụ |
| **Thích nghi (adaptive)** | nhanh hơn khi dữ liệu đã gần sắp xếp |

Tính ổn định hay bị coi nhẹ nhưng rất thực dụng: để sắp một bảng theo cột A rồi theo cột B mà vẫn giữ thứ tự theo A trong từng nhóm B, ta sắp theo A trước rồi theo B sau bằng một thuật toán ổn định. Phần sắp xếp không so sánh bên dưới có ví dụ cụ thể.

## Bốn thuật toán, một bảng so sánh

Dưới đây là bốn thuật toán tự cài, mỗi cái đếm **số phép so sánh** (`cmp`) và **số lần ghi** (`moves`). Đếm thao tác thay vì đo giây (xem [Big-O & Complexity](/docs/dsa/complexity)) giúp kết quả không phụ thuộc máy và không bị Python thông dịch làm nhiễu.

- **Insertion sort**: giữ phần đầu đã sắp xếp, lấy từng phần tử kế và chèn vào đúng chỗ bằng cách dịch các phần tử lớn hơn sang phải. `O(n^2)` ở trường hợp xấu và trung bình, nhưng **`O(n)` nếu dữ liệu đã sắp xếp**: thích nghi.
- **Merge sort**: chia đôi, sắp xếp từng nửa, **trộn** hai nửa (so sánh hai đầu, lấy cái nhỏ hơn). Recurrence `T(n) = 2T(n/2) + n` cho `Θ(n log n)` bất kể dữ liệu (xem bài Complexity); cần `O(n)` bộ nhớ phụ; ổn định.
- **Quicksort**: chọn một **pivot**, **phân hoạch** mảng thành phần nhỏ hơn và lớn hơn pivot, rồi sắp xếp từng phần. Trung bình `O(n log n)`, tại chỗ, nhưng nếu pivot luôn rơi vào đầu mút thì phần chia là `n-1` và `0`, `T(n) = T(n-1) + n`, tức `Θ(n^2)`. **Không ổn định**.
- **Heap sort**: xây max-heap (xem [Tree](/docs/dsa/trees)), rồi lần lượt đưa phần tử lớn nhất về cuối. `O(n log n)` đảm bảo, tại chỗ, không ổn định.

```python
import random, math, sys
sys.setrecursionlimit(100000)

class Counter:
    def __init__(self): self.cmp = self.moves = 0

def insertion_sort(a, c):
    for i in range(1, len(a)):
        x, j = a[i], i - 1
        while j >= 0:
            c.cmp += 1
            if a[j] <= x: break
            a[j + 1] = a[j]; c.moves += 1; j -= 1
        a[j + 1] = x; c.moves += 1

def merge_sort(a, c):
    if len(a) <= 1: return a
    mid = len(a) // 2
    l, r = merge_sort(a[:mid], c), merge_sort(a[mid:], c)
    out, i, j = [], 0, 0
    while i < len(l) and j < len(r):
        c.cmp += 1
        if l[i] <= r[j]: out.append(l[i]); i += 1
        else: out.append(r[j]); j += 1
        c.moves += 1
    out += l[i:] + r[j:]; c.moves += len(l) - i + len(r) - j
    return out

def quick_sort(a, c, pivot="first"):
    """Lomuto, tại chỗ. pivot: 'first' (ngây thơ), 'random', 'median3'."""
    stack = [(0, len(a) - 1)]
    while stack:
        lo, hi = stack.pop()
        while lo < hi:
            if pivot == "random":
                k = random.randint(lo, hi)
            elif pivot == "median3":
                mid = (lo + hi) // 2
                k = sorted([(a[lo], lo), (a[mid], mid), (a[hi], hi)])[1][1]
            else:
                k = lo
            a[lo], a[k] = a[k], a[lo]
            p, i = a[lo], lo
            for j in range(lo + 1, hi + 1):
                c.cmp += 1
                if a[j] < p:
                    i += 1; a[i], a[j] = a[j], a[i]; c.moves += 1
            a[lo], a[i] = a[i], a[lo]; c.moves += 1
            # đệ quy phía nhỏ hơn bằng stack, lặp phía lớn: độ sâu stack O(log n)
            if i - lo < hi - i: stack.append((i + 1, hi)); hi = i - 1
            else: stack.append((lo, i - 1)); lo = i + 1

def heap_sort(a, c):
    n = len(a)
    def sift(i, end):
        while True:
            l, r, m = 2 * i + 1, 2 * i + 2, i
            if l < end:
                c.cmp += 1
                if a[l] > a[m]: m = l
            if r < end:
                c.cmp += 1
                if a[r] > a[m]: m = r
            if m == i: return
            a[i], a[m] = a[m], a[i]; c.moves += 1; i = m
    for i in range(n // 2 - 1, -1, -1): sift(i, n)
    for end in range(n - 1, 0, -1):
        a[0], a[end] = a[end], a[0]; c.moves += 1; sift(0, end)

def run(name, fn, data):
    a, c = list(data), Counter()
    out = fn(a, c)
    res = out if out is not None else a
    assert res == sorted(data), name
    return c

random.seed(12)
n = 2000
inputs = {
    "ngẫu nhiên": [random.random() for _ in range(n)],
    "đã sắp xếp": sorted(random.random() for _ in range(n)),
    "ngược": sorted((random.random() for _ in range(n)), reverse=True),
    "gần sắp xếp (1% đảo)": None,
}
base = sorted(random.random() for _ in range(n))
for _ in range(n // 100):
    i, j = random.randrange(n), random.randrange(n); base[i], base[j] = base[j], base[i]
inputs["gần sắp xếp (1% đảo)"] = base

algos = [
    ("insertion", insertion_sort), ("merge", merge_sort),
    ("quick (pivot đầu)", lambda a, c: quick_sort(a, c, "first")),
    ("quick (pivot ngẫu nhiên)", lambda a, c: quick_sort(a, c, "random")),
    ("quick (median-of-3)", lambda a, c: quick_sort(a, c, "median3")),
    ("heap", heap_sort),
]
print(f"số phép so sánh khi sắp xếp n = {n}   (n log2 n = {n * math.log2(n):.0f}, n^2/2 = {n*n//2})")
print(f"{'':<26}" + "".join(f"{k:>24}" for k in inputs))
for name, fn in algos:
    row = []
    for k, data in inputs.items():
        c = run(name, fn, data)
        row.append(f"{c.cmp:>14} ({c.moves:>6} ghi)")
    print(f"{name:<26}" + "".join(f"{x:>24}" for x in row))
```

Mỗi cột là một dạng dữ liệu, mỗi hàng một thuật toán. Từng thuật toán có "chữ ký" riêng:

- **Insertion sort**: với dữ liệu ngẫu nhiên tốn khoảng `n^2/4` = 1.009.631 phép so sánh (đúng một nửa của `n^2/2`); đã sắp xếp chỉ **1.999** (`n - 1`, đúng thích nghi); ngược tốn **1.999.000**, tức `n(n-1)/2` cả hai vế. Với dữ liệu gần sắp xếp, 24.803 phép: rất rẻ. Đó là lý do nó vẫn sống trong các thuật toán thực tế dưới dạng bước cuối cho đoạn nhỏ.
- **Merge sort**: số so sánh ổn định quanh `n log2 n` (19.428 với dữ liệu ngẫu nhiên, **ít hơn** cả `21.932` của `n log2 n` vì mỗi lần trộn tốn `n - 1` thay vì `n`); đã sắp xếp hay ngược còn ít hơn (khoảng một nửa), vì khi một nửa toàn nhỏ hơn thì trộn dừng sớm. Nhưng **số lần ghi** luôn 21.952 vì nó luôn chép. Không thích nghi về chép dữ liệu.
- **Quicksort pivot đầu**: gần tối ưu với dữ liệu ngẫu nhiên (23.659) nhưng **thảm hoạ** ở đã sắp xếp và ngược: **1.999.000** so sánh, đúng bằng `n(n-1)/2`. Pivot là phần tử đầu mà dữ liệu đã sắp xếp nghĩa là mỗi lần phân hoạch tách ra `0` và `n-1`. Dữ liệu gần sắp xếp cũng xấu (306.044, gấp 13 lần).
- **Quicksort pivot ngẫu nhiên**: số so sánh ở mọi dạng dữ liệu gần nhau (22.900 tới 26.761), không có đầu vào nào làm nó chậm một cách có hệ thống. Cái giá là hằng số lớn hơn khoảng 20% đến 30% so với median-of-3 trên dữ liệu ngẫu nhiên (25.831 so với 20.309).
- **Quicksort median-of-3** (lấy trung vị của đầu, giữa, cuối): tốt nhất ở ngẫu nhiên và đã sắp xếp (20.309 và 17.964), nhưng ở dữ liệu **ngược** vẫn tốn **501.002** so sánh, tức một phần tư `n^2/2`. Ở bản Lomuto này, mỗi lần phân hoạch xoáy trật tự của mảng theo cách làm lệch lần phân hoạch kế. Bài học: median-of-3 giảm khả năng xấu nhưng **không loại bỏ** nó. Không có quy tắc chọn pivot tất định đơn giản nào loại bỏ hoàn toàn.
- **Heap sort**: 35.964 đến 39.188 so sánh ở mọi dạng dữ liệu: ổn định và chặn trên được, nhưng **gần gấp đôi** merge sort ở dữ liệu ngẫu nhiên (37.672 so với 19.428), và không hưởng lợi gì khi dữ liệu đã có thứ tự. Mỗi bước `sift` tốn hai phép so sánh (con trái với con phải, rồi với cha), và truy cập nhảy cóc ở mảng lớn thân thiện cache kém hơn quicksort.

Tóm lại, không có người thắng tuyệt đối: quicksort nhanh nhất trên dữ liệu "bình thường", merge sort không bao giờ xấu và ổn định, heap sort chặn được trường hợp tồi nhất mà không tốn bộ nhớ phụ, insertion sort thắng khi đoạn ngắn hoặc gần sắp xếp. Thư viện thật ghép chúng lại (xem Timsort và introsort bên dưới).

### Vì sao quicksort trung bình `O(n log n)`

Giả sử pivot luôn chia mảng thành hai phần tỉ lệ `1/10` và `9/10`, tệ hơn trường hợp chia đôi nhiều. Recurrence `T(n) = T(n/10) + T(9n/10) + n`: cây đệ quy có tầng nào cũng tốn tối đa `n`, và đường dài nhất (luôn đi sang nhánh `9/10`) có `log_{10/9} n` tầng, một hằng số nhân của `log n`. Kết quả vẫn `Θ(n log n)`. Chỉ khi tỉ lệ chia **tới `0` và `n-1`** thì mới thành `n^2`. Pivot ngẫu nhiên khiến việc này có xác suất cực nhỏ, bất kể đầu vào.

## Giới hạn dưới: vì sao không thể nhanh hơn n log n

Mọi thuật toán so sánh có thể vẽ thành **cây quyết định**: mỗi nút trong là một phép so sánh `a_i < a_j?`, hai nhánh là kết quả có hoặc không, mỗi **lá** là một thứ tự hoàn chỉnh của đầu vào. Để đúng với mọi đầu vào, cây phải có **ít nhất một lá cho mỗi hoán vị**, tức ít nhất `n!` lá. Cây nhị phân có `L` lá thì cao ít nhất `log2 L`. Vậy trong trường hợp xấu nhất cần ít nhất

```text
log2(n!)  ≈  n log2 n - 1,44 n   phép so sánh        (công thức Stirling)
```

Nên **không thuật toán sắp xếp dựa trên so sánh nào** nhanh hơn `Ω(n log n)`. Hãy xem giới hạn dưới sát tới mức nào so với merge sort:

```python
import math
print(f"{'n':>4} {'n! (số hoán vị)':>20} {'ceil(log2 n!)':>14} {'merge sort xấu nhất':>20} {'insertion xấu nhất n(n-1)/2':>28}")
def merge_worst(n):                           # W(n) = W(n//2) + W(n - n//2) + n - 1
    return 0 if n <= 1 else merge_worst(n // 2) + merge_worst(n - n // 2) + n - 1
for n in (3, 4, 5, 8, 10, 12, 16, 100, 1000):
    f = math.factorial(n)
    print(f"{n:>4} {f if n <= 16 else '~10^' + str(int(math.log10(f))):>20} {math.ceil(math.log2(f)):>14} {merge_worst(n):>20} {n*(n-1)//2:>28}")
```

```text
   3                    6              3                    3                            3

   5                  120              7                    8                           10
```

Với `n = 3` và `n = 4`, merge sort đạt đúng giới hạn (3 và 5). Với `n = 5` nó tốn 8 trong khi cận dưới là 7 (có thuật toán riêng cho `n` nhỏ đạt 7); với `n = 1000` merge sort tốn 8977, chỉ hơn cận dưới 8530 khoảng 5%. Insertion sort: `499.500` so với `8.530`. **Merge sort gần như tối ưu về số phép so sánh**; điểm yếu của nó là bộ nhớ phụ.

Hệ quả hai chiều: không cần tìm thuật toán so sánh nhanh hơn `n log n`, nhưng có thể thoát giới hạn bằng cách **không so sánh**.

## Sắp xếp không so sánh: counting và radix sort

Cây quyết định chỉ áp dụng khi thông tin duy nhất ta dùng là phép so sánh. Nếu khoá là **số nguyên trong một miền nhỏ**, ta có thể dùng chính giá trị làm chỉ số mảng.

**Counting sort**: đếm số lần mỗi giá trị `0 .. k-1` xuất hiện, cộng dồn để biết "nhóm giá trị `v` bắt đầu từ vị trí nào", rồi đặt từng phần tử vào đúng vị trí. `O(n + k)`. Đặt phần tử theo thứ tự xuất hiện ban đầu thì **ổn định**.

**Radix sort (LSD)**: với số nguyên lớn, chia thành các "chữ số" trong cơ số `b` (ví dụ `b = 256`, tức mỗi byte) và counting sort **từng chữ số từ thấp lên cao**. Tính ổn định của counting sort là điều khiến cách này **đúng**: sau khi sắp theo chữ số cao nhất, thứ tự của các số cùng chữ số cao nhất vẫn giữ kết quả từ các lượt trước. `O(d (n + b))` với `d` là số chữ số.

```python
import random, time

def counting_sort(a, k, key=lambda x: x):
    """a: list; key(x) in [0, k). Ổn định: duyệt ngược khi đặt."""
    count = [0] * (k + 1)
    for x in a: count[key(x) + 1] += 1
    for i in range(k): count[i + 1] += count[i]          # count[v] = vị trí bắt đầu của nhóm v
    out = [None] * len(a)
    for x in a:                                          # duyệt xuôi + vị trí tăng dần giữ thứ tự ban đầu
        out[count[key(x)]] = x; count[key(x)] += 1
    return out

def radix_sort(a, base=256):
    """LSD radix cho số nguyên không âm: counting sort từng 'chữ số' từ thấp lên cao."""
    if not a: return a
    exp, m = 1, max(a)
    while m // exp > 0:
        a = counting_sort(a, base, key=lambda x, e=exp: (x // e) % base)
        exp *= base
    return a

# 1) tính ổn định: sắp theo cấp, các bản ghi cùng cấp giữ nguyên thứ tự trước đó
people = [("An", 3), ("Binh", 1), ("Chi", 3), ("Dung", 2), ("Em", 1), ("Phuc", 3)]
print("trước:", people)
print("sort theo cấp (ổn định): ", counting_sort(people, 4, key=lambda p: p[1]))

# 2) đúng sai và thời gian
random.seed(21)
print()
print(f"{'n':>9} {'giá trị tối đa':>15} | {'radix (base 256)':>17} {'sorted()':>10}")
for n, hi in ((100_000, 10**6), (1_000_000, 10**6), (1_000_000, 10**9)):
    a = [random.randrange(hi) for _ in range(n)]
    t = time.perf_counter(); r = radix_sort(a); t1 = time.perf_counter() - t
    t = time.perf_counter(); s = sorted(a); t2 = time.perf_counter() - t
    assert r == s
    print(f"{n:>9} {hi:>15,} | {t1*1000:>14.0f} ms {t2*1000:>7.0f} ms")
```

```text
sort theo cấp (ổn định):  [('Binh', 1), ('Em', 1), ('Dung', 2), ('An', 3), ('Chi', 3), ('Phuc', 3)]

   100000       1,000,000 |             60 ms      11 ms
```

Phần ổn định: sắp theo cấp, ba người cấp 3 vẫn đứng đúng thứ tự `An, Chi, Phuc` như danh sách gốc, hai người cấp 1 đúng thứ tự `Binh, Em`. Không ổn định thì thứ tự trong nhóm là tuỳ ý.

Phần thời gian là bài học trung thực: radix sort **không cần so sánh nhưng vẫn thua** `sorted()` khoảng 5 đến 7 lần ở cả ba cỡ. Lý do không phải thuật toán sai: `sorted()` chạy bằng C (Timsort), còn radix sort ở đây là vòng lặp Python cho từng "chữ số" (3 lượt với số tới một triệu, 4 lượt với một tỉ). Đó là chuyện **hằng số ẩn** của bài [Big-O & Complexity](/docs/dsa/complexity): lợi thế tiệm cận chỉ lộ ra khi cùng một nền cài đặt. Trong C hoặc Rust, radix sort trên số nguyên hay khoá cố định thường nhanh hơn sắp xếp so sánh đáng kể, và nó là cách cơ sở dữ liệu và công cụ GPU sắp xếp các số lớn. Giới hạn: miền khoá phải nhỏ (counting) hoặc khoá phải phân rã được thành chữ số (radix); không dùng được cho "so sánh hai bản ghi theo hàm tuỳ ý".

## Thư viện chuẩn thật sự dùng gì

### Timsort (Python, Java cho object)

Tim Peters viết **Timsort** cho Python năm 2002 dựa trên một quan sát: dữ liệu thật hiếm khi ngẫu nhiên hoàn toàn; nó thường chứa sẵn các **đoạn đã tăng (hoặc giảm) dần** gọi là run. Timsort: (1) quét tìm các run tự nhiên (run giảm thì đảo lại), (2) nếu run ngắn hơn `minrun` (32 đến 64) thì nới ra bằng **insertion sort** nhị phân, (3) trộn các run bằng merge, với quy tắc chọn cặp nào trộn trước để giữ cây trộn cân bằng (từ Python 3.11 là chính sách "powersort"), và khi một run thắng liên tục thì chuyển sang chế độ **galloping** (nhảy theo luỹ thừa 2 để tìm chỗ chèn). Nó ổn định.

Hãy đếm số phép so sánh thực của `sorted()` theo hình dạng dữ liệu, bằng `cmp_to_key` bọc một bộ đếm:

```python
import random, math
from functools import cmp_to_key

def comparisons(data):
    cnt = [0]
    def cmp(a, b):
        cnt[0] += 1
        return -1 if a < b else (1 if a > b else 0)
    sorted(data, key=cmp_to_key(cmp))
    return cnt[0]

random.seed(31)
n = 100_000
shapes = {
    "ngẫu nhiên": [random.random() for _ in range(n)],
    "đã sắp xếp": list(range(n)),
    "ngược hoàn toàn": list(range(n, 0, -1)),
    "10 đoạn tăng nối nhau": sum((sorted(random.random() for _ in range(n // 10)) for _ in range(10)), []),
    "sắp xếp + 100 phần tử mới ở cuối": list(range(n - 100)) + [random.random() * n for _ in range(100)],
    "toàn số giống nhau": [7] * n,
}
print(f"n = {n}: n-1 = {n-1}, n log2 n = {n * math.log2(n):.0f}, log2(n!) ≈ {math.lgamma(n + 1) / math.log(2):.0f}")
print(f"{'hình dạng dữ liệu':<36} {'số so sánh':>12} {'/ n':>7}")
for name, d in shapes.items():
    c = comparisons(d)
    print(f"{name:<36} {c:>12} {c / n:>7.2f}")
```

```text

hình dạng dữ liệu                      số so sánh     / n
ngẫu nhiên                                1531895   15.32
đã sắp xếp                                  99999    1.00
ngược hoàn toàn                             99999    1.00
10 đoạn tăng nối nhau                      439989    4.40
sắp xếp + 100 phần tử mới ở cuối           102509    1.03
```

Dữ liệu ngẫu nhiên: 1.531.895 phép so sánh, sát cận dưới lý thuyết `log2(n!)` ≈ 1.516.704 (chỉ hơn 1%). Nhưng với dữ liệu có cấu trúc, nó xuống còn **tuyến tính**: đã sắp xếp hay **ngược hoàn toàn** chỉ tốn `n - 1` (một lần quét phát hiện một run duy nhất, run ngược được đảo tại chỗ); 10 đoạn tăng nối nhau tốn khoảng `4,4n` (gần `n log2 10 = 3,3n` cộng chi phí phát hiện run); thêm 100 phần tử vào cuối mảng đã sắp xếp tốn `1,03n`. Đây là thuật toán thích nghi đúng nghĩa: "dữ liệu có cấu trúc thì nhanh hơn `n log n`" là sự thật có thể đo.

### Introsort (C++ `std::sort`) và pdqsort

C++ không yêu cầu ổn định cho `std::sort`, nên dùng quicksort vì nhanh nhất ở dữ liệu ngẫu nhiên, nhưng quicksort có điểm yếu như trên. **Introsort** (Musser, 1997) vá: chạy quicksort (pivot median-of-3), **theo dõi độ sâu đệ quy**, nếu vượt khoảng `2 log2 n` thì **đổi sang heap sort** cho đoạn đó (đảm bảo `O(n log n)` trong trường hợp xấu nhất), và với đoạn nhỏ (khoảng 16 phần tử) kết thúc bằng insertion sort. Ba thuật toán, mỗi cái làm phần nó giỏi nhất. `pdqsort` (pattern-defeating quicksort) tiếp tục theo hướng đó: nhận diện các mẫu xấu (đã sắp xếp, ngược, nhiều phần tử bằng nhau) và xử lý riêng; nhiều thư viện hiện đại (Go từ 1.19 và các thuật toán không ổn định của Rust) dùng thuật toán thuộc họ này.

| Thư viện | Thuật toán | Ổn định |
|---|---|---|
| Python `sorted`, `list.sort` | Timsort | có |
| Java `Arrays.sort(Object[])`, `Collections.sort` | Timsort | có |
| Java `Arrays.sort(int[])` | dual-pivot quicksort | không (không cần với số nguyên) |
| C++ `std::sort` | introsort | không |
| C++ `std::stable_sort` | merge sort (cần bộ nhớ phụ) | có |
| Go `sort.Slice` | pdqsort (từ 1.19) | không (`sort.SliceStable` thì có) |
| Rust `slice::sort` / `sort_unstable` | driftsort / ipnsort (từ Rust 1.81) | có / không |

Việc **thư viện chọn ổn định hay không** có hệ quả thực tế: nếu code của bạn phụ thuộc vào "sắp theo A rồi theo B" thì phải dùng bản ổn định.

## Sắp xếp ngoài: dữ liệu lớn hơn bộ nhớ

Mọi thuật toán trên giả định dữ liệu nằm trong RAM. Khi dữ liệu lớn hơn, đơn vị chi phí đổi sang **số lần đọc ghi đĩa**, và **merge sort** trở thành lựa chọn tự nhiên vì nó đọc tuần tự:

1. **Pha tạo run**: đọc từng mẻ vừa bộ nhớ, sắp xếp trong RAM, ghi ra file run.
2. **Pha trộn `k` đường**: đọc đồng thời `k` run, dùng một min-heap `k` phần tử để luôn lấy được phần tử nhỏ nhất trong các đầu run, ghi kết quả ra.

Với `N` phần tử, bộ nhớ chứa `M` phần tử và khối đĩa `B`, số run là `N/M`; nếu trộn được `k` đường cùng lúc thì số lượt trộn là `⌈log_k(N/M)⌉`. Mỗi lượt đọc và ghi mọi phần tử đúng một lần. Thí nghiệm: 2 triệu số nguyên (15,3 MB) nhưng chỉ cho phép giữ 100.000 số (0,8 MB) trong bộ nhớ một lần:

```python
import os, random, struct, heapq, tempfile, time

def write_run(path, nums):
    with open(path, "wb") as f: f.write(struct.pack(f"{len(nums)}q", *nums))

def read_run(path, chunk=4096):
    with open(path, "rb") as f:
        while True:
            b = f.read(8 * chunk)
            if not b: return
            yield from struct.unpack(f"{len(b) // 8}q", b)

def external_sort(src, dst, mem_items):
    tmp = tempfile.mkdtemp()
    runs = []
    with open(src, "rb") as f:                            # pha 1: đọc từng mẻ vừa bộ nhớ, sắp xếp, ghi run
        while True:
            b = f.read(8 * mem_items)
            if not b: break
            nums = sorted(struct.unpack(f"{len(b) // 8}q", b))
            p = os.path.join(tmp, f"run{len(runs)}.bin"); write_run(p, nums); runs.append(p)
    with open(dst, "wb") as out:                          # pha 2: trộn k run bằng heapq.merge (min-heap k phần tử)
        buf = []
        for x in heapq.merge(*(read_run(p) for p in runs)):
            buf.append(x)
            if len(buf) == 4096: out.write(struct.pack("4096q", *buf)); buf.clear()
        if buf: out.write(struct.pack(f"{len(buf)}q", *buf))
    for p in runs: os.remove(p)
    os.rmdir(tmp)
    return len(runs)

N, MEM = 2_000_000, 100_000
random.seed(5)
d = tempfile.mkdtemp(); src, dst = os.path.join(d, "in.bin"), os.path.join(d, "out.bin")
with open(src, "wb") as f:
    for _ in range(N // 100_000): f.write(struct.pack("100000q", *[random.randrange(10**12) for _ in range(100_000)]))
print(f"{N:,} số nguyên 8 byte = {os.path.getsize(src) / 2**20:.1f} MB; bộ nhớ cho phép giữ {MEM:,} số ({MEM * 8 / 2**20:.1f} MB) mỗi lần")
t = time.perf_counter(); k = external_sort(src, dst, MEM); dt = time.perf_counter() - t
res = list(read_run(dst))
assert res == sorted(read_run(src)) and len(res) == N
print(f"pha 1 tạo {k} run, pha 2 trộn {k} đường; tổng {dt:.1f} giây; kết quả đúng")
```

```text
2,000,000 số nguyên 8 byte = 15.3 MB; bộ nhớ cho phép giữ 100,000 số (0.8 MB) mỗi lần
pha 1 tạo 20 run, pha 2 trộn 20 đường; tổng 1.3 giây; kết quả đúng
```

Hai triệu số được chia thành 20 run, trộn một lượt 20 đường, và kết quả được kiểm tra trùng với `sorted()` trong bộ nhớ. Vì `20` run trộn được trong một lượt, dữ liệu chỉ qua đĩa hai lần (một lượt ghi run, một lượt trộn), tức `log_20(20) = 1` lượt trộn. Một lượt trộn cho `k = 1000` run nghĩa là dữ liệu cỡ `1000 × bộ nhớ` vẫn chỉ qua đĩa hai lượt; vì thế sắp xếp ngoài hầu như luôn là hai lượt trong thực tế.

Nguyên tắc này nằm sau `ORDER BY` của cơ sở dữ liệu khi kết quả không vừa `work_mem`, lệnh `sort` của Unix (sắp xếp tạm ra file trong `/tmp`) và giai đoạn shuffle-sort của MapReduce. Cách làm trộn nhiều đường cũng là lý do heap (xem [Tree](/docs/dsa/trees)) có mặt trong trộn `k` danh sách.

## Quan sát và chẩn đoán

- Python: `sorted(data, key=...)` sắp xếp theo khoá trong một lần gọi hàm khoá cho mỗi phần tử (decorate-sort-undecorate tự động); chọn `key` thay vì `cmp` vì nhanh hơn nhiều.
- Sắp xếp nhiều khoá: dùng tuple làm khoá `key=lambda r: (r.a, r.b)`, hoặc gọi `sort` nhiều lần theo thứ tự khoá **ngược** (vì Timsort ổn định).
- Muốn biết thuật toán dùng bao nhiêu so sánh: bọc phép so sánh trong bộ đếm như ở phần Timsort.
- Trong `EXPLAIN` của cơ sở dữ liệu, `Sort Method: external merge  Disk: ...` nghĩa là sắp xếp đã tràn ra đĩa (chặng cơ sở dữ liệu sẽ nói về cách đọc).

| Triệu chứng | Nguyên nhân hay gặp | Cách xử lý |
|---|---|---|
| Sắp xếp tự cài chậm bất thường với dữ liệu đã sắp xếp | quicksort pivot đầu hoặc cuối | pivot ngẫu nhiên hoặc median-of-3, hoặc dùng sort của thư viện |
| Thứ tự các bản ghi bằng nhau thay đổi sau khi sort | thuật toán không ổn định (`std::sort`, quicksort, heap sort) | dùng bản ổn định, hoặc thêm chỉ số ban đầu làm khoá phụ |
| `RecursionError` khi sắp xếp mảng lớn bằng đệ quy | quicksort đệ quy trên dữ liệu xấu | đệ quy nhánh nhỏ, lặp nhánh lớn (độ sâu `O(log n)`) như code trên |
| Hết bộ nhớ khi sắp xếp | merge sort cần bộ nhớ phụ `O(n)` | sắp xếp tại chỗ (heap, quick) hoặc sắp xếp ngoài |
| Sắp xếp `ORDER BY` chậm khi tập kết quả lớn | tràn ra đĩa | tăng bộ nhớ làm việc, hoặc dùng chỉ mục đã sẵn thứ tự (xem chặng cơ sở dữ liệu) |

## Lưu ý

- `n log n` là giới hạn cho thuật toán **dựa trên so sánh**; counting và radix sort thoát được bằng cách dùng giá trị khoá làm chỉ số, đổi lại bị ràng buộc về miền khoá.
- Quicksort `O(n log n)` là trung bình; trường hợp xấu là `O(n^2)` và dễ chạm với pivot cố định và dữ liệu có cấu trúc. Median-of-3 không loại bỏ nó (bảng trên: 501.002 phép ở dữ liệu ngược); introsort mới là câu trả lời có đảm bảo.
- Merge sort ổn định, đáng tin cậy, sát giới hạn dưới nhưng tốn `O(n)` bộ nhớ phụ; heap sort tại chỗ và có chặn trên nhưng chậm hơn trong thực tế vì truy cập bộ nhớ nhảy cóc.
- Insertion sort không chỉ là "thuật toán chậm cho bài tập": nó `O(n)` trên dữ liệu gần sắp xếp và thắng ở đoạn nhỏ, vì vậy nằm bên trong Timsort và introsort.
- Tính ổn định quyết định đúng sai của sắp xếp nhiều khoá. Biết thư viện bạn đang dùng ổn định hay không.
- `sorted()` của Python tuyến tính trên dữ liệu đã có run: đừng "sắp xếp lại" để cho chắc nhưng cũng đừng lo nếu nó đã sẵn thứ tự.
- Radix sort tuyến tính theo lý thuyết nhưng hằng số và bộ nhớ có thể thắng: trong Python thuần nó thua `sorted()` vài lần; so sánh phải trên cùng nền cài đặt.
- Dữ liệu không vừa RAM thì sắp xếp ngoài (tạo run rồi trộn `k` đường); số lượt đọc ghi đĩa mới là chi phí chính.

**Cần biết trước:** Big-O và amortized ở bài [Big-O & Complexity](/docs/dsa/complexity); mảng, dynamic array và linked list ở bài [Array & Linked List](/docs/dsa/arrays-linked-lists).

**Cách đọc bài:** mỗi mục có một câu **Đoán trước** và kết bằng một câu **Thử ngay**. Hãy tự trả lời trong đầu (hoặc ra giấy) rồi mới xem đáp án. Việc tự nhớ lại và tự đoán giúp nhớ lâu hơn nhiều so với chỉ đọc.

## Ý chính

Mảng lấy phần tử theo **chỉ số** trong `O(1)`, nhưng ta thường tra theo **khoá** chứ không theo vị trí. <Term>Hash table</Term> biến khoá thành chỉ số: một **hàm băm** đổi khoá thành một số nguyên, lấy phần dư theo số ô của mảng, và đó là ô cần nhìn. Nếu các khoá rải đều trên các ô, mỗi ô chỉ có vài khoá, và tra, thêm, xoá đều tốn `O(1)` trung bình, dù bảng có một nghìn hay một trăm triệu khoá.

Lời hứa đó có điều kiện. Hai khoá có thể rơi vào cùng một ô (va chạm), và chi phí phụ thuộc vào việc bảng đầy tới đâu (hệ số tải). Bảng phải tự lớn lên trước khi quá đầy, khoá không được đổi sau khi đã chèn, và nếu kẻ tấn công chọn được các khoá cùng rơi vào một ô, mọi thao tác thoái hoá về `O(n)`.

## Từ khoá ra chỉ số

**Đoán trước:** kiểm tra một số có nằm trong `list` một triệu phần tử chậm hơn kiểm tra trong `list` mười nghìn phần tử bao nhiêu lần? Với `set` thì sao?

```python
import timeit
for n in (10_000, 100_000, 1_000_000):
    lst = list(range(n)); st = set(lst); x = n - 1      # x ở cuối: list phải duyệt hết
    t_list = min(timeit.repeat(lambda: x in lst, number=20, repeat=5)) / 20
    t_set = min(timeit.repeat(lambda: x in st, number=20_000, repeat=5)) / 20_000
    print(f"n={n:>9,}: list {t_list * 1e6:>9.1f} µs | set {t_set * 1e6:.3f} µs")
```

```text
n=   10,000: list      91.4 µs | set 0.058 µs
n=  100,000: list    1166.9 µs | set 0.058 µs
n=1,000,000: list   10006.1 µs | set 0.058 µs
```

`list` tăng đúng theo `n`, vì nó so `x` với từng phần tử. `set` gần như không đổi. Nó không duyệt gì cả: nó tính ra ngay ô cần nhìn.

Cách tính có hai bước. **Hàm băm** (hash function) đổi khoá thành một số nguyên lớn. Rồi lấy phần dư cho số ô `cap` để ra chỉ số trong mảng. Python băm số nguyên thành chính nó; với chuỗi, một hàm băm đơn giản có thể trộn từng ký tự vào kết quả:

```python
def h(s):                                    # hàm băm chuỗi đơn giản: trộn từng ký tự
    x = 0
    for ch in s:
        x = (x * 31 + ord(ch)) % 2**64
    return x

cap = 8
for key in (3, 11, 42):
    print(f"khoá {key!r:>8}: hash {hash(key):>20}, ô {hash(key) % cap}")
for key in ("alice", "bob", "carol"):
    print(f"khoá {key!r:>8}: hash {h(key):>20}, ô {h(key) % cap}")
```

```text
khoá        3: hash                    3, ô 3
khoá       11: hash                   11, ô 3
khoá       42: hash                   42, ô 2
khoá  'alice': hash             92903040, ô 0
khoá    'bob': hash                97717, ô 5
khoá  'carol': hash             94431409, ô 1
```

Hàm băm tốt cho bảng cần ba tính chất: **xác định** (cùng khoá luôn ra cùng số), **nhanh**, và **rải đều** (các khoá gần giống nhau vẫn rơi vào các ô khác nhau).

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ mỗi khoá có một giá trị băm riêng, không trùng ai. Thật ra hàm băm chỉ cần rải đều; hai khoá khác nhau hoàn toàn có thể ra cùng ô. Ở trên, `3` và `11` đều vào ô 3. Băm cũng không phải mã hoá: nó không giấu được dữ liệu và không cần đảo ngược được.

**Thử ngay:** bảng 8 ô, `hash(k) = k`. Các khoá `5, 13, 21, 29` rơi vào ô nào?

<Expand title="Đáp án">

Cả bốn vào ô 5, vì chúng cùng dư 5 khi chia 8. Đây là kiểu dữ liệu làm hỏng bảng băm: khoá có quy luật trùng với số ô. Hàm băm thật trộn bit kỹ hơn để tránh chuyện này.

</Expand>

## Va chạm là chuyện chắc chắn xảy ra

Hai khoá cùng rơi vào một ô gọi là **va chạm**. Có thể nghĩ: bảng một triệu ô, nạp vài trăm nghìn khoá mới va chạm. Thử đo.

**Đoán trước:** bảng 1.000.000 ô, khoá rơi vào ô ngẫu nhiên. Trung bình tới khoá thứ bao nhiêu thì có va chạm đầu tiên?

```python
import random

def first_collision(m):
    seen = set()
    while True:
        i = random.randrange(m)              # khoá mới rơi vào một ô ngẫu nhiên
        if i in seen:
            return len(seen) + 1
        seen.add(i)

random.seed(1)
for m in (365, 10_000, 1_000_000):
    trials = [first_collision(m) for _ in range(2000)]
    print(f"m={m:>9,} ô: va chạm đầu tiên trung bình ở khoá thứ {sum(trials) / len(trials):7.1f}  (√m = {m**0.5:5.0f})")
```

```text
m=      365 ô: va chạm đầu tiên trung bình ở khoá thứ    24.8  (√m =    19)
m=   10,000 ô: va chạm đầu tiên trung bình ở khoá thứ   126.5  (√m =   100)
m=1,000,000 ô: va chạm đầu tiên trung bình ở khoá thứ  1268.8  (√m =  1000)
```

Chỉ khoảng `1,25 × √m` khoá là đã va chạm: một triệu ô thì chừng 1.250 khoá. Đây là **nghịch lý ngày sinh**: một lớp 23 người đã có quá nửa khả năng có hai người trùng ngày sinh. Vì vậy mọi bảng băm phải được thiết kế để **va chạm rẻ**, chứ không phải để tránh nó. Có hai họ cách làm: chaining và open addressing.

**Thử ngay:** bảng có 10.000 ô. Va chạm đầu tiên xảy ra quanh khoá thứ mấy?

<Expand title="Đáp án">

Khoảng `1,25 × √10.000 = 125`, khớp với dòng giữa của output.

</Expand>

## Chaining: mỗi ô là một danh sách

Cách trực tiếp nhất: mỗi ô (bucket) giữ một danh sách các cặp khoá–giá trị rơi vào ô đó. Tìm một khoá thì tính ô, rồi so khoá với từng phần tử trong danh sách của ô.

```python
class ChainingTable:
    def __init__(self, cap=8):
        self.buckets = [[] for _ in range(cap)]
        self.cmp = 0                          # đếm số lần so sánh khoá
    def _bucket(self, key):
        return self.buckets[hash(key) % len(self.buckets)]
    def put(self, key, val):
        b = self._bucket(key)
        for i, (k, _) in enumerate(b):
            self.cmp += 1
            if k == key: b[i] = (key, val); return
        b.append((key, val))
    def get(self, key):
        for k, v in self._bucket(key):
            self.cmp += 1
            if k == key: return v
        raise KeyError(key)

t = ChainingTable(8)
for k in (3, 11, 19, 6, 14):
    t.put(k, f"v{k}")
for i, b in enumerate(t.buckets):
    if b: print(f"ô {i}: {[k for k, _ in b]}")
t.cmp = 0; t.get(19)
print("get(19) so sánh", t.cmp, "khoá")
```

```text
ô 3: [3, 11, 19]
ô 6: [6, 14]
get(19) so sánh 3 khoá
```

Chi phí phụ thuộc độ dài danh sách. Gọi <Term>load factor</Term> (hệ số tải) là `α = n / m`: số khoá chia số ô. Với hàm băm rải đều, mỗi danh sách dài trung bình `α`, và tìm một khoá có sẵn tốn trung bình khoảng `1 + α/2` lần so sánh.

**Đoán trước:** nạp 100.000 khoá ngẫu nhiên, đo số lần so sánh trung bình khi `α` là 0,5, 1, 2 và 4.

```python
def avg_cmp_chaining(alpha, N=100_000):
    t = ChainingTable(int(N / alpha))
    ks = random.sample(range(10**9), N)
    for k in ks: t.put(k, 1)
    t.cmp = 0
    for k in ks: t.get(k)
    return t.cmp / N

random.seed(3)
for a in (0.5, 1, 2, 4):
    print(f"α = {a}: {avg_cmp_chaining(a):.2f} lần so sánh mỗi lần tìm thấy (lý thuyết 1 + α/2 = {1 + a/2:.2f})")
```

```text
α = 0.5: 1.25 lần so sánh mỗi lần tìm thấy (lý thuyết 1 + α/2 = 1.25)
α = 1: 1.50 lần so sánh mỗi lần tìm thấy (lý thuyết 1 + α/2 = 1.50)
α = 2: 2.00 lần so sánh mỗi lần tìm thấy (lý thuyết 1 + α/2 = 2.00)
α = 4: 3.00 lần so sánh mỗi lần tìm thấy (lý thuyết 1 + α/2 = 3.00)
```

Số đo bám sát công thức. Chaining **thoái hoá nhẹ nhàng**: bảng chứa gấp bốn lần số ô vẫn chỉ cần 3 lần so sánh. Nhưng chi phí vẫn tăng theo `α`, nên muốn `O(1)` thì phải giữ `α` dưới một hằng số, bằng cách cho bảng lớn lên (mục "Bảng phải lớn lên" bên dưới).

**Thử ngay:** bảng chaining 1.000 ô chứa 1.000.000 khoá và không bao giờ lớn lên. Tìm một khoá tốn khoảng bao nhiêu lần so sánh? Bảng này còn là `O(1)` không?

<Expand title="Đáp án">

`α = 1000`, nên khoảng `1 + 1000/2 ≈ 501` lần. Không còn `O(1)`: số ô cố định thì mỗi danh sách dài `n / 1000`, chi phí tăng tuyến tính theo `n`, chỉ chậm hơn tìm tuyến tính một hằng số.

</Expand>

## Open addressing: va chạm thì tìm ô trống khác

Chaining cần một danh sách cho mỗi ô, tức thêm con trỏ và thêm object rải rác trong bộ nhớ. <Term>Open addressing</Term> để mọi khoá nằm thẳng trong một mảng. Khi ô của khoá đã có người khác, nó đi tìm ô khác theo một quy tắc cố định. Quy tắc đơn giản nhất là **linear probing**: thử ô kế tiếp `i+1, i+2, ...`, tới cuối mảng thì quay về đầu. Mỗi lần đọc một ô gọi là một lần **thăm** (probe).

Tìm kiếm đi theo đúng đường đó: bắt đầu ở ô nhà, đi tiếp tới khi gặp khoá (tìm thấy) hoặc gặp một ô **trống** (chắc chắn không có, vì nếu có thì khoá đã được đặt vào ô trống đó hoặc trước nó).

```python
EMPTY, DELETED = object(), object()          # ô chưa dùng, ô đã xoá (bia mộ)

class LinearProbingTable:
    def __init__(self, cap=8):
        self.keys = [EMPTY] * cap; self.vals = [None] * cap
        self.probes = 0                       # đếm số ô đã thăm
    def _find(self, key):
        """Trả về (ô chứa key hoặc None, ô trống đầu tiên có thể dùng để chèn)."""
        cap = len(self.keys); i = hash(key) % cap; free = None
        for _ in range(cap):
            self.probes += 1
            k = self.keys[i]
            if k is EMPTY:
                return None, (i if free is None else free)
            if k is DELETED:
                if free is None: free = i     # nhớ chỗ để chèn, nhưng vẫn đi tiếp
            elif k == key:
                return i, None
            i = (i + 1) % cap
        return None, free
    def put(self, key, val):
        i, free = self._find(key)
        if i is None: i = free
        self.keys[i], self.vals[i] = key, val
    def get(self, key):
        i, _ = self._find(key)
        if i is None: raise KeyError(key)
        return self.vals[i]
    def delete(self, key):
        i, _ = self._find(key)
        if i is None: raise KeyError(key)
        self.keys[i], self.vals[i] = DELETED, None

def show(t):
    return " ".join("." if k is EMPTY else "X" if k is DELETED else str(k) for k in t.keys)
```

Bảng này chưa tự lớn lên; mục sau sẽ bàn. Phần `DELETED` (bia mộ) được giải thích ở Ví dụ 3.

### Mô phỏng linear probing bằng tay

Đọc được bảng open addressing là kỹ năng cần để hiểu vì sao nó chậm khi đầy. Ba ví dụ dưới dùng bảng 8 ô và `hash(k) = k`, tức ô nhà là `k % 8`.

#### Ví dụ 1 (giải sẵn): chèn 3, 11, 19, 6, 14

1. `3`: ô nhà 3 trống, đặt vào ô 3.
2. `11`: ô nhà `11 % 8 = 3` đã có `3`, thử ô 4, trống, đặt vào ô 4.
3. `19`: ô nhà 3 có `3`, ô 4 có `11`, ô 5 trống, đặt vào ô 5.
4. `6`: ô nhà 6 trống, đặt vào ô 6.
5. `14`: ô nhà 6 có `6`, ô 7 trống, đặt vào ô 7.
6. Tìm `19` phải thăm 3 ô (3, 4, 5). Tìm `14` thăm 2 ô (6, 7).

```python
t = LinearProbingTable(8)
for k in (3, 11, 19, 6, 14): t.put(k, 1)
print("bảng:", show(t))
for k in (19, 14):
    t.probes = 0; t.get(k); print(f"get({k}) thăm {t.probes} ô")
```

```text
bảng: . . . 3 11 19 6 14
get(19) thăm 3 ô
get(14) thăm 2 ô
```

Để ý ô 3 tới 7 đã thành một đoạn liền. Khoá nào có ô nhà rơi vào bất kỳ đâu trong đoạn này cũng phải đi tới cuối đoạn, rồi nằm ở đó và làm đoạn dài thêm. Hiện tượng này gọi là **tụ cụm** (clustering).

#### Ví dụ 2 (giải một nửa): chèn thêm 27

Tiếp tục từ bảng trên. Điền vào chỗ trống:

1. Ô nhà của `27` là `27 % 8 =` ___.
2. Các ô từ đó tới ô 7 đều đã có khoá, nên nó quay về đầu mảng và đặt ở ô ___.
3. Chèn `27` phải thăm ___ ô.

<Expand title="Đáp án">

1. Ô 3.
2. Ô 0: các ô 3, 4, 5, 6, 7 đều có khoá, quấn về ô 0 thì trống.
3. 6 ô (3, 4, 5, 6, 7, 0).

```python
t.probes = 0; t.put(27, 1)
print("bảng:", show(t), f"| chèn 27 thăm {t.probes} ô")
```

```text
bảng: 27 . . 3 11 19 6 14 | chèn 27 thăm 6 ô
```

Một khoá có ô nhà là 3 phải đi 6 ô, chỉ vì đoạn tụ cụm đã dài. Bảng mới đầy 6/8.

</Expand>

#### Ví dụ 3 (tự làm): xoá rồi tìm

Tiếp tục từ bảng có `27`. Xoá `11` (ở ô 4). Rồi tìm `19`.

Nếu xoá bằng cách đặt ô 4 về **trống**, tìm `19` sẽ ra kết quả gì? Vì sao bảng phải đặt một **bia mộ** (tombstone, `X`) thay vì để trống? Sau khi xoá bằng bia mộ, tìm `19` thăm bao nhiêu ô, và tìm `35` (không có trong bảng) thăm bao nhiêu ô?

<Expand title="Đáp án">

Nếu ô 4 trống, tìm `19` đi từ ô 3 (có `3`), sang ô 4, gặp ô trống và kết luận "không có", dù `19` vẫn nằm ở ô 5. Ô trống là tín hiệu dừng, nên xoá không được tạo ra ô trống giữa đường đi của khoá khác.

Bia mộ nói "ô này từng có khoá, cứ đi tiếp". Tìm `19`: ô 3, 4 (bia mộ), 5, là 3 ô. Tìm `35`: ô nhà 3, rồi 4, 5, 6, 7, 0, 1, gặp ô 1 trống mới dừng, là 7 ô.

```python
t.delete(11)
print("bảng:", show(t))
for k in (19, 35):
    t.probes = 0
    try: t.get(k); kq = "thấy"
    except KeyError: kq = "không có"
    print(f"get({k}): {kq}, thăm {t.probes} ô")
```

```text
bảng: 27 . . 3 X 19 6 14
get(19): thấy, thăm 3 ô
get(35): không có, thăm 7 ô
```

Bia mộ không chứa khoá nhưng vẫn làm đường tìm dài ra. Chèn mới được phép dùng lại ô bia mộ (biến `free` trong code), còn dọn hẳn thì phải đợi lần bảng lớn lên và chèn lại mọi khoá.

</Expand>

### Bảng đầy thì linear probing chậm rất nhanh

Lý thuyết (Knuth) cho số ô thăm trung bình theo `α` khi khoá rải đều:

| | Tìm thấy | Tìm không có |
|---|---|---|
| Linear probing | `½ (1 + 1/(1−α))` | `½ (1 + 1/(1−α)²)` |

**Đoán trước:** ở `α = 0,9`, tìm một khoá **không có** trong bảng tốn trung bình bao nhiêu lần thăm: khoảng 2, khoảng 10, hay khoảng 50?

```python
def avg_probes_lp(alpha, N=100_000):
    t = LinearProbingTable(int(N / alpha))
    ks = random.sample(range(10**9), N)
    for k in ks: t.put(k, 1)
    t.probes = 0
    for k in ks: t.get(k)
    hit = t.probes / N
    t.probes = 0
    for k in random.sample(range(10**9, 2 * 10**9), N):
        try: t.get(k)
        except KeyError: pass
    return hit, t.probes / N

random.seed(5)
print(f"{'α':>5} | {'tìm thấy: đo / lý thuyết':>25} | {'không có: đo / lý thuyết':>25}")
for a in (0.25, 0.5, 0.75, 0.9):
    hit, miss = avg_probes_lp(a)
    print(f"{a:>5} | {hit:>13.2f} / {0.5 * (1 + 1 / (1 - a)):>6.2f} | {miss:>13.2f} / {0.5 * (1 + 1 / (1 - a)**2):>6.2f}")
```

```text
    α |  tìm thấy: đo / lý thuyết |  không có: đo / lý thuyết
 0.25 |          1.17 /   1.17 |          1.39 /   1.39
  0.5 |          1.50 /   1.50 |          2.49 /   2.50
 0.75 |          2.50 /   2.50 |          8.55 /   8.50
  0.9 |          5.34 /   5.50 |         45.77 /  50.50
```

Từ `α = 0,5` lên `0,9`, tìm không có tăng từ khoảng 2,5 lên gần 46 lần thăm (lý thuyết 50,5), vì nó phải đi hết đoạn tụ cụm mới gặp ô trống. Chi phí tăng theo `1/(1−α)²`, nên bảng open addressing phải giữ `α` thấp, thường dưới 0,5 tới 0,75.

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ bảng băm đầy 90% vẫn nhanh như bảng đầy 50%, chỉ là tốn ít RAM hơn. Thật ra với open addressing, đi từ 50% lên 90% làm thao tác tìm không có chậm đi khoảng 20 lần. Mỗi bảng băm thật đều có một ngưỡng `α` tối đa, và chọn ngưỡng là đánh đổi giữa RAM và thời gian.

Bù lại, khi `α` thấp, open addressing thường nhanh hơn chaining trên máy thật: các ô cần thăm nằm liền nhau trong mảng, nên thân thiện cache (xem bài [Array & Linked List](/docs/dsa/arrays-linked-lists)). `dict` và `set` của Python dùng open addressing.

**Thử ngay:** một bảng linear probing có 1.000 ô. Bạn muốn tìm không có tốn trung bình không quá khoảng 5 lần thăm. Bảng được chứa tối đa khoảng bao nhiêu khoá?

<Expand title="Đáp án">

Cần `½ (1 + 1/(1−α)²) ≤ 5`, tức `1/(1−α)² ≤ 9`, `1−α ≥ 1/3`, `α ≤ 2/3`. Khoảng 666 khoá. Ngưỡng hai phần ba này cũng chính là ngưỡng `dict` của Python dùng.

</Expand>

## Bảng phải lớn lên

Để giữ `α` dưới ngưỡng, bảng làm như dynamic array: khi vượt ngưỡng thì cấp mảng mới lớn gấp đôi (hoặc hơn) và **băm lại** (rehash) mọi khoá vào mảng mới, vì số ô đổi thì `hash % cap` cũng đổi. Một lần rehash tốn `O(n)`, nhưng hiếm, nên chi phí chia đều ra vẫn là `O(1)` amortized, đúng như phân tích dynamic array ở bài [Big-O & Complexity](/docs/dsa/complexity).

**Đoán trước:** `dict` của Python đổi kích thước ở những số phần tử nào?

```python
import sys
d, last, sizes = {}, sys.getsizeof({}), []
for i in range(200):
    d[i] = i
    if sys.getsizeof(d) != last:
        sizes.append(len(d)); last = sys.getsizeof(d)
print("dict đổi kích thước khi có:", sizes, "phần tử")
n = 100_000
print(f"{n:,} phần tử: dict {sys.getsizeof({i: i for i in range(n)}):,} byte | list {sys.getsizeof(list(range(n))):,} byte (chưa tính object int)")
```

```text
dict đổi kích thước khi có: [1, 6, 11, 22, 43, 86, 171] phần tử
100,000 phần tử: dict 5,242,960 byte | list 800,056 byte (chưa tính object int)
```

Phần tử đầu tiên tạo bảng 8 ô; các lần sau rơi vào các số `6, 11, 22, 43, 86, 171`, tức mỗi bảng cho dùng khoảng hai phần ba số ô rồi gấp đôi. Cái giá là bộ nhớ: cùng 100.000 phần tử, `dict` tốn gấp vài lần `list`. Bảng băm mua tốc độ bằng RAM.

**Thử ngay:** vì sao khi bảng lớn lên, không thể chép các khoá sang đúng vị trí cũ trong mảng mới như dynamic array?

<Expand title="Đáp án">

Vị trí của một khoá là `hash(k) % cap`. `cap` đổi thì vị trí đổi: với `cap = 8` khoá `11` ở ô 3, với `cap = 16` nó phải ở ô 11. Chép nguyên vị trí thì lần tìm sau sẽ nhìn vào ô 11 và không thấy. Phải tính lại vị trí cho từng khoá.

</Expand>

## Khoá phải băm được và không đổi

Bảng băm chỉ đúng nếu hai điều luôn giữ: **khoá bằng nhau thì hash bằng nhau**, và **hash của một khoá không đổi** trong lúc nó nằm trong bảng.

**Đoán trước:** chèn một object vào `dict`, rồi sửa một trường của nó. Còn tìm thấy nó không?

```python
class Point:
    def __init__(self, x, y): self.x, self.y = x, y
    def __eq__(self, o): return (self.x, self.y) == (o.x, o.y)
    def __hash__(self): return hash((self.x, self.y))

p = Point(1, 2)
d = {p: "A"}
p.x = 99                                    # sửa khoá sau khi đã chèn
print("p in d:", p in d, "| Point(99, 2) in d:", Point(99, 2) in d, "| Point(1, 2) in d:", Point(1, 2) in d)
print("nhưng dict vẫn có", len(d), "mục:", list(d.values()))
try:
    {[1, 2]: "B"}
except TypeError as e:
    print("dùng list làm khoá ->", e)
```

```text
p in d: False | Point(99, 2) in d: False | Point(1, 2) in d: False
nhưng dict vẫn có 1 mục: ['A']
dùng list làm khoá -> unhashable type: 'list'
```

Khoá "biến mất" dù vẫn nằm trong bảng. Tìm `p` thì tính hash mới, nhìn vào ô mới, không thấy. Tìm `Point(1, 2)` thì nhìn đúng ô cũ, nhưng so sánh với `p` giờ là `(99, 2)` nên không bằng. Python chặn trước cho các kiểu có thể đổi: `list`, `dict`, `set` không băm được. Khi tự viết class làm khoá, cài `__eq__` và `__hash__` cùng nhau, và chỉ băm các trường không bao giờ đổi.

**Hiểu lầm hay gặp ở đây:** nhiều người nghĩ cài `__eq__` là đủ để dùng object làm khoá. Thật ra nếu `a == b` mà `hash(a) != hash(b)`, hai khoá bằng nhau sẽ nằm ở hai ô khác nhau, và `dict` coi chúng là hai mục. Python tự đặt `__hash__ = None` khi bạn cài `__eq__` mà không cài `__hash__`, để báo lỗi sớm.

**Thử ngay:** `d = {1: "a"}`, rồi `d[1.0] = "b"`, rồi `d[True] = "c"`. `d` có mấy mục?

<Expand title="Đáp án">

Một mục, giá trị `"c"`. `1 == 1.0 == True` trong Python, và Python đảm bảo hash của chúng bằng nhau, nên cả ba là cùng một khoá.

</Expand>

## Khi kẻ tấn công chọn khoá: hash flooding

Mọi phân tích ở trên giả định khoá rải đều. Nếu khoá do **người dùng** gửi lên (tên trường trong JSON, tham số URL) và hàm băm ai cũng biết, kẻ tấn công có thể dựng hàng nghìn khoá cùng rơi vào một ô. Bảng thoái hoá thành một danh sách dài: mỗi lần chèn tốn `O(n)`, cả đợt tốn `O(n^2)`. Đây là **hash flooding**, được công bố rộng năm 2011 và ảnh hưởng PHP, Java, Ruby, Python thời đó.

Hàm băm chuỗi cổ điển của Java là `h = 31 × h + ký_tự`. Với nó, `"Aa"` và `"BB"` cùng ra `2112`, nên mọi cách ghép các khối `"Aa"` và `"BB"` cũng cùng hash: `k` khối cho `2^k` chuỗi va chạm.

**Đoán trước:** cùng 16.384 khoá, chèn khoá ngẫu nhiên và chèn khoá va chạm cố ý vào bảng chaining dùng hàm băm này. Số lần so sánh chênh nhau bao nhiêu?

```python
import itertools, time

def java_hash(s):
    x = 0
    for ch in s:
        x = (31 * x + ord(ch)) & 0xFFFFFFFF
    return x

def colliding(k):
    return ["".join(p) for p in itertools.product(["Aa", "BB"], repeat=k)]

print('java_hash("Aa") =', java_hash("Aa"), '| java_hash("BB") =', java_hash("BB"))

def trial(name, keys):
    buckets = [[] for _ in range(1 << 16)]
    cmp, t0 = 0, time.perf_counter()
    for key in keys:
        b = buckets[java_hash(key) % len(buckets)]
        for k in b:
            cmp += 1
            if k == key: break
        else:
            b.append(key)
    print(f"{name:<22} {len(keys):>6} khoá: {cmp:>11,} lần so sánh, {(time.perf_counter() - t0) * 1000:8.1f} ms")

random.seed(5)
for k in (10, 12, 14):
    bad = colliding(k)
    good = ["".join(random.choices("abcdefghijklmnopqrstuvwxyz", k=2 * k)) for _ in bad]
    trial(f"ngẫu nhiên (2^{k})", good)
    trial(f"va chạm cố ý (2^{k})", bad)
```

```text
java_hash("Aa") = 2112 | java_hash("BB") = 2112
ngẫu nhiên (2^10)        1024 khoá:          11 lần so sánh,      3.0 ms
va chạm cố ý (2^10)      1024 khoá:     523,776 lần so sánh,     45.6 ms
ngẫu nhiên (2^12)        4096 khoá:         143 lần so sánh,     28.7 ms
va chạm cố ý (2^12)      4096 khoá:   8,386,560 lần so sánh,    621.7 ms
ngẫu nhiên (2^14)       16384 khoá:       2,055 lần so sánh,     89.4 ms
va chạm cố ý (2^14)     16384 khoá: 134,209,536 lần so sánh,   9688.9 ms
```

Khoá va chạm cố ý tốn đúng `n(n−1)/2` lần so sánh (với `n = 1024` là 523.776), còn khoá ngẫu nhiên chỉ vài nghìn. Mỗi lần số khoá gấp 4, thời gian gấp khoảng 15, đúng dáng `n^2`. 16.384 chuỗi 28 ký tự, chưa tới nửa MB dữ liệu, làm một lõi CPU bận gần 10 giây.

Cách phòng thủ chính là **hàm băm có khoá bí mật**: mỗi tiến trình bốc ngẫu nhiên một khoá lúc khởi động, và hàm băm phụ thuộc khoá đó, nên kẻ tấn công không tính trước được va chạm. Python từ 3.4 dùng SipHash (Aumasson và Bernstein, 2012) cho `str` và `bytes`. Chạy cùng một lệnh ba lần:

```python
import subprocess, sys, os
code = "print(hash('hello'))"
for run in range(3):
    env = dict(os.environ); env.pop("PYTHONHASHSEED", None)
    out = subprocess.run([sys.executable, "-c", code], capture_output=True, text=True, env=env).stdout.strip()
    print(f"lần chạy {run + 1}: hash('hello') = {out}")
print("hash(12345) =", hash(12345), "(số nguyên thì không ngẫu nhiên hoá)")
```

```text
lần chạy 1: hash('hello') = 2885855912509067683
lần chạy 2: hash('hello') = -1512185736645333005
lần chạy 3: hash('hello') = -2838406719917167643
hash(12345) = 12345 (số nguyên thì không ngẫu nhiên hoá)
```

Mỗi lần chạy, `hash('hello')` khác nhau. Hệ quả: **đừng lưu `hash()` của Python ra file hay gửi qua mạng**, và đừng dựa vào thứ tự duyệt một `set` chuỗi, vì nó có thể đổi giữa hai lần chạy. Cần giá trị băm ổn định thì dùng `hashlib`. Java chọn cách khác: từ Java 8, một bucket quá dài được đổi thành cây cân bằng, nên trường hợp xấu nhất còn `O(log n)` mỗi thao tác.

**Thử ngay:** Python ngẫu nhiên hoá hash của chuỗi nhưng không ngẫu nhiên hoá hash của số nguyên. Một API nhận JSON có khoá là chuỗi rồi đổi sang `dict`. Nó có an toàn trước hash flooding không? Nếu API nhận một danh sách số nguyên rồi đưa vào `set` thì sao?

<Expand title="Đáp án">

Khoá chuỗi thì an toàn, vì kẻ tấn công không biết khoá bí mật của SipHash. Số nguyên thì đoán được (`hash(k) = k`), nên vẫn có thể chọn các số rơi vào cùng chuỗi thăm. Chuỗi thăm của CPython có trộn thêm các bit cao của hash nên khó hơn linear probing thuần, nhưng không có bảo đảm như khoá bí mật. Giới hạn số phần tử nhận vào là lớp phòng thủ bổ sung.

</Expand>

## Đi sâu hơn

Các phần dưới không cần để đọc tiếp chặng DSA.

<Expand title="Robin Hood hashing: cùng trung bình, đuôi ngắn hẳn">

Linear probing có khoá may (nằm ngay ô nhà) và khoá xui (bị đẩy đi rất xa). **Robin Hood hashing** lưu kèm mỗi khoá khoảng cách `dist` từ ô nhà tới ô nó đang ở. Khi chèn, nếu gặp một khoá có `dist` nhỏ hơn khoá đang chèn, tức "giàu" hơn, thì cướp ô của nó và đẩy nó đi tiếp. Khi tìm, nếu khoảng cách đã đi vượt `dist` của ô đang đứng thì khoá chắc chắn không có, nên dừng sớm.

```python
import statistics

class RobinHood:
    def __init__(self, cap):
        self.cap, self.keys, self.dist = cap, [None] * cap, [0] * cap
    def put(self, key):
        i, d = hash(key) % self.cap, 0
        while True:
            if self.keys[i] is None:
                self.keys[i], self.dist[i] = key, d; return
            if self.dist[i] < d:                     # kẻ đang ở đây giàu hơn: cướp chỗ
                key, self.keys[i] = self.keys[i], key
                d, self.dist[i] = self.dist[i], d
            i = (i + 1) % self.cap; d += 1
    def probes(self, key):
        i, d = hash(key) % self.cap, 0
        while self.keys[i] is not None and d <= self.dist[i]:
            if self.keys[i] == key: return d + 1
            i = (i + 1) % self.cap; d += 1
        return d + 1

class PlainLP:
    def __init__(self, cap): self.cap, self.keys = cap, [None] * cap
    def put(self, key):
        i = hash(key) % self.cap
        while self.keys[i] is not None: i = (i + 1) % self.cap
        self.keys[i] = key
    def probes(self, key):
        i, d = hash(key) % self.cap, 1
        while self.keys[i] is not None:
            if self.keys[i] == key: return d
            i = (i + 1) % self.cap; d += 1
        return d

random.seed(11)
N, cap = 90_000, 100_000                             # α = 0,9
ks = random.sample(range(10**9), N); miss = random.sample(range(10**9, 2 * 10**9), N)
print(f"{'':<15} {'thấy: TB':>9} {'lâu nhất':>9} | {'không có: TB':>13} {'lâu nhất':>9}")
for name, cls in (("linear probing", PlainLP), ("Robin Hood", RobinHood)):
    t = cls(cap)
    for k in ks: t.put(k)
    hit = [t.probes(k) for k in ks]; mis = [t.probes(k) for k in miss]
    print(f"{name:<15} {statistics.mean(hit):>9.2f} {max(hit):>9} | {statistics.mean(mis):>13.2f} {max(mis):>9}")
```

```text
                 thấy: TB  lâu nhất |  không có: TB  lâu nhất
linear probing       5.66       548 |         51.11       761
Robin Hood           5.66        37 |          6.12        38
```

Trung bình khi tìm thấy bằng nhau: Robin Hood không bớt tổng công, nó chia lại công. Nhưng lần tìm lâu nhất ngắn hẳn, và tìm không có nhanh hơn nhiều nhờ dừng sớm. Rust từng dùng Robin Hood cho `HashMap` trước khi chuyển sang SwissTable (`hashbrown`), một biến thể open addressing giữ 1 byte metadata mỗi ô để so 16 ô cùng lúc bằng lệnh SIMD. Go dùng SwissTable cho `map` từ bản 1.24.

</Expand>

<Expand title="Bên trong dict của Python">

Từ Python 3.6, `dict` là **compact dict** với hai mảng: một mảng **chỉ số** thưa (kích thước luỹ thừa của 2, mỗi ô 1 tới 8 byte tuỳ cỡ bảng) và một mảng **entries** dày gồm các bộ `(hash, key, value)` theo **thứ tự chèn**. Tra cứu băm khoá ra ô trong mảng chỉ số, đọc số ở đó để tới entry thật. Mảng thưa chỉ chứa số nhỏ nên ít tốn RAM, entries liền nhau nên duyệt nhanh, và thứ tự chèn được giữ miễn phí (Python 3.7 đưa vào đặc tả).

Chuỗi thăm không phải linear probing thuần: `perturb` bắt đầu bằng hash, mỗi bước `perturb >>= 5` và `i = (5*i + perturb + 1) mod size`. Hai khoá cùng ô nhà nhưng khác bit cao sẽ rẽ hướng khác nhau, giảm tụ cụm.

</Expand>

<Expand title="Consistent hashing: chia khoá cho nhiều máy">

Cụm cache có `N` server, khoá `k` nằm ở server `h(k) mod N`. Thêm một server thì `N` đổi và gần như mọi khoá đổi chỗ, cả cụm cache nguội cùng lúc. **Consistent hashing** đặt cả server lẫn khoá lên một vòng số; khoá thuộc server đầu tiên gặp khi đi theo chiều kim đồng hồ. Thêm server chỉ lấy phần khoá nằm ngay trước nó. Mỗi server xuất hiện nhiều lần trên vòng (virtual node) để chia tải đều.

```python
import bisect, hashlib

def sh(s):                                   # băm ổn định giữa các lần chạy
    return int.from_bytes(hashlib.sha256(s.encode()).digest()[:8], "big")

class Ring:
    def __init__(self, nodes, vnodes=100):
        self.vnodes, self.points, self.owner = vnodes, [], {}
        for n in nodes: self.add(n)
    def add(self, node):
        for i in range(self.vnodes):
            p = sh(f"{node}#{i}"); bisect.insort(self.points, p); self.owner[p] = node
    def get(self, key):
        i = bisect.bisect(self.points, sh(key)) % len(self.points)
        return self.owner[self.points[i]]

keys = [f"user:{i}" for i in range(100_000)]
moved_mod = sum(sh(k) % 10 != sh(k) % 11 for k in keys)
nodes = [f"s{i}" for i in range(10)]
r = Ring(nodes); before = {k: r.get(k) for k in keys}
r.add("s10"); moved = sum(before[k] != r.get(k) for k in keys)
print(f"thêm server thứ 11: h mod N đổi chỗ {moved_mod / len(keys):.1%} khoá, consistent hashing {moved / len(keys):.1%}")
for v in (1, 10, 100, 1000):
    r = Ring(nodes, vnodes=v); load = {n: 0 for n in nodes}
    for k in keys: load[r.get(k)] += 1
    print(f"  {v:>4} vnode/server: server nhiều nhất / ít nhất = {max(load.values()) / min(load.values()):.2f}x")
```

```text
thêm server thứ 11: h mod N đổi chỗ 90.9% khoá, consistent hashing 10.2%
     1 vnode/server: server nhiều nhất / ít nhất = 23.01x
    10 vnode/server: server nhiều nhất / ít nhất = 3.21x
   100 vnode/server: server nhiều nhất / ít nhất = 1.20x
  1000 vnode/server: server nhiều nhất / ít nhất = 1.13x
```

Chia lấy dư làm khoảng `N/(N+1)` khoá đổi chỗ; consistent hashing chỉ khoảng `1/(N+1)`. Với 1 điểm mỗi server, tải lệch rất nặng; vài trăm virtual node thì gần đều. Dynamo, Cassandra và client của Memcached dùng ý tưởng này.

</Expand>

<Expand title="Bảng băm trong các hệ thống thật">

| Hệ thống | Cách làm |
|---|---|
| CPython `dict`, `set` | open addressing, compact dict, SipHash cho chuỗi, lớn lên ở khoảng 2/3 |
| Java `HashMap` | chaining; lớn lên ở `α = 0,75`; bucket từ 8 phần tử đổi thành cây đỏ-đen |
| Rust `HashMap` | SwissTable (`hashbrown`), SipHash-1-3 có khoá |
| Go `map` | SwissTable từ Go 1.24 |
| Redis `dict` | chaining, **rehash dần dần**: giữ hai bảng và chuyển vài bucket mỗi thao tác để không có cú dừng `O(n)` |

Redis chọn rehash dần vì nó cần độ trễ ổn định: một lần rehash `O(n)` trên bảng chục triệu khoá là một cú dừng thấy được.

</Expand>
